# 人工覆核後再接自動化

<!-- learner-content:start -->
## AI建議不是已核准資料
完成物是從Source到ReviewedQueue，再到分流紀錄與未寄出草稿的一筆完整測試。下載[九欄規格](../assets/part5-input-contract.md)、[覆核隊列CSV](../assets/part5-reviewed-queue.csv)與[重建步驟](../assets/part5-rebuild-guide.md)。本節仍用網頁AI，不接API，也不宣稱分類自動完成。

流程是：Source保留原文→人把文字交給AI→人核對→在ReviewedQueue追加完整新列→Make觸發→條件與防重→分流→紀錄與草稿。更新Source的舊列不會讓Watch New Rows讀到新列，這是兩種不同動作。

## 示範：把建議變成可查的資料
```text
請分類以下虛構表單，category只能inquiry、complaint、partnership、other。
姓名小林；email learner@example.com；主旨詢問方案；原文：請問基礎方案月費。
輸出category、summary、next_action三欄。只整理原文，不新增價格或承諾；next_action待人工確認。
```

核對例：inquiry／詢問基礎方案／準備方案說明草稿。補上來源原有的submitted_at、name、email、subject、message；再寫review_status=已覆核，一共九欄。AI只建議三欄，不替你核准。未知價格要查規則，不能在草稿編一個。

## 跟著做：防重與草稿
Filter通過後，用submitted_at、小寫且去前後空白的email、去前後空白的subject組成來源鍵。Google Sheets的Make an API Call讀ProcessingLog的A欄，Router前的Filter用`flatten(4.body.values)`檢查此鍵是否已存在；已有鍵就停止，不新增紀錄或草稿。一次一列序列處理；這能測教材防重，不能保證並行時不重複。

業務與合作分支寫ProcessingLog後，再寫Drafts：recipient填虛構測試郵件、subject填主旨、body保留已核對摘要，status=未寄出。草稿寫入成功後，用Update a Cell把同筆紀錄的draft_status從「待建立」改為「已建立」。此為表格草稿，不接寄信模組。客服只標人工處理，other進待處理；兩者無通知草稿。

如果紀錄成功但草稿失敗，保留draft_status=待建立，先檢查同鍵Drafts是否已存在，再從Make的未完成執行重跑草稿步驟。不要直接重跑整筆造成重複。這條教學流程已用虛構資料試跑；你自己的成果仍須附自己的執行證據。

## 自己試：不讓AI的錯值混進後段
讓AI把同一原文分成complaint時，你應回原文判斷這是詢問，修回inquiry再入列。重複追加同來源鍵，應被防重；把時間改掉會變新鍵，不能用改時間「修好」重複測試。

交付Source、九欄覆核列、執行紀錄、分流紀錄與草稿。下節測失敗恢復。沒有Google／Make權限，先做完整欄位演練，自動化能力仍待驗。
