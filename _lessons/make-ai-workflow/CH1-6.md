## 教學流程（Teaching Flow）

### 破題 / Hook

前五節已經把流程拆解、契約、最小可跑路徑、LLM 設計與 JSON 修改串起來。最後一節不再新增一堆工具，而是要證明你能把同一套方法轉到另一個工作情境，並把成果交給沒有參與課堂的人。

阿凱選擇「每週彙整客戶回饋」作為變體：基準流程仍是 Sheets → Gemini → Filter → Docs；本節只練習批次彙整，或把來源替換成 Gmail，讓 LLM 協助列出需要重新檢查的模組與測試。最後把安全藍圖、變更紀錄、測試結果與交接說明整理成一個可展示的資料夾。

**本節完成物**：

1. variant-v1：一個只改一個主要變因的工作流變體與設計規格。
2. handoff-pack-v1：包含流程圖、資料契約、變更紀錄、測試案例、已知限制與還原步驟。
3. demo-record-v1：五分鐘展示腳本，能說明需求、操作、結果與失敗出口。

**起始狀態**：你有 CH1-4 的 workflow-spec-v1、CH1-5 的 blueprint-safe-v1.json 與 diff-log-v1；CH1-3 依模式提供 `scenario-v1`（Make）或 `scenario-v1-offline-map` 與 `run-log-v1-simulated`（離線）。若無法執行 Make，使用固定輸出、流程表與測試紀錄完成離線交接包，不把它寫成已執行 Scenario。

### 概念 / Concepts

#### 變體不是重做一門新課

變體是保留核心契約與可重用模組，只修改一個明確的工作條件。這讓你能回答「哪裡變了」與「哪些證據要重跑」，而不是把所有成果重新複製一遍。

| 變因 | 保持不變 | 必須重新驗證 |
|---|---|---|
| 批次彙整 | 輸入／輸出契約、人工確認出口 | Iterator 或彙整模組、批次測試 |
| Gmail 來源 | Gemini 輸出、Filter、Docs | sender、subject + body 映射 |

**正例**：選擇「批次彙整」一個變因，保留 summary、reply_draft、needs_review，只有增加資料集合與彙整規則。  
**錯例**：同時換來源、改 prompt、刪 Filter、加入額外動作，最後無法知道哪個變更造成結果不同。  
**你要判斷**：若選 Gmail 來源，只重做來源欄位映射與相關測試；不要改動既有的 Filter、Docs 與人工出口。

#### 交接包的最低證據

交接包不是把所有檔案丟進資料夾，而是讓接手者能回答五件事：這個版本解決什麼問題、從哪裡開始、哪些欄位不變、如何測試成功、失敗時如何停止或還原。

| 交接內容 | 可觀察證據 |
|---|---|
| 目的與範圍 | 一段變體說明與不變條件 |
| 流程結構 | 模組與欄位映射圖 |
| 測試 | 成功、停止、錯誤至少三條案例 |
| 安全與限制 | 去敏 JSON、未實作出口與不得做的事 |
| 還原 | 原始版本、差異摘要與還原步驟 |

### 操作示範 / Demo：把 scenario-v1 轉成批次彙整變體

#### 變體需求

> 每週將多筆客戶回饋整理成一份摘要文件；每筆資料仍要先符合輸入契約，任何一筆需要人工確認時，整批先停在 CH1-3 的待人工確認出口，不建立文件。

**唯一主要變因**：從「一次處理一筆」改為「一次處理一批」。來源、Gemini 輸出契約、Filter 安全條件與 Docs 交付先保持不變。

#### 變體規格完成品

| 階段 | 模組／資料 | 保持不變 | 變更內容 | 驗證證據 |
|---|---|---|---|---|
| 1 | Sheets / Watch Rows | source 欄位映射 | 收集一週資料集合 | 有 3 筆合法 bundle |
| 2 | Iterator／批次整理 | 每筆輸入契約 | 逐筆檢查必填與型別 | 缺值列被標記，不送 Gemini |
| 3 | Gemini / Generate | 三個輸出欄位 | 依集合產生批次摘要 | 每筆輸入與輸出可追溯 |
| 4 | Filter | true 必須停下 | 任一筆 true 即整批待人工 | 有待人工確認狀態與負責人 |
| 5 | Google Docs | 文件 URL 與內容檢查 | 建立每週摘要文件 | 文件含期間、來源筆數、摘要 |

#### 測試案例完成品

| 案例 | 資料變更 | 預期狀態 | 交接證據 |
|---|---|---|---|
| A：三筆皆合格 | 3 筆皆有 message_text、needs_review=false | 建立一份每週 Docs | 文件 URL、筆數與摘要 |
| B：一筆需人工 | 第 2 筆 needs_review=true | 整批待人工，不建立 Docs | 待人工確認狀態與負責人 |
| 案例 3：一筆缺值 | 第 3 筆 message_text 空白 | 在 Iterator 停止該列，整批待修正 | 缺值紀錄與重試位置 |

#### 交接者視角

接手者先讀 handoff-pack-v1/README，知道本版本只改批次處理；再看契約與映射，確認來源欄位仍可替換；最後依三條測試案例逐一驗證。若沒有這三層證據，展示再漂亮也只是一次性示範。

### 動手 / Hands-on：完成你的變體與交接包

#### 完成物與最短路徑

- **完成物**：variant-v1、handoff-pack-v1、demo-record-v1。
- **起始狀態**：已開啟本節九份材料，以及 CH1-3～CH1-5 的安全檔、契約、diff 與測試紀錄；建立新資料夾，不覆寫正式版本。先在 README 填寫執行模式 `MAKE` 或 `SIMULATED`。
- **最短可跑路徑**：先選一個變因並寫不變條件，再做規格與測試，最後才整理展示腳本。

#### 步驟 1：選擇一個變因

- **模式**：Together
- **學員操作**：先填寫[變體選擇單](../../courses/make-ai-workflow/assets/CH1-6-variant-choice.md)，從 A 批次彙整、B Gmail 來源兩個選項選一個；建立 variant-v1，寫變更目的與不變條件。
- **講師提示**：先決定只改什麼，才知道哪些原有證據仍可沿用。
- **預期結果**：變體文件只有一個主要變因，正式 scenario-v1 保持不動。
- **快速檢查**：同學能用一句話說出變體和原版的差異。
- **卡住時**：回到「變因／保持不變／重新驗證」三欄，先選最小範圍。

#### 步驟 2：建立變體規格

- **模式**：Together
- **學員操作**：複製[變體規格模板](../../courses/make-ai-workflow/assets/CH1-6-variant-spec-template.md)，若選批次彙整，同時開啟[三筆批次輸入](../../courses/make-ai-workflow/assets/CH1-6-batch-input.csv)與[批次模組卡](../../courses/make-ai-workflow/assets/CH1-6-batch-module-cards.md)；列出變體的模組、輸入、輸出、控制條件、未實作出口與需重新驗證的項目，沿用 CH1-2 的契約欄位。
- **講師提示**：新模組不是自動合理；若契約需要改，必須列出版本差異。
- **預期結果**：variant-v1 有完整模組表與欄位映射，不只有一句「加入批次」。
- **快速檢查**：每個新增或移除的模組都有責任與下游影響。
- **卡住時**：先畫原版，再用一種標記表示新增、保留與移除。

#### 步驟 3：請 LLM 協助找影響範圍

- **模式**：Demo → Together
- **學員操作**：把去敏的原版規格、變更目的與契約貼給 LLM，要求只輸出「受影響模組、需重跑測試、未知事項」三張表；沒有 LLM 帳號時，先依[固定輸出 fixture](../../courses/make-ai-workflow/assets/CH1-6-fixed-output-fixtures.json)完成同樣的影響判讀。
- **講師提示**：這次 LLM 只做影響分析，不直接重寫 JSON；安全邊界延續 CH1-5。
- **預期結果**：得到可審查的影響清單，未提供的連線與欄位標為需人工確認。
- **快速檢查**：影響清單能指出至少一個不變模組與一個必須重測模組。
- **卡住時**：補上「不得新增未定義欄位、不得使用 credential、不要產生完整藍圖」。

#### Checkpoint：變體是否只改一個變因

- **現在應該看到**：變更目的、不變條件、影響模組與重測項目互相一致；原版檔案沒有被覆寫。
- **若沒看到**：退回步驟 1 或 2，刪除順手加入的工具與未經需求支持的欄位。
- **通過後才能繼續**：接手者能判斷哪些 CH1-3 測試可沿用，哪些必須重跑。

#### 步驟 4：建立變體測試表

- **模式**：Together
- **Make 路徑**：依[測試矩陣](../../courses/make-ai-workflow/assets/CH1-6-test-matrix.md)與[批次中間輸出](../../courses/make-ai-workflow/assets/CH1-6-batch-intermediate-output.md)設計成功、需要人工、資料缺值三個案例；每案只改一個主要條件，寫輸入、預期結果、實際平台證據與負責人。
- **離線路徑**：使用同一份矩陣與中間輸出設計三個模擬案例；結果欄填預期路由、固定輸出與 `{{simulated_document_url}}`，並標記 `SIMULATED`，不填實際 URL。
- **講師提示**：測試要涵蓋安全停止，不能只有「流程完成」。
- **預期結果**：test cases 能逐案判斷建檔、停止、重試與還原。
- **快速檢查**：Make 每案都有文件 URL、待人工確認狀態或平台錯誤紀錄；離線每案都有固定輸出、預期停止位置與模擬標記。
- **卡住時**：沿用 CH1-3 的成功、人工與錯誤路徑，再把變體差異寫進輸入。

#### 步驟 5：執行或模擬成功案例

- **模式**：Together
- **Make 路徑**：執行成功案例，若選批次彙整，對照[批次中間輸出](../../courses/make-ai-workflow/assets/CH1-6-batch-intermediate-output.md)保存實際輸出、文件 URL、資料筆數、執行 ID 與執行時間；去敏後放入 handoff pack。
- **離線路徑**：用[固定輸出 fixture](../../courses/make-ai-workflow/assets/CH1-6-fixed-output-fixtures.json)與[批次中間輸出](../../courses/make-ai-workflow/assets/CH1-6-batch-intermediate-output.md)填寫預期輸出、`{{simulated_document_url}}`、資料筆數與 `SIMULATED`；不得稱為可查證文件。
- **講師提示**：展示資料要能重現，不要放入真實帳號或客戶內容。
- **預期結果**：Make 成功案例有完整輸出與可查證文件；離線案例有完整固定輸出與預期文件內容，但明確標示尚未在平台驗證。
- **快速檢查**：Make 另一個人能只看紀錄重現成功條件；離線接手者能依固定輸出重建預期判斷。
- **卡住時**：先使用教師固定輸出，將實際連線問題記為限制，不阻塞教學判斷。

#### 步驟 6：執行或模擬停止與錯誤案例

- **模式**：Together
- **Make 路徑**：執行 `needs_review=true` 與 `message_text` 空白的案例，記錄平台停止模組、執行 ID、下游影響、負責人與重試／還原位置；true 案例沿用 CH1-3 的人工出口。
- **離線路徑**：依固定輸出與批次中間輸出推演 `needs_review=true`、缺值兩條出口，記錄預期停止模組、下游影響、負責人與重試／還原位置，標示 `SIMULATED`。
- **講師提示**：停止是交付的一部分；沒有停止證據，不能說變體安全。
- **預期結果**：案例不會建立不合格文件，且有可追蹤處理出口。
- **快速檢查**：Make 交接者能指出平台目前狀態；離線交接者能指出預期狀態，且不把它當成已完成的 Make 執行。
- **卡住時**：回看 CH1-2 的失敗處理表與 CH1-5 diff log。

#### Checkpoint：測試與交接是否閉合

- **現在應該看到**：每個變體變更都有至少一個測試；每個失敗有負責人、停止／記錄／重試／還原位置。
- **若沒看到**：回到步驟 4～6 補測試或修正紀錄，不要先寫展示稿。
- **通過後才能繼續**：handoff-pack-v1 能讓未參與課堂的人開始驗證。

#### 步驟 7：整理交接包

- **模式**：Solo
- **學員操作**：依[交接 README 模板](../../courses/make-ai-workflow/assets/CH1-6-handoff-readme-template.md)建立 handoff-pack-v1 資料夾，放入 README、variant-v1、契約與映射、blueprint-safe、diff-log、test-cases、限制與還原說明；檔名與版本一致。
- **講師提示**：資料夾結構本身也是流程的一部分；不要只交一個沒有上下文的 JSON。
- **預期結果**：接手者可依 README 找到起始狀態、操作順序、預期結果與修復方式。
- **快速檢查**：移除你的口頭說明後，另一個人仍能依文件開始。
- **卡住時**：用「先讀 README → 看契約 → 看差異 → 跑測試 → 查還原」五步補齊。

#### 步驟 8：寫五分鐘展示腳本

- **模式**：Check
- **學員操作**：複製[五分鐘展示紀錄](../../courses/make-ai-workflow/assets/CH1-6-demo-record-template.md)為 demo-record-v1，依序寫需求、原版、唯一變因、操作、成功結果、停止結果、限制與下一步；每段指向檔案或欄位。
- **講師提示**：展示不是朗讀工具名稱，而是讓觀眾看見一次決策如何被驗證。
- **預期結果**：五分鐘內可展示一條成功路徑與一條安全停止路徑。
- **快速檢查**：腳本中的每個結論都有文件、欄位、URL 或測試紀錄證據。
- **卡住時**：刪除背景口號，只保留「問題 → 改變 → 操作 → 結果 → 證據」。

### 變化練習 / Solo Transfer

交換變因：若原本做批次彙整，改成 Gmail 來源；若原本做 Gmail，改成批次彙整。只保留原有契約與控制條件，列出新的來源映射或批次規則，以及必須重跑的三個測試，不重寫整個交接包。

### 檢核 / Verification

- [ ] variant-v1 只改一個主要變因，並列出不變條件與重新驗證項目。
- [ ] handoff-pack-v1 包含 README、契約／映射、去敏 JSON、diff log、測試與還原。
- [ ] 測試涵蓋成功、需要人工、資料缺值三條路徑；`MAKE` 案例有執行 ID、URL 或平台錯誤，`SIMULATED` 案例有固定輸出、預期路由與 `SIMULATED` 標記。
- [ ] 交接紀錄說明資料來源、輸入／輸出、控制條件、負責人與既有人工出口。
- [ ] demo-record-v1 可在五分鐘內展示一次成功與一次安全停止。
- [ ] 變體未使用 credential、token、固定帳號或個資；正式原版檔案保持不變。

### 商業情境案例 / Case

雯姊要把阿凱的變體交給另一個專案小組。她不只看文件有沒有產生，而是要求接手者能知道為何改、哪裡不改、怎麼測試與怎麼還原。這使「可交接」成為具體成果，而不是一句口號。

### 常見錯誤 / Pitfalls

1. **變體同時改太多東西**：來源、prompt、資料格式與額外動作一起變。修正是只保留一個主要變因。
2. **交接包只放 JSON**：接手者不知道起始狀態、測試與限制。修正是用 README 串起契約、diff、測試與還原。
3. **展示只講成功**：觀眾看不到安全出口。修正是固定展示一條成功與一條停止／待人工路徑。

### 檢核題 / Quiz

#### Q1

哪一項最能證明工作流變體可交接？

A. 有一個漂亮的流程截圖。  
B. 有版本化規格、契約、測試、失敗出口、限制與還原步驟，接手者可照 README 開始。  
C. 有更多模組。
