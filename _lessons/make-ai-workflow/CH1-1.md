## 教學流程（Teaching Flow）

### 破題：先看一件工作如何被自動完成

阿凱在弄一下行銷工作室收到一筆客戶回饋。現在的做法是：先看試算表的一列資料，再手動請 AI 整理，接著複製到文件，最後寄信通知主管。只要其中一個欄位看錯，文件和 Email 就可能帶著錯誤一起送出去。

他希望把這段重複工作排成一條固定路徑：

```text
客戶回饋的一列資料
  → Gemini 整理成一段文字
  → Google Docs 保存報告
  → Email 通知主管
```

這四個站點連在一起，就是一條自動化流程。今天先不要求你登入平台或設定連線，而是先把這條路徑看懂，因為還不知道資料怎麼移動時，直接按按鈕只會讓錯誤更難找。

這裡說的**資料流**，就是同一筆資料從來源欄位出發，依序經過處理、保存與通知；每一站都會留下下一站能讀的結果。你現在要追的不是四個工具名稱，而是「這一筆資料在每一站變成了什麼」。

先認識本節會用到的四個詞：

- **Make**：把不同服務接成自動化流程的平台。
- **情境流程（Scenario）**：在 Make 裡保存的一條完整自動化路徑；本案例就是「試算表 → Gemini → 文件 → Email」。
- **模組（Module）**：流程中的一個工作站。它接收輸入，完成一個動作，再交出輸出。
- **Blueprint**：把一條已完成的情境流程設定記錄成文字檔的「流程食譜」。這類檔案通常使用 JSON 格式，也就是用欄位記錄設定的文字格式；本節只讀它，不要求你從零編寫 JSON。

因此，本節的學習順序是「先讀懂，再建立」：你會使用教師提供的去敏（已移除連線與個資）Blueprint 與測試資料，把已完成的 4 模組流程整理成一張 `v1-sheets` 地圖。最後才把第一個資料來源想像成 Gmail，做一個只替換來源欄位的 `v2-gmail` 轉移註記。這不是跳過 Make，而是先建立之後設定 Make 所需的資料流概念。

**本節完成物**：一張 `v1-sheets` 四模組地圖（`v1` 表示第一版），包含「順序、模組、角色、輸入、輸出、映射備註、失敗影響」七欄；另附一段 `v2-gmail` 來源替換註記（`v2` 表示只替換資料來源後的第二版）。第一個練習會先給你一份已完成的流程食譜，請你按照資料流把它重畫成地圖；等你能說清楚每個工作站的輸入與輸出，再把同樣的邏輯搬到 Make 畫面。

**本節不處理**：分流、資料格式轉換與人工審核控制。這些會在後續單元用實際模組逐一示範；今天先把四個工作站的資料流讀清楚。

### 概念：四個角色，加上兩個跨模組問題

先把這份案例的四個模組分成四種「工作角色」。這是為了讀圖，不是 Make 的官方模組分類：

| 角色 | 白話問題 | 本案例對應 |
|---|---|---|
| 資料來源 | 第一批資料從哪裡進來？ | Google Sheets / Watch Rows |
| 處理 | 哪個模組把資料變成新的內容？ | Gemini / Create a Completion |
| 內容交付 | AI 結果被保存到哪裡？ | Google Docs / Create a Document |
| 通知 | 誰會收到結果？ | Google Email / Send an Email |

把每個模組想成一個工作站後，再補兩個 Make 介面常見的詞。模組每執行一次，會交出一小包本次資料，Make 稱它為 **Bundle**；在本案例裡，就是「這一列客戶回饋目前帶著哪些值」。Gemini 要做的工作說明，稱為 **Prompt**；你可以先把它理解成「告訴 AI 要讀哪些值、要產出什麼的文字指令」。

四個角色之外，再固定問兩個問題：

1. **資料映射**：把上一個模組交出的值，指定給下一個模組的欄位。要問的是：「上一個模組的哪個欄位，放進下一個模組的哪個欄位？」在本案例中，`{{2.result}}` 讀取第 2 號（Gemini）模組的 `result` 欄位，接著同時成為 Docs 內容與 Email 內文。
2. **失敗影響**：這個模組沒有交出預期結果時，下游哪裡會停、誰要接手、要從哪個模組重跑？

**正例**：位置鍵是匯出檔裡暫時使用的欄位編號；把 `google-sheets:watchRows` 的位置鍵 `1`、`2`、`3` 對照成「姓名、評分、回饋」，再說明這三個值如何進入 Gemini Prompt。

**非例**：只寫「Sheets → AI → Email」。這只記工具，不足以說明欄位、內容或錯誤位置。

如果文件是空白，先查 `result` 是否真的由 Gemini 產生，以及 Docs 是否映射到 `{{2.result}}`；不要先重建整條流程。

在這個案例裡，資料不是「經過四個工具」就算完成，而是沿著一條有因果的路徑移動：Sheets 先交出一列資料，Gemini 才能把其中三個值放進 Prompt；Gemini 完成後交出 `result`，Docs 與 Email 才能各自使用同一份文字。為了讓接手者看得懂這條路徑，我們在地圖中增加「映射備註」欄。

**映射備註不是另一個輸出欄位**，而是一句把箭頭說完整的話，至少回答三件事：「這個值從哪裡來？要放到哪裡？下一步為什麼需要它？」例如：Sheets 的位置鍵 `3` 代表回饋，所以把它放進 Gemini Prompt 的回饋欄；Gemini 產生的 `result` 再提供給 Docs 內容與 Email 內文。這樣讀者看到備註，就能從前因追到後果，而不是只看到幾個箭頭。

### 操作示範：把已驗證的 4 模組 Blueprint 讀成地圖

以下使用課程提供的去敏（已移除連線與個資）Blueprint 與 `CH1-1-test-data.csv`。你可以把 Blueprint 想成一份「已組好的流程食譜」：先看 `flow` 裡列出的模組，再看每個模組的輸入與輸出，不必先讀懂整份 JSON 語法。原始匯出保留 Make 的模組 ID 與映射寫法，但連線、檔案 ID 與收件人都已改成 placeholder（暫代文字）；這些 placeholder 只是提醒日後要重新綁定，不是要填進地圖的帳號。

Blueprint 裡的編號是**模組 ID**（平台用來辨認每個工作站的編號），不一定連號。本案例的 ID 是 `1`、`2`、`7`、`8`，真正的執行順序仍以流程中的排列為準；地圖另外使用 1–4 表示學習時的順序，避免把「模組身分」和「執行先後」混在一起。

匯出的 Bundle 有時只把欄位叫作位置鍵 `1`、`2`、`3`，沒有直接寫出姓名、評分、回饋。這就是為什麼要先用測試資料對照，再在地圖中補上工作上的語意；位置鍵不是新的資料，而是同一列資料在匯出檔裡的暫時名稱。

本例的時間戳記位於位置鍵 `0`；Docs 會用位置鍵 `0`（時間）與 `1`（姓名）組成文件名稱，而 Gemini 只讀位置鍵 `1`、`2`、`3`。

#### 示範輸入

```text
timestamp = 2026-08-26T09:00:00+08:00
customer_name = 林小姐
rating = 2
feedback = 物流延遲，客服回覆太慢
```

#### 示範中間結果與完成品

先追一筆資料再讀表格：林小姐的「物流延遲，客服回覆太慢」先存在 Sheets 這一列的第 3 個位置；因此它會被放進 Gemini 的回饋欄。Gemini 產生 `result` 後，Docs 用它建立文件，Email 再用同一份 `result` 發出通知。下表的「映射備註」就是把這段前因後果寫給下一位接手者。

| 順序 | 模組 | 角色 | 輸入 | 輸出 | 映射備註（來源、去向與用途） | 失敗影響 |
|---:|---|---|---|---|---|---|
| 1 | Google Sheets / Watch Rows | 資料來源 | 一列試算表資料；匯出 Bundle 的位置鍵 `1`、`2`、`3` | 一列可供下一模組使用的資料 | Sheets 先交出一列；位置鍵 `1`、`2`、`3` 分別代表姓名、評分、回饋，下一步才能把三個值放進 Gemini Prompt | 沒有新列：來源負責人記錄觸發條件，修正工作表後從 Watch Rows 重跑；無法確認時停止，不送空資料 |
| 2 | Gemini / Create a Completion | 處理 | `{{1.\`1\`}}`、`{{1.\`2\`}}`、`{{1.\`3\`}}` | 單一文字欄位 `result` | 因為三個位置值已放進 Prompt，Gemini 才能產生 `result`；這份 `result` 接著提供給 Docs 與 Email | `result` 空白／格式不符：流程負責人記錄錯誤，回到 Prompt 與映射修正，再從 Gemini 重跑；仍失敗則標記待修正並停止 |
| 3 | Google Docs / Create a Document | 內容交付 | 文件名稱 `客服回饋：{{1.\`0\`}}-{{1.\`1\`}}`；內容 `{{2.result}}` | 文件名稱與文件 URL／ID | Sheets 的位置鍵 `0`（時間）與 `1`（姓名）先組成文件名稱；Gemini 的 `result` 再寫入文件內容，形成可保存的交付物 | 沒有文件 URL：文件負責人記錄權限錯誤，修正連線／資料夾後從 Docs 重跑；仍無法建立就停止，不送 Email |
| 4 | Google Email / Send an Email | 通知 | 主旨 `{{7.name}}`、內文 `{{2.result}}`、課堂提供的收件人 placeholder | 寄信狀態或 message ID | Docs 已保存 `result` 後，Email 再沿用同一份文字作為內文，讓收件人收到與文件一致的通知 | 寄信失敗：通知負責人記錄寄信結果，修正收件人／連線後只從 Email 重跑；收件狀態不明則停止並人工確認 |

讀這張表時要注意：這份 4 模組流程沒有額外的分流或人工審核控制。如果工作規則要求人工審核，必須在後續設計中增加可驗證的控制模組；本節先不把尚未建立的規則當成流程的一部分。

#### 用一句話追資料

```text
試算表的一列
  → 位置鍵 1、2、3 進入 Gemini Prompt
  → Gemini 產生單一文字欄位 result
  → result 同時寫入 Google Docs 與 Email 內文
```

這句話就是地圖的最小骨架。接下來的跟做會把骨架展開成七欄；其中「映射備註」要把每個箭頭寫成完整句，讓另一個人可以從欄位、用途與失敗影響接手。

### 動手：完成 `v1-sheets` 地圖，再做 Gmail 來源轉移

#### 起始狀態與環境界線

- **檔案**：`courses/make-ai-workflow/assets/CH1-1-reference-4module.sanitized.blueprint.json`、`CH1-1-test-data.csv`、`CH1-1-import-map.md`。
- **工具**：可用 Google Sheets、Google Docs 或 Markdown 編輯七欄表格；若要在 Make 查看 Bundle，使用自己的 Make 帳號與 Google／Gemini 連線。
- **權限**：若要在 Make 畫面查看，教師提供的 Scenario 只需讀取權限；Google Docs／Email 示範需要各自的連線設定。連線設定是平台代表你存取 Google 服務的授權，不是本節要學的 JSON。沒有權限時，使用本頁完整示範表，不把登入當成本節阻塞點。
- **免費界線**：本節不要求付費連接器、信用卡或購買額度；模型可用性與免費額度依課堂當日工作區為準。受限時保留固定輸入與 `CH1-1-expected-result.md`，完成欄位判讀。
- **畫面找不到時**：在 Make 模組搜尋 `Watch Rows`、`Create a Completion`、`Create a Document`、`Send an Email`；名稱不同時以 `import-map.md` 的 module ID 對照。仍找不到就回到表格路徑。本節只需讀懂模組的輸入與輸出，不要求你先建立或執行 Scenario。

本節把跟做分成四個 **Stage（階段）**：S1 先認出來源欄位，S2 追 Gemini 的中間結果，S3 接上文件與通知，S4 只替換資料來源。步驟標籤的意思是：**Demo** 教師先示範、**Together** 全班同步跟做、**Solo** 你獨立完成、**Check** 停下來核對；它們是課堂節奏，不是 Make 的功能名稱。每個 **Checkpoint（檢查點）** 都是完成一段後的停站，確認前一段真的成立，才繼續往下接。

#### Stage S1：建立地圖欄位

**步驟 1｜Together · 建立 `v1-sheets`**

- **學員操作**：建立一張表，欄位依序為「順序、模組、角色、輸入、輸出、映射備註（來源、去向與用途）、失敗影響」；先填入 1–4 與四個模組名稱，標題寫 `v1-sheets`。
- **預期結果**：表格有 4 列，順序為 Sheets、Gemini、Docs、Email。
- **快速檢查**：遮住模組名稱，只看角色欄，能說出四列分別負責取得、處理、保存與通知。
- **卡住時**：若欄位少於七欄，回到 **S1** 補齊後再填資料；不要刪除已有列。無法建立表格時，複製本頁示範表到 Markdown，完成後停在「待轉入表格」狀態。

**步驟 2｜Together · 對照來源資料**

- **學員操作**：在 Sheets 列填入輸入「試算表新增的一列」，輸出填入「位置鍵 `1`、`2`、`3`」；映射備註改寫成完整句：「Sheets 先交出一列，位置鍵 `1`、`2`、`3` 分別代表姓名、評分、回饋，所以三個值會進入 Gemini Prompt。」
- **預期結果**：任何讀者都能知道這份匯出 Bundle 不是自動帶出 `customer_name` 等命名欄位，而是先用位置鍵，再由地圖賦予語意。
- **快速檢查**：指出 `feedback` 的來源不是 Gemini，而是 Sheets 的位置鍵 `3`。
- **卡住時**：若把輸出寫成「Google Sheets」，回到 **S1** 的來源列，改成實際值或位置鍵；修正後從步驟 2 重跑，不需清除其他列。

#### Checkpoint 1：來源欄位可追蹤

現在應看到：Sheets 列已寫出一列資料、位置鍵 `1/2/3` 與三個語意欄位。若沒看到，回到步驟 2 修正；通過後才能把這些值交給 Gemini。

#### Stage S2：寫出 Gemini 的中間結果

**步驟 3｜Demo → Together · 對照 Prompt 與 `result`**

- **學員操作**：先把 `{{ }}` 讀成「把前一個模組交出的值插入這裡」：前面的 `1` 是 Sheets 的模組 ID，反引號中的 `1/2/3` 是這一列的三個位置鍵。接著在 Gemini 列填入輸入 `{{1.\`1\`}}`、`{{1.\`2\`}}`、`{{1.\`3\`}}`；輸出只填 `result`；映射備註寫成因果句：「Sheets 的位置鍵 `1`、`2`、`3` 已進入 Gemini Prompt，因此 Gemini 產生 `result`，後續 Docs 內容與 Email 內文都讀 `{{2.result}}`。」
- **預期結果**：你能用完整句讀出：「Sheets 的第 3 個資料值進入 Gemini 的回饋欄位，Gemini 產生一個 `result` 文字，後面兩個模組都讀它。」
- **快速檢查**：地圖沒有 `summary`、`reply_draft`、`needs_review` 等未出現在 4 模組 Blueprint 的欄位。
- **卡住時**：若只寫「AI 結果」，回到 **S2**，打開 `CH1-1-import-map.md` 對照 `result`；若值為空，保留原始測試列，修正映射後從 Gemini 重跑，不刪除來源資料。

**步驟 4｜Together · 寫出處理失敗影響**

- **學員操作**：在 Gemini 列的失敗影響寫「`result` 空白或格式不符 → 流程負責人回到 Prompt／欄位映射修正 → 從 Gemini 重跑；保留原始輸入」。
- **預期結果**：失敗影響包含現象、負責人、修正位置、重跑點與資料保留方式。
- **快速檢查**：另一個人看到這格，不需要猜要不要重新讀 Sheets。
- **卡住時**：若只寫「Gemini 失敗」，回到 **S2** 補完整句；修正後仍無輸出就安全停止在「待修正」，不要把空白送到 Docs。

#### Checkpoint 2：`result` 是唯一中間輸出

現在應看到：Gemini 只有 `result` 一個輸出，且兩個後續模組都從它取值。若出現其他欄位，先回到步驟 3；通過後才能填 Docs 與 Email。

#### Stage S3：補上內容交付與通知

**步驟 5｜Together · 對照 Docs 與 Email 映射**

- **學員操作**：Docs 列填入文件名稱 `客服回饋：{{1.\`0\`}}-{{1.\`1\`}}`、內容 `{{2.result}}`，輸出「文件名稱與 URL／ID」；映射備註寫「Sheets 的位置鍵 `0`（時間）與 `1`（姓名）組成文件名稱，Gemini 交出的 `result` 寫入文件內容，形成可保存的交付物」。Email 列填入輸入「主旨 `{{7.name}}`、內文 `{{2.result}}`、課堂提供收件人」，輸出「寄信狀態或 message ID」；先注意 `7` 是 Docs 的模組 ID，`name` 是文件名稱，所以它被用來組成 Email 主旨；再把映射備註寫成「Docs 保存同一份 `result` 後，Email 沿用它作為內文，讓通知與文件一致」。
- **預期結果**：地圖看得出 Docs 與 Email 使用同一個 `result`，但輸出狀態不同；文件 URL 不會自動成為 Email 內文。
- **快速檢查**：若 Docs 沒有 URL，能說明要停在 Docs，不重送 Email；若 Email 失敗，能從 Email 單獨重跑。
- **卡住時**：回到 **S3** 對照 `import-map.md`；若把 `{{7.name}}` 當成內文，改回主旨欄。修正後只重跑被修正的模組；不要清除已建立文件。

**步驟 6｜Check · 完成四模組失敗影響**

#### Checkpoint 3：`v1-sheets` 可以交接

現在應看到：四列都有輸入、輸出、映射與失敗影響；`result` 從 Gemini 流到 Docs 與 Email。若沒看到，回到缺欄位的步驟；通過後才做來源替換。

#### Stage S4：只替換資料來源

## 常見錯誤 3 條：先查欄位規則，再查工具（Common Pitfalls）

1. **把位置鍵當成命名欄位**：現象是直接在地圖寫「Sheets 輸出 `customer_name`」，原因是沒有查看匯出 Bundle；解法是用 `import-map.md` 將位置鍵 `1/2/3` 對照姓名、評分、回饋，再把對照寫入映射備註。
2. **把 `result` 拆成不存在的欄位**：現象是地圖出現 `summary`、`reply_draft` 或 `needs_review`，原因是把另一個案例的欄位規則套進 4 模組 Blueprint；解法是回到 Stage S2，確認 Gemini 輸出只有 `result`，後續 Docs 與 Email 都讀同一欄。
3. **下游失敗卻整條重跑**：現象是 Email 寄信失敗後又建立一份重複文件，原因是沒有記錄模組的失敗影響；解法是依 Stage S3 只修正 Email 並從 Email 重跑，保留已成功建立的 Docs，無法確認收件狀態時停止並人工確認。

## 檢核題 2 條（Quiz）

**Q1（概念驗證）**：在這份 4 模組 Blueprint 中，哪一項最能說明資料映射？

- [ ] A. 把 Google Sheets 改成 Gmail。
- [x] B. 將 Sheets Bundle 的位置鍵 `3` 放入 Gemini Prompt 的回饋欄位，並將 `{{2.result}}` 放到 Docs 內容。
- [ ] C. 把 Email 模組移到流程最前面。
- [ ] D. 把連線 placeholder 改成自己的帳號名稱。

**解答**：B。映射描述的是一個模組交出的值如何成為下一個模組的輸入；更換工具或連線不等於映射。

**Q2（應用驗證）**：Google Sheets 的來源要換成 Gmail，哪些部分要重新檢查？

- [ ] A. 只改第一個模組名稱，後面全部照抄。
- [ ] B. 把 Gmail 的 `subject` 直接當成 Gemini 的 `result`。
- [x] C. 重新確認 `sender`、`subject`、`body` 如何進入 Gemini；保留 Gemini 的 `result`，並確認 Docs 與 Email 仍讀 `{{2.result}}`。
- [ ] D. 因為來源不同，所以移除 Docs 與 Email。

**解答**：C。來源替換會改變輸入契約，但不代表下游輸出名稱跟著改變；要重新檢查的是欄位去向與保留的模組。
