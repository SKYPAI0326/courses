## 教學流程（Teaching Flow）

### 破題 / Hook

CH1-4 教你讓 LLM 先產出設計規格；本節處理更容易出事的情境：已有一份 Make JSON，但只想修一個欄位映射或一條 Filter 條件。直接把完整藍圖貼給 LLM，可能洩漏連線設定，也可能讓它順手重寫不相關模組。

阿凱要讓 scenario-v1 的 Filter 讀取 Gemini 輸出的 `needs_review`，並修正 Filter 將文字「false」誤當布林值的問題。他不要求 LLM 重建整份流程，而是提供去敏 JSON、變更目標與不變條件，要求輸出最小 diff、理由、測試與還原步驟。若沒有 Make 工作區，則只用同一份去敏 JSON 審查差異與預期路由，不把模擬結果寫成平台執行證據。

**本節完成物**：

1. blueprint-safe-v1.json：移除 credential、token、固定帳號、資料夾 ID 與個資的安全藍圖。
2. change-request-v1：一份只改一個主要變因的修改需求與驗收條件。
3. diff-log-v1：原始／修改後欄位差異、採用理由、測試結果與還原指令或步驟；若離線完成，另標示 `SIMULATED` 與尚待平台驗證項目。

**起始狀態**：你有教師提供的去敏 JSON 與 CH1-2 契約；任何真實連線資訊都不進 LLM。Make 路徑可匯入並執行自己的安全副本；離線路徑使用 JSON、固定 diff 與測試表完成靜態審查，學習目標的「修改範圍與安全判斷」成立，但不包含真實 Docs URL、Filter 執行紀錄或平台錯誤訊息。

### 概念 / Concepts

#### 最小修改是什麼

最小修改表示只改變達成需求所需的欄位、條件或模組參數，保留其他節點、順序與連線。它不是「改得越少越好」的美學，而是讓測試與還原範圍可控。

| 修改類型 | 允許範圍 | 不應順手改動 |
|---|---|---|
| Filter 欄位映射 | `feedback_text` → `needs_review` | 來源模組、Docs 版型 |
| 條件型別 | 「false」→ false | Gemini prompt 全文、通知模組 |
| 輸出欄位 | 保留 needs_review | 重新命名所有輸出 |

**正例**：只修改 Filter 的比較值與型別，並提供 false、true 與文字型別錯誤三個測試。  
**錯例**：LLM 回傳一份完全重排的 JSON，雖然看似乾淨，卻無法知道哪些變更造成新的失敗。  
**你要判斷**：如果需求只說「修正欄位映射」，LLM 卻新增 Email 模組，應退回並要求最小 diff。

#### 安全 JSON 的邊界

安全 JSON 不是把所有資料刪到不能用，而是保留教學所需的結構與欄位，移除可以登入、識別個人或定位雲端資源的值。

| 要保留 | 要移除或替換 |
|---|---|
| 模組類型、順序、欄位名稱、條件、範例輸出 | OAuth token、API key、credential ID、資料夾 ID、真實 Email、個資 |

### 操作示範 / Demo：用 LLM 提出一個可還原的最小 diff

#### 去敏前後的片段

原始教學片段只保留結構，敏感值先替換：

    { "module": "Gemini / Generate",
      "input": { "message_text": "{{sample_text}}" },
      "output": { "summary": "{{summary}}", "reply_draft": "{{draft}}", "needs_review": "{{flag}}" },
      "connection": "{{removed_credential}}" }

connection 的值在送給 LLM 前改成 placeholder；sample_text 不使用真實姓名、信箱或訂單編號。

#### 變更需求

    只修改 Filter 的條件型別與 Gemini → Filter 的欄位映射。
    目標：needs_review 必須是布林值；false 才能通往 Google Docs，true 必須停在待人工確認。
    不變條件：不新增模組、不改來源、不改 Docs 欄位、不改提示詞文字。
    請輸出：修改前後差異、每個差異的理由、三個測試案例、還原方式。

#### LLM 回傳的最小差異

| 路徑 | 修改前 | 修改後 | 理由 | 驗證 |
|---|---|---|---|---|
| Filter.condition.value | 「false」 | false | 讓條件使用布林值 | 用 false 通過、true 停止 |
| Filter.input | feedback_text | needs_review | 控制欄位應來自 Gemini 輸出 | 檢查映射與輸出契約 |

LLM 另外列出「未修改」清單：來源模組、Gemini prompt、Docs、連線設定 placeholder 均維持不變。這份清單讓人能快速發現 LLM 是否偷改了範圍。

#### 測試與還原結果

| 測試 | 輸入 | 預期 | Make 實際判斷／離線模擬判斷 |
|---|---|---|---|
| A：可繼續 | needs_review=false | 進 Docs | 通過，取得文件 URL |
| B：需人工 | needs_review=true | 停在人工出口 | 通過，未建立 Docs |
| C：型別錯誤 | needs_review="false" | 標記型別錯誤、不通過、不下游 | 標記型別錯誤，未採用且未執行下游 |

Make 路徑：A、B 通過，且 C 沒有被誤放行，才可接受 diff；紀錄執行 ID、Docs URL 或停止訊息。離線路徑：逐列比對固定輸出與預期路由，將欄位路徑、型別與安全邊界標為 `SIMULATED`，並把真實 URL／執行 ID 列入尚待平台驗證。任一路徑測試不符合預期，都要保留 blueprint-safe-v1.json，還原到修改前版本，不能在未記錄的狀態繼續疊改。

### 動手 / Hands-on：安全地要求 LLM 修改 JSON

#### 完成物與最短路徑

- **完成物**：blueprint-safe-v1.json、change-request-v1、diff-log-v1。
- **起始狀態**：已開啟本節的去敏藍圖、去敏檢查表、變更需求單、固定測試案例與差異紀錄模板；CH1-2 契約與 CH1-3 scenario-v1 作為前置參考，所有敏感值已替換成 placeholder。
- **最短可跑路徑**：先完成去敏檢查，再請 LLM 只改一個條件，最後以三個測試案例驗證。

#### 步驟 1：複製並去敏藍圖

- **模式**：Together
- **學員操作**：先開啟[去敏藍圖 fixture](../../courses/make-ai-workflow/assets/CH1-5-sanitized-blueprint.fixture.json)與[去敏檢查表](../../courses/make-ai-workflow/assets/CH1-5-sanitization-checklist.md)，再將教師 JSON 複製為 blueprint-safe-v1.json；搜尋 token、secret、password、credential、真實 Email、資料夾 ID 與個資，以 placeholder 替換並保留模組結構。
- **講師提示**：去敏不是刪掉欄位名；要讓 LLM 看懂結構，但無法登入或識別真人。
- **預期結果**：JSON 可解析，保留模組、輸入、輸出、條件與連線 placeholder。
- **快速檢查**：檔案中沒有真實 token、credential 值、固定帳號或個資。
- **卡住時**：依去敏檢查表逐項搜尋；不確定的值先替換成 `{{needs_human_check}}`，不要猜安全與否。

#### 步驟 2：寫變更需求與不變條件

- **模式**：Together
- **學員操作**：複製[變更需求單](../../courses/make-ai-workflow/assets/CH1-5-change-request-template.md)為 change-request-v1，寫明唯一主要變因「修正 needs_review 型別與 Filter 映射」，並列出不改來源、提示詞、Docs 與模組數量。
- **講師提示**：不變條件是 diff 的邊界，也是後續審核依據。
- **預期結果**：需求能被另一個人判斷是否超出範圍。
- **快速檢查**：同學能用一句話說出允許與禁止的修改。
- **卡住時**：回到示範的兩個修改路徑；不要把「順便優化」寫進需求。

#### 步驟 3：要求 LLM 只輸出 diff

- **模式**：Demo → Together
- **學員操作**：複製[完整 LLM 最小 diff Prompt](../../courses/make-ai-workflow/assets/CH1-5-prompt-template.md)，將去敏 JSON 貼入指定位置，再依 change-request-v1 要求輸出修改前／後、理由、未修改清單、測試、還原。沒有 LLM 帳號時，改讀[固定 diff 範例](../../courses/make-ai-workflow/assets/CH1-5-llm-fixed-diff.md)，完成同樣的審查表。
- **講師提示**：完整 JSON 可以作為參考，但第一個交付物應是可讀 diff，不是整份重寫。
- **預期結果**：LLM 回答包含明確路徑與三個測試案例：false、true 與文字型別錯誤。
- **快速檢查**：每個 diff 都能指出路徑、舊值、新值與理由。
- **卡住時**：補上「不得新增模組、不得改動未列路徑、資料不足寫需人工確認」。

#### Checkpoint：修改範圍是否受控

- **現在應該看到**：只有 Filter 型別與輸入映射變更；來源、Gemini prompt、Docs 與連線 placeholder 被列在未修改清單。
- **若沒看到**：退回 LLM 回答，要求「只輸出變更表」，不要直接複製整份新 JSON。
- **通過後才能繼續**：你能逐項說明每個變更如何對應 contract-output-v1。

#### 步驟 4：人工審查 diff

- **模式**：Together
- **學員操作**：依[差異與決策紀錄](../../courses/make-ai-workflow/assets/CH1-5-diff-log-template.md)將每個差異標記「接受／退回／需確認」；檢查 needs_review 的來源、型別、Filter 去向與未修改清單。
- **講師提示**：LLM 提供建議，人負責決定是否符合事實與範圍。
- **預期結果**：diff-log-v1 有每個修改的採用狀態與理由。
- **快速檢查**：指出一個不能只靠文字判斷、需要實際執行的項目。
- **卡住時**：回看 CH1-3 的成功／停止測試；不能由靜態 diff 證明的內容標記需測試。

#### 步驟 5：先跑成功案例

- **模式**：Together
- **Make 路徑**：依[固定測試案例](../../courses/make-ai-workflow/assets/CH1-5-test-cases.md)用 `needs_review=false` 的輸入執行修改後流程，記錄執行 ID、Docs URL、執行狀態與實際輸出。
- **離線路徑**：依同一份測試案例逐欄比對固定 diff 與預期輸出，在 `diff-log-v1` 記錄 `SIMULATED`、預期文件內容與 `{{simulated_document_url}}`；不得填寫或推測真實 URL。
- **講師提示**：成功案例只證明通過路徑，還不能證明安全分流。
- **預期結果**：Make 路徑建立 Docs，內容符合 `summary` 與 `reply_draft` 契約；離線路徑只完成欄位與路由的模擬判斷。
- **快速檢查**：Make 的文件內容、URL 與執行 ID 都存在；離線檢查固定輸出與契約一致，並保留 `SIMULATED` 標記。
- **卡住時**：比較修改前後 diff；Make 再查 Filter 輸入與型別及 Docs，離線則列出尚待平台驗證，不把缺少連線當成測試失敗。

#### 步驟 6：再跑停止案例

- **模式**：Together
- **Make 路徑**：沿用固定測試案例，用 `needs_review=true` 執行，確認資料停在人工出口；再用 `needs_review="false"` 測試型別錯誤，記錄停止位置、執行 ID 與結果。
- **離線路徑**：用固定測試案例比對 `true → manual_review`、`"false" → type_error` 的預期路由，記錄停止位置與原因並標示 `SIMULATED`；不宣稱平台真的攔截。
- **講師提示**：安全測試要包含「看似相同但型別不符」的案例。
- **預期結果**：Make 路徑的 true 不建立 Docs、文字型別不被自動轉換；離線路徑記錄相同預期但標示 `SIMULATED`。
- **快速檢查**：Make log 有停止位置、執行 ID、原因、負責人與重試方式；離線 log 有預期停止位置、原因與尚待平台驗證欄。
- **卡住時**：先停用後續通知，回到輸出契約檢查布林值；離線不要把固定輸出改寫成實際錯誤訊息。

#### Checkpoint：測試是否證明最小修改

- **Make 路徑現在應該看到**：false 成功、true 停止、文字型別錯誤被攔截，且每案有執行 ID、Docs URL 或停止訊息；所有結果都能回到 `diff-log-v1`。
- **離線路徑現在應該看到**：三案的預期路由與固定輸出逐列相符，所有紀錄標示 `SIMULATED`，並列出真實執行尚待驗證。
- **若沒看到**：任一路徑都先還原 JSON，逐一檢查；不要在多個修改同時存在時猜原因。
- **通過後才能繼續**：Make 依實際執行結果決定接受或退回 diff；離線依模擬審查結果決定是否送交後續平台驗證。

#### 步驟 7：接受、退回或還原

- **模式**：Solo
- **Make 路徑**：在差異與決策紀錄中填寫實際結果；若三個測試符合預期，將狀態標為接受；若任一失敗，標為退回並使用 blueprint-safe-v1.json 還原，再記錄下一個修正需求。
- **離線路徑**：在差異與決策紀錄中填寫模擬結果；若三個預期路由與靜態檢查符合，標為「離線審查通過／待 Make 驗證」，不可直接標為平台接受；若任一不符，標為退回並還原。
- **講師提示**：還原不是失敗，而是控制變更範圍的正式步驟。
- **預期結果**：diff-log-v1 有明確決策與版本位置，沒有未標記的半成品。
- **快速檢查**：另一個人能知道目前採用哪個版本、如何回到上一版。
- **卡住時**：保留原始安全檔；若找不到還原來源，停止，不要覆寫現有 JSON。

#### 步驟 8：保存交接紀錄

- **模式**：Check
- **學員操作**：在 diff log 最下方寫變更目的、影響模組、測試結果、還原步驟與下一位負責人；移除所有秘密值後才分享。
- **講師提示**：交接文件要描述決策與證據，不只附上 LLM 回答。
- **預期結果**：下一位設計者可在不接觸 credential 的情況下理解與重做修改。
- **快速檢查**：只看 diff log 能說出改了什麼、為何改、如何驗證與如何還原。
- **卡住時**：依序補「變更／理由／測試／狀態／還原」五欄。

### 變化練習 / Solo Transfer

只把變更改成「Docs 標題加入測試日期」，要求 LLM 不修改來源、Gemini 輸出、Filter 與通知；產出另一份 diff，並說明哪些測試仍需重跑、哪些可沿用。

### 檢核 / Verification

- [ ] blueprint-safe-v1.json 可解析，沒有 credential、token、固定帳號、資料夾 ID 與個資。
- [ ] change-request-v1 只改一個主要變因，並列出不變條件。
- [ ] LLM diff 有路徑、舊值、新值、理由、未修改清單、測試與還原。
- [ ] Make 路徑測試涵蓋 false 成功、true 停止、文字型別錯誤三條路徑，並留下執行 ID、Docs URL 或停止訊息；離線路徑以同三案完成靜態比對，所有結果標示 `SIMULATED`。
- [ ] diff-log-v1 能指出接受／退回／需確認的決策與負責人。
- [ ] 任一測試失敗時，能回到安全 JSON，而不是覆寫未驗證版本；離線路徑另列出尚待 Make 驗證的執行證據。

### 商業情境案例 / Case

雯姊要求阿凱只修正一個欄位映射，不接受「順便重整流程」。阿凱以去敏 JSON、差異表與測試紀錄回報，讓雯姊能在沒有連線權限的情況下審查變更。這是職場上比「AI 幫我改好了」更可交接的做法。

### 常見錯誤 / Pitfalls

1. **把完整藍圖原封不動貼給 LLM**：可能洩漏秘密。修正是先做去敏副本並搜尋敏感關鍵字。
2. **接受整份重寫 JSON**：無法知道改動範圍。修正是要求最小 diff、未修改清單與版本還原。
3. **只測試成功案例**：看不到 Filter 失效。修正是固定測試 false、true 與型別錯誤。

### 檢核題 / Quiz

#### Q1

哪一項最能證明「最小修改」？

A. LLM 產生一份更長的完整 JSON。  
B. 只有指定路徑變更，其他模組列在未修改清單，且測試能重現結果。  
C. 重新建立所有連線。  
D. 刪除原始版本。

**答案：B。**最小修改需要範圍、理由與可驗證差異。

#### Q2

修改後 needs_review=「false」仍通過 Filter，最適合的處理是什麼？

A. 接受，因為結果看起來正確。  
B. 標記型別錯誤，暫停下游並退回或修正輸出契約。  
C. 將所有值轉成字串。  
D. 刪除 Filter。

**答案：B。**契約要求布林值，不能以看似相同的文字取代。
