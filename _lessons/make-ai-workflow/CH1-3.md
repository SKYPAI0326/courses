## 教學流程（Teaching Flow）

### 破題 / Hook

CH1-1 先用 Sheets → Gemini → Docs → Email 的四模組基準教你讀懂資料如何流動，CH1-2 再把來源欄位整理成可替換的輸入／輸出契約。本節不回頭修改 CH1-1 的原始藍圖，而是建立新的練習版本 `scenario-v1`：在 Gemini 與 Docs 之間加入 Filter，先驗證結構化輸出與安全停止，再決定是否加入通知。這是「從讀圖基準升級成可測試最短流程」，不是把 Filter 假裝成 CH1-1 原本就有的模組。

如果你有 Make 工作區，會實際建立與執行這條最短流程；如果沒有連線，則使用本節的模組卡與固定輸出完成離線模擬。兩條路徑的產物名稱與驗收證據不同，不能把模擬結果寫成真實執行結果。

阿凱在弄一下行銷工作室收到一筆客戶回饋。今天的任務是用 Google Sheets 作為示範來源，讓 Gemini 依照 `contract-input-v1` 產生固定格式的摘要、回覆草稿與 `needs_review`，再用 Filter 決定是否建立 Google Docs。Sheets 是本節的基準入口；下一個來源替換練習只使用 Gmail，同一份契約仍可沿用。

**本節完成物**：

1. Make 路徑：`scenario-v1`、實際 `run-log-v1` 與 `test-cases-v1`，包含執行時間、Filter 結果與真實 Docs URL／停止狀態。
2. 離線路徑：`scenario-v1-offline-map`、`run-log-v1-simulated` 與 `test-cases-v1`，包含模組映射、固定輸出、預期路由與 `SIMULATED` 標記；不產生真實 Scenario 或 URL。

**起始狀態**：你已有 CH1-2 的三份契約文件與去敏測試資料；教師可提供 Make 藍圖或讓你從空白 Scenario 開始。請先決定走 Make 或離線路徑；沒有可用連線時，不建立虛構的 Docs URL，改用[離線模擬執行包](../../courses/make-ai-workflow/assets/CH1-3-offline-run-fixture.md)完成映射、固定輸出與模擬測試判斷。

**本節可直接取得的材料**：第一次操作前，請先開啟 [四張模組卡](../../courses/make-ai-workflow/assets/CH1-3-module-cards.md)、[兩筆測試資料](../../courses/make-ai-workflow/assets/CH1-3-test-data.csv)、[Gemini 固定輸出](../../courses/make-ai-workflow/assets/CH1-3-gemini-output-fixtures.json)、[執行紀錄模板](../../courses/make-ai-workflow/assets/CH1-3-run-log-template.md)、[測試案例模板](../../courses/make-ai-workflow/assets/CH1-3-test-cases-template.md)與[離線模擬執行包](../../courses/make-ai-workflow/assets/CH1-3-offline-run-fixture.md)。有 Make 連線時，模組卡用來逐項設定；沒有連線時，離線包提供每一步的固定輸入、輸出與預期路由。

### 概念 / Concepts

#### 最短可跑路徑與完整流程的差別

最短可跑路徑只保留能驗證核心學習的模組：來源、處理、控制、第一個後續動作。它讓你先確認資料有進 Gemini、輸出符合契約、Filter 會分流，再加入通知或其他延伸。直接一次接完所有模組，任何錯誤都會同時出現在多個位置，初學者很難定位。

本節的示範流程如下：

```text
Google Sheets / Watch Rows
  → Gemini / Generate
  → Filter：needs_review = false
  → Google Docs / Create a Document
```

當 `needs_review=true` 時，資料不進 Docs，而是停在「待人工確認」的未實作出口。這個出口仍要寫進執行紀錄，否則測試只涵蓋成功路徑。

#### 模組設定的四個可觀察結果

| 設定面向 | 要回答的問題 | 本節證據 |
|---|---|---|
| 輸入映射 | 這個模組拿到哪個契約欄位？ | Sheets 的 `feedback` → `message_text` |
| 處理設定 | 模組如何產生下一個結果？ | Gemini 依固定輸出格式生成三欄 |
| 控制條件 | 什麼資料可以繼續？ | `needs_review = false` 才進 Docs |
| 執行證據 | 如何知道真的成功或失敗？ | Run log 記錄 bundle、輸出、狀態與出口 |

**正例**：先用一筆已知的 Sheets 資料執行，確認 Gemini 回傳 `summary`、`reply_draft`、`needs_review`，再建立 Docs。  
**錯例**：直接把整封資料塞進 Docs，看到文件出現就認為流程成功，卻沒有檢查 AI 輸出欄位與 Filter 分流。  
**你要判斷**：如果 Docs 有建立但內容是空白，先回到 Gemini 的輸出契約與 Docs 映射，不先重建來源模組。

### 操作示範 / Demo：從契約到第一筆成功執行

#### 原始任務與測試資料

> 當試算表新增一筆客戶回饋，先讓 Gemini 產生摘要、回覆草稿與審核旗標；只有不需要人工確認時，才建立 Google Docs。需要確認的資料留下執行紀錄，等待後續處理。

測試資料：`customer_name=林小姐`、`rating=2`、`feedback=物流延遲，客服回覆太慢`。依 CH1-2 的契約，這筆資料先被正規化成 `customer_identity=林小姐`、`message_text=物流延遲，客服回覆太慢`、`urgency_signal=2`、`owner_email=ops@example.com`。

#### 完整模組設定表

| 順序 | 模組 | 角色 | 主要設定 | 輸入 | 預期輸出 | 驗證與失敗出口 |
|---:|---|---|---|---|---|---|
| 1 | Google Sheets / Watch Rows | 資料來源 | 讀取新增列 | `customer_name`、`rating`、`feedback` | 一筆來源資料 | 沒有新列：資料來源負責人檢查觸發條件，記錄後重試 |
| 2 | Gemini / Generate | 處理 | 使用 `contract-output-v1` 格式 | `customer_identity`、`message_text`、`urgency_signal` | `summary`、`reply_draft`、`needs_review` | 欄位空白或型別錯誤：流程負責人記錄，修正輸入後重試 |
| 3 | Filter | 控制 | `needs_review = false` | `needs_review` | 通過或待人工確認 | `true` 停在人工出口，不建立 Docs |
| 4 | Google Docs / Create a Document | 後續動作 | 標題與內容使用 Gemini 輸出 | `summary`、`reply_draft` | 文件 URL | URL 缺失：檢查權限與映射，暫停後續通知 |

#### Gemini 的實際輸入與輸出

Gemini 不直接接收未整理的三個 Sheets 欄位，而是接收契約欄位與明確輸出要求：

```text
請根據以下資料產生 JSON，不要加入其他欄位：
customer_identity：林小姐
message_text：物流延遲，客服回覆太慢
urgency_signal：2

輸出欄位：summary（文字）、reply_draft（文字）、needs_review（布林值）
```

示範回傳：

| summary | reply_draft | needs_review |
|---|---|---|
| 物流延遲且客服回覆時間過長 | 感謝你的回饋，我們會檢查物流通知流程並改善客服回覆時間。 | `true` |

因為 `needs_review=true`，Filter 不通過，資料停在待人工確認出口；這次不應建立 Docs。再用一筆一般回饋測試 `needs_review=false`，才能看到 Docs 的成功結果。

#### 執行結果與判斷

| 測試 | Filter 結果 | Docs | 狀態 | 理由 |
|---|---|---|---|---|
| A：需要確認 | `true`，不通過 | 不建立 | 待人工確認 | 避免未核准內容進入後續動作 |
| B：一般回饋 | `false`，通過 | 建立文件 URL | 已完成 | 輸出符合契約且通過控制條件 |

在 Make 路徑中，這兩筆結果共同構成「可執行」的證據；只看到 B 的文件 URL，不能證明 A 的安全出口存在。離線路徑則把同樣的兩條路由記為 `SIMULATED`，只能證明你理解映射與判斷規則，不能替代平台執行證據。

### 動手 / Hands-on：建立並測試最小流程

#### 完成物與最短路徑

- **完成物**：Make 路徑為 `scenario-v1`、實際 `run-log-v1`、`test-cases-v1`；離線路徑為 `scenario-v1-offline-map`、`run-log-v1-simulated`、`test-cases-v1`。
- **起始狀態**：先開啟上方六份本節材料，再依需求選擇 Make 空白 Scenario 或離線模組卡；已準備 CH1-2 的契約與兩筆測試資料；不需要付費連接器。
- **模板**：使用 [執行紀錄模板](../../courses/make-ai-workflow/assets/CH1-3-run-log-template.md) 與 [測試案例模板](../../courses/make-ai-workflow/assets/CH1-3-test-cases-template.md)；若無法下載，可依頁面欄位建立同樣表格。
- **最短可跑路徑**：Make 路徑先完成 Sheets → Gemini → Filter → Docs 的一筆 `false` 成功路徑，再補 `true` 與輸出錯誤測試；離線路徑依模擬執行包逐步填寫預期輸出與 `SIMULATED` 證據。

#### 步驟 1：建立最小流程

- **模式**：Together
- **Make 路徑**：建立 Scenario `scenario-v1`，依序放入 Google Sheets / Watch Rows、Gemini / Generate、Filter、Google Docs / Create a Document；先不要加入 Email 或其他通知。
- **離線路徑**：不建立 Scenario。複製四張模組卡，建立 `scenario-v1-offline-map`，依同樣順序寫出每個模組的輸入、輸出、條件與停止出口。
- **講師提示**：模組順序是資料流的最短路徑，不是完整產品版；先讓每個中間結果可觀察。
- **預期結果**：Make 路徑畫面上有四個模組；離線路徑的地圖上有四個模組與相同順序。
- **快速檢查**：從左到右能說出每個模組的角色與下一個模組需要什麼；離線學員不應把地圖命名成可執行 Scenario。
- **卡住時**：若找不到模組，改用教師提供的模組卡記錄設定，不把登入問題當成本節阻塞。

#### 步驟 2：映射來源欄位

- **模式**：Together
- **Make 路徑**：在 Sheets 模組指定測試試算表與工作表；確認輸出欄位對應 `customer_identity`、`message_text`、`urgency_signal` 的來源值。
- **離線路徑**：開啟離線模擬執行包，將同一筆固定輸入抄入 `scenario-v1-offline-map`，逐欄註明來源欄位到契約欄位的映射，不填寫試算表連線或執行 ID。
- **講師提示**：Watch Rows 的輸出仍是來源欄位，正規化欄位要在交給 Gemini 前說明映射。
- **預期結果**：Make 路徑的測試 bundle 能看見林小姐、回饋文字與 rating=2；離線路徑的輸入表有相同三個值與映射說明。
- **快速檢查**：遮住試算表名稱，只看欄位值仍能判斷這是一筆客戶回饋；離線紀錄不可寫成 Make bundle。
- **卡住時**：回看 CH1-2 的 `mapping-v1`；不要把 `owner_email` 從客戶列猜出來，使用課程提供的固定設定。

#### 步驟 3：設定 Gemini 輸入與輸出

- **模式**：Demo → Together
- **Make 路徑**：將 `customer_name`／`feedback`／`rating` 映射到契約欄位，貼上示範的輸出要求，指定只回傳 `summary`、`reply_draft`、`needs_review` 三欄。
- **離線路徑**：使用離線模擬執行包中的固定 Gemini 輸出，將三個輸出欄位與型別寫入地圖；不宣稱已呼叫 Gemini。
- **講師提示**：輸出格式是下游的契約，不是美化文字；先驗證欄位與型別，再談提示詞風格。
- **預期結果**：Make 路徑的 Gemini 測試輸出含兩個文字欄位與一個布林欄位；離線路徑的固定輸出表含相同欄位，並標記 `SIMULATED`。
- **快速檢查**：逐欄圈出 `summary`、`reply_draft`、`needs_review`，並寫下各自的下游用途。
- **卡住時**：若輸出混入說明文字，先把「只回傳 JSON 欄位」寫進提示詞，並在記錄中標為輸出格式錯誤。

#### Checkpoint：Gemini 輸出是否符合契約

- **Make 路徑現在應該看到**：輸入欄位可追溯到 CH1-2，輸出有三欄且型別正確；尚未執行 Docs。
- **離線路徑現在應該看到**：固定輸入、固定輸出與欄位映射均已寫入離線地圖，旁邊有 `SIMULATED` 標記；尚未填寫文件 URL。
- **若沒看到**：回到步驟 2 或 3，先修正映射或輸出格式，不要繼續設定 Filter。
- **通過後才能繼續**：兩條路徑都能指出哪一欄控制分流、哪兩欄會進入文件；Make 才能繼續設定平台 Filter。

#### 步驟 4：設定 Filter 分流

- **模式**：Together
- **Make 路徑**：在 Filter 建立條件 `needs_review = false`，通過路徑連到 Docs；在執行紀錄說明 `true` 會進待人工確認出口。
- **離線路徑**：在離線地圖標出 `false → Docs`、`true → 待人工確認` 兩條路徑，使用固定輸出逐條填寫預期結果；不宣稱畫面真的攔截了 bundle。
- **講師提示**：Filter 不修改資料，只決定是否繼續；不要把它當成內容審核器。
- **預期結果**：Make 路徑的 `false` 可通過、`true` 不會建立 Docs；離線路徑的兩條預期路由均標示 `SIMULATED`。
- **快速檢查**：先用示範中的 `true` 執行，確認 Docs 沒有新文件。
- **卡住時**：檢查布林值是否被當成文字；若型別不明，回到 Gemini 輸出契約。

#### 步驟 5：映射 Google Docs

- **模式**：Together
- **Make 路徑**：將 `summary` 與 `reply_draft` 放入文件標題／內容欄位，設定文件名稱包含測試識別，例如 `feedback-test-A`；保存實際文件 URL。
- **離線路徑**：在離線執行紀錄填入 `{{simulated_document_url}}`，並把預期文件標題與內容抄入模擬欄位；不得產生或填寫看似真實的 URL。
- **講師提示**：Make 路徑的文件建立成功證據是 URL 與內容，不是模組亮起綠色；離線路徑只能填寫 `{{simulated_document_url}}` placeholder。
- **預期結果**：Make 路徑的 `needs_review=false` 測試建立一份含摘要與草稿的文件；離線路徑只有預期文件內容與 placeholder。
- **快速檢查**：Make 打開文件確認內容與 Gemini 回傳一致；離線改以逐欄比對固定輸出，不把 placeholder 當成 URL。
- **卡住時**：Make 先查 Docs 權限與欄位映射；離線回看固定輸出與地圖欄位，不把缺少連線寫成流程錯誤。

#### Checkpoint：成功路徑是否可重現

- **Make 路徑現在應該看到**：一筆 `false` 測試有真實 Docs URL，一筆 `true` 測試沒有建立文件；兩筆都有實際執行紀錄。
- **離線路徑現在應該看到**：兩筆路由均有固定輸入、預期輸出與 `SIMULATED` 紀錄；沒有真實 URL 或執行 ID。
- **若沒看到**：Make 回到 Filter 確認條件與測試值；離線回到模擬包的對應案例，不補造平台證據。
- **通過後才能繼續**：接手者只看對應模式的 log，就能說出成功、待人工確認與錯誤各自的出口。

#### 步驟 6：記錄一筆成功執行

- **模式**：Together
- **Make 路徑**：在 `run-log-v1` 記錄測試資料、執行時間、Gemini 三欄輸出、Filter 結果、Docs URL 與狀態 `已完成`。
- **離線路徑**：在 `run-log-v1-simulated` 記錄固定輸入、固定輸出、預期 Filter 結果、`{{simulated_document_url}}` 與狀態 `SIMULATED／未在 Make 驗證`。
- **講師提示**：執行紀錄是交接與除錯證據，不是流水帳；至少保留能重現判斷的欄位。
- **預期結果**：Make 的成功案例可由另一位同事依實際 log 重現；離線案例可依模擬包重建預期判斷，但不宣稱重跑平台。
- **快速檢查**：Make 遮住畫面只看 log 能重述資料走過哪些模組；離線只檢查欄位與路由是否完整。
- **卡住時**：依 `test-cases-v1` 的欄位順序補寫：輸入、輸出、條件、結果、證據。

#### 步驟 7：故意製造一個失敗

- **模式**：Solo
- **Make 路徑**：複製測試資料成 B，將 `message_text` 清空或把 `needs_review` 改成文字；只改一個主要變因，執行後記錄停止模組、錯誤原因、負責人與重試方式。
- **離線路徑**：依模擬包的型別錯誤案例，只改一個主要變因，將預期停止位置、原因、負責人與重試方式寫入 `run-log-v1-simulated`，並標示 `SIMULATED`。
- **講師提示**：失敗測試不是把流程弄壞，而是確認安全出口真的存在。
- **預期結果**：Make 流程在來源、Gemini 或 Filter 的對應位置停止，不建立空白 Docs；離線紀錄呈現相同預期出口，但不宣稱實際停止。
- **快速檢查**：log 中能指出哪個契約條件不合格，以及下游為何暫停。
- **卡住時**：回看 CH1-2 的失敗處理表；不要把所有錯誤都寫成「重跑全部」。

#### 步驟 8：提交最小流程與測試包

- **模式**：Check
- **Make 路徑**：保存 `scenario-v1` 藍圖、實際 `run-log-v1`、`test-cases-v1`；在交接說明中寫出若來源改成 Gmail，哪些模組保持不變、哪些欄位需重新映射。
- **離線路徑**：保存 `scenario-v1-offline-map`、`run-log-v1-simulated`、`test-cases-v1`，在交接說明中寫出同樣的來源替換判斷，並標示尚未在 Make 驗證。
- **講師提示**：本節交付的是可測試的最小流程，不是完成所有通知與權限設定。
- **預期結果**：Make 的三份文件與藍圖可交給 CH1-4 使用；離線的地圖、模擬 log 與測試包可供 CH1-4 審查規格，但不能當成已執行藍圖。
- **快速檢查**：接手者依對應模式的測試包，能重建一筆成功與一筆失敗的判斷；離線包明確標示需要後續平台驗證。
- **卡住時**：逐項檢查完成物、輸入契約、輸出契約、兩條 Filter 路徑與對應模式的證據；離線不要補寫實際 URL。

### 變化練習 / Solo Transfer

複製 `scenario-v1` 成 `scenario-gmail-variant`，只替換來源為 Gmail / Watch Emails；保留 Gemini、Filter、Docs 的契約與控制條件。映射 `sender → customer_identity`、`subject + body → message_text`，並在測試包中標記 Gmail 沒有 `urgency_signal`。

**預期成果**：你能指出來源替換只影響輸入映射；如果主旨與內文都空白，Make 流程停在來源檢查，離線地圖則記錄同一個預期出口並標示 `SIMULATED`。

### 檢核 / Verification

- [ ] Make 路徑的 `scenario-v1` 有 Sheets、Gemini、Filter、Docs 四個核心模組，順序與契約一致；離線路徑使用 `scenario-v1-offline-map`，不可命名成可執行 Scenario。
- [ ] Make 路徑至少一筆 `needs_review=false` 建立真實 Docs，一筆 `true` 停在待人工確認，不建立文件；離線路徑對應兩筆都標示 `SIMULATED`，不可填寫虛構 URL。

- [ ] Make 路徑的 `run-log-v1` 記錄輸入、輸出、Filter 結果、文件 URL／停止狀態、負責人與重試出口；離線路徑的 `run-log-v1-simulated` 記錄預期輸出、placeholder、停止位置並標示模擬模式。

### 商業情境案例 / Case

弄一下行銷工作室的阿凱要把客戶回饋整理給雯姊。雯姊不要求他把所有通知都自動寄出，而是先要一條能證明「資料有被正確整理、需要審核時不會誤送」的最小流程。這也是本節為什麼先做到 Docs，不把 Email 當成主軸。

### 常見錯誤 / Pitfalls

1. **一次接太多模組**：看到流程很短就加入 Email、額外控制模組與格式化。原因是把展示完整誤當成可驗證；修正是回到 Sheets → Gemini → Filter → Docs 的最短路徑。
2. **只看綠色成功狀態**：Docs 有建立就認為流程成功。原因是沒有查看 bundle 與契約；修正是同時檢查三個 Gemini 輸出、Filter 值與文件內容。
3. **失敗時全部重跑**：空值或型別錯誤直接重跑整條流程。原因是沒有記錄停止模組；修正是先定位契約缺口，再由指定負責人重試單一模組。

### 檢核題 / Quiz

#### Q1

為什麼本節先建立 Docs，而不是直接把結果寄出？

A. Docs 一定比 Email 免費。  
B. 文件能留下可觀察的輸出與 URL，先驗證內容與映射，再決定是否加入通知。  
C. Email 不能接 Make。  
D. Filter 只能接 Docs。

**答案：B。**本節先證明資料、輸出與控制條件可被檢查；通知是後續可替換的動作。

#### Q2

`needs_review=true` 的執行紀錄至少要包含什麼？

A. 只記「流程失敗」。  
B. Filter 值、停止位置、負責人、待人工確認出口與後續重試方式。  
C. 重新建立一個 Scenario。  
D. 刪除測試資料。

**答案：B。**可執行流程必須同時證明成功路徑與安全停止路徑。
