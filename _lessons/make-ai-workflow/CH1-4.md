## 教學流程（Teaching Flow）

### 破題 / Hook

CH1-3 已經把「可執行」與「離線模擬」分開：有 Make 的學員手上是 `scenario-v1`，沒有連線的學員手上是 `scenario-v1-offline-map` 與 `run-log-v1-simulated`。兩者都能用來審查規格，但只有 Make 路徑有平台執行證據。每次換來源、增加欄位或加入審核條件，都要重新整理模組清單與測試案例；LLM 可以協助整理這些工作，但它不會自動知道你的資料契約，也不會替你承擔錯誤映射的責任。

本節的任務不是「請 AI 幫我做自動化」；而是把需求、資料契約與限制條件交給 LLM，要求它產出一份人可以逐項檢查的工作流設計規格。阿凱會用同一個客戶回饋案例，請 LLM 提出模組清單、欄位映射、分流條件與測試案例，再用 CH1-2 的契約逐列驗收。

**本節完成物**：

1. `workflow-spec-v1`：包含需求假設、模組清單、映射、限制與測試案例的設計規格。
2. `prompt-log-v1`：記錄送給 LLM 的完整提示、提供的契約摘要與每次修正理由。
3. `review-checklist-v1`：逐項標記 LLM 內容為保留、修正或拒絕，不能只寫「看起來可以」。

**起始狀態**：你有 CH1-2 的契約、兩筆測試資料，以及 CH1-3 的其中一條成果：Make 路徑使用 `scenario-v1` 與實際 `run-log-v1`；離線路徑使用 `scenario-v1-offline-map` 與 `run-log-v1-simulated`。可以使用免費可用的 LLM 介面或教師提供的固定輸出，不需要把 Make token 或任何真實帳號貼給 LLM。

**本節可直接取得的材料**：第一次操作前，請先開啟 [去敏需求描述](../../courses/make-ai-workflow/assets/CH1-4-requirement-brief.md)、[完整提示詞模板](../../courses/make-ai-workflow/assets/CH1-4-prompt-template.md)、[工作流規格模板](../../courses/make-ai-workflow/assets/CH1-4-workflow-spec-template.md)、[提示紀錄模板](../../courses/make-ai-workflow/assets/CH1-4-prompt-log-template.md)、[人工審核清單](../../courses/make-ai-workflow/assets/CH1-4-review-checklist-template.md) 與 [LLM 固定輸出](../../courses/make-ai-workflow/assets/CH1-4-llm-fixed-output.md)。有免費 LLM 介面時使用提示詞模板；沒有帳號或額度時，使用固定輸出完成同樣的逐列審核。

### 概念 / Concepts

#### LLM 在流程設計中的正確角色

LLM 適合做三件事：把自然語言需求拆成模組責任、把契約欄位整理成映射表、依已知限制提出測試案例。LLM 不適合直接決定未提供的連線設定、猜測不存在的欄位，或替你按下上線按鈕。

因此提示詞必須同時提供：**任務、已知資料、限制、輸出格式與驗證要求**。缺少其中一項，LLM 可能生成一段流暢但無法執行的答案。

| 提示區塊 | 白話問題 | 本節提供的內容 |
|---|---|---|
| 任務 | 要設計什麼？ | 客戶回饋整理與人工審核流程 |
| 已知資料 | LLM 可以使用哪些欄位？ | `contract-input-v1`、`contract-output-v1` |
| 限制 | 哪些事不能猜？ | 不含 credential；不得新增未定義欄位 |
| 輸出格式 | 要交付什麼？ | 模組表、映射表、測試表、疑點清單 |
| 驗證要求 | 如何知道答案合格？ | 每列對應契約欄位與成功／失敗出口 |

**正例**：要求 LLM 以表格列出模組角色、輸入、輸出、限制與測試案例，並標出不確定處。  
**錯例**：只輸入「幫我做一個自動回覆流程」，讓 LLM 自己猜工具、欄位與收件人。  
**你要判斷**：如果 LLM 建議 `customer_phone`，但契約沒有這個欄位，應標成「未提供、不得直接採用」，而不是因為看起來合理就加入。

#### 設計規格不是藍圖

`workflow-spec-v1` 是給人審查與後續建置使用的設計文件，不是可以直接匯入 Make 的 JSON。它要留下決策理由、未解疑點與測試案例，讓下一步能把規格轉成模組，而不是把 LLM 的長篇文字當成事實。

### 操作示範 / Demo：把需求交給 LLM，再把答案拆回契約

#### 原始需求

> 工作室收到客戶回饋後，先產生摘要與回覆草稿；需要人工確認的內容不得直接進入文件或通知；一般內容建立 Google Docs，之後再由團隊決定是否加上通知。

#### 提示詞完整版本

```text
你是流程設計助理，不是流程執行者。
請依下列資料設計一份可檢查的 Make 流程規格。

任務：整理客戶回饋，產生摘要與回覆草稿，需人工確認時停止後續動作。
輸入契約：customer_identity（必填文字）、message_text（必填文字）、
urgency_signal（選填數字或空值）、owner_email（固定 Email 設定）。
輸出契約：summary（必填文字）、reply_draft（必填文字）、
needs_review（必填布林值）。
限制：不得使用 credential、token 或個資；不得新增契約未定義的欄位；
Email 不是本次主軸，只列為可替換的後續動作。

請輸出四張表：1. 模組清單 2. 欄位映射 3. 控制與失敗出口 4. 測試案例。
每列都要標明輸入、輸出、驗證方式與不確定處；若資料不足，請寫「需人工確認」。
```

#### LLM 回傳的設計規格（完成品）

| 順序 | 模組角色 | 模組建議 | 輸入 | 輸出 | 驗證方式 | 疑點／限制 |
|---:|---|---|---|---|---|---|
| 1 | 資料來源 | Sheets / Watch Rows（可替換 Gmail） | 來源欄位 | `customer_identity`、`message_text`、`urgency_signal` | 必填欄位與文字內容檢查 | 連線設定需由人提供 |
| 2 | 處理 | Gemini / Generate | 三個輸入契約欄位 | `summary`、`reply_draft`、`needs_review` | 欄位存在與型別檢查 | 不接受未定義欄位 |
| 3 | 控制 | Filter | `needs_review` | `false` 通過；`true` 待人工 | 用兩個測試值驗證 | 人工確認模組未實作 |
| 4 | 後續動作 | Google Docs / Create a Document | `summary`、`reply_draft` | 文件 URL | 文件內容與 URL | 需檢查權限 |

#### LLM 測試案例（完成品）

| 案例 | 變更的輸入 | 預期結果 | 驗證證據 |
|---|---|---|---|
| A：一般回饋 | `needs_review=false` | 通過 Filter，建立 Docs | 文件 URL 與兩個文字欄位 |
| B：需人工確認 | `needs_review=true` | 停在人工出口，不建立 Docs | Filter 停止紀錄 |
| C：型別錯誤 | `needs_review="true"` | 不猜測，標記型別錯誤 | 錯誤紀錄與修正責任 |

#### 人的逐項驗收

LLM 的四張表不是自動通過。阿凱對照 CH1-2 的契約發現：模組清單與欄位都對上，但「人工確認模組」沒有實作，因此他把它標成未實作出口；如果 LLM 提到 `customer_phone` 或直接寄信，就標記拒絕，不讓未定義欄位進入 `workflow-spec-v1`。

### 動手 / Hands-on：讓 LLM 產生可檢查的設計規格

#### 完成物與最短路徑

- **完成物**：`workflow-spec-v1`、`prompt-log-v1`、`review-checklist-v1`。
- **起始狀態**：先開啟上方六份本節材料，再使用 CH1-2 三份契約、CH1-3 的 Make `scenario-v1` 或離線 `scenario-v1-offline-map` 與去敏測試資料；LLM 介面可用或使用固定輸出。兩條路徑都只審查設計規格，不把離線資料當成平台執行紀錄。
- **模板**：複製 [工作流規格模板](../../courses/make-ai-workflow/assets/CH1-4-workflow-spec-template.md)、[提示紀錄模板](../../courses/make-ai-workflow/assets/CH1-4-prompt-log-template.md) 與 [人工審核清單](../../courses/make-ai-workflow/assets/CH1-4-review-checklist-template.md)；無法下載時，可依頁面欄位建立同樣表格。
- **最短可跑路徑**：先用完整提示詞取得四張表，再逐列比對契約；不要先要求 LLM 產生 JSON。

#### 步驟 1：整理需求與邊界

- **模式**：Together
- **學員操作**：複製原始需求，另列出「本次要做」「本次不做」；不做項目包含 credential、實際寄信與未定義客戶欄位。
- **講師提示**：限制不是附註，而是避免 LLM 自行補齊的護欄。
- **預期結果**：`prompt-log-v1` 有一段可直接送出的需求與限制。
- **快速檢查**：遮住工具名稱，仍能說明任務要交付什麼結果。
- **卡住時**：回到 CH1-3 的完成物，先寫成功與停止狀態，再補工具。

#### 步驟 2：貼入契約摘要

- **模式**：Together
- **學員操作**：把輸入／輸出契約的欄位、必填狀態、型別與缺值處理貼入提示詞；移除所有真實帳號與連線資訊。
- **講師提示**：只貼必要資料，讓 LLM 能設計映射但看不到秘密。
- **預期結果**：提示詞明確包含四個輸入欄位與三個輸出欄位。
- **快速檢查**：逐欄圈出 `message_text`、`reply_draft`、`needs_review`。
- **卡住時**：使用 CH1-2 的表格，不要從 Make 畫面臨時抄欄位。

#### 步驟 3：要求固定輸出格式

- **模式**：Demo → Together
- **學員操作**：要求 LLM 輸出模組清單、欄位映射、控制／失敗出口、測試案例四張表，並要求每列提供驗證方式與疑點。
- **講師提示**：表格是審核介面；沒有固定欄位就無法比較 LLM 兩次回答。
- **預期結果**：得到 `workflow-spec-v1` 的四張表，且不是一段無法定位的長文。
- **快速檢查**：每張表都有輸入、輸出或驗證欄位。
- **卡住時**：補上「若資料不足寫需人工確認」，不要讓 LLM 自行猜答案。

#### Checkpoint：LLM 回答是否可審核

- **現在應該看到**：四張表、契約欄位、控制條件、成功／失敗案例都出現；未提供的資訊被標記疑點。
- **若沒看到**：回到步驟 2 或 3，補契約與輸出格式，不要直接採用整段敘述。
- **通過後才能繼續**：你能在回答中找到每一個模組的輸入、輸出、限制與驗證方式。

#### 步驟 4：比對模組清單

- **模式**：Together
- **學員操作**：逐列對照 `scenario-v1` 與 `workflow-spec-v1`，將模組標記「保留／修正／拒絕」，並寫理由。
- **講師提示**：工具名相同不代表責任相同；要看角色與下游用途。
- **預期結果**：模組清單每列都有人的審核狀態。
- **快速檢查**：指出一列 LLM 建議與契約不符的內容，或確認它為何保留。
- **卡住時**：回到四種模組角色與輸出契約，先判責任再判工具。

#### 步驟 5：比對欄位映射與限制

- **模式**：Together
- **學員操作**：檢查 `customer_identity`、`message_text`、`owner_email`、`needs_review` 的來源、型別與去向；任何未定義欄位標記拒絕。
- **講師提示**：映射錯誤比工具錯誤更難被察覺，因為答案看起來仍然完整。
- **預期結果**：`review-checklist-v1` 有欄位級判斷與修正理由。
- **快速檢查**：確認 `sender` 未被當成 `owner_email`，`needs_review` 未被寫成文字條件。
- **卡住時**：使用「原始欄位 → 契約欄位 → 下游」三段式追蹤。

#### 步驟 6：驗證測試案例

- **模式**：Together
- **學員操作**：檢查 LLM 是否提出一般、需人工、型別錯誤三種案例；若缺少一種，要求它只補該案例，不重新生成整份規格。
- **講師提示**：測試案例要改一個主要變因，才能知道哪條規則被觸發。
- **預期結果**：`workflow-spec-v1` 有三種案例與可觀察預期結果。
- **快速檢查**：每個案例都有輸入變更、預期狀態與驗證證據。
- **卡住時**：回看 CH1-3 的 `test-cases-v1`，沿用已有測試，不接受抽象的「測試成功」。

#### Checkpoint：規格能否交給建置者

- **現在應該看到**：每個模組、欄位、限制與測試都有審核狀態；未實作的人工出口被保留為疑點。
- **若沒看到**：回到步驟 4～6，補上保留／修正／拒絕與理由。
- **通過後才能繼續**：另一位建置者只看 `workflow-spec-v1`，能開始配置模組而不需要猜欄位。

#### 步驟 7：提出一次受控追問

- **模式**：Solo
- **學員操作**：只改一個條件，要求 LLM 將來源從 Sheets 改為 Gmail；保留輸出契約、Filter 與 Docs，並要求列出受影響欄位。
- **講師提示**：追問要限定變因，才能比較前後差異。
- **預期結果**：LLM 只修改來源與輸入映射，明確寫出 `sender`、`subject + body` 與 `owner_email` 的用途。
- **快速檢查**：沒有新增 `customer_phone` 或付費連線要求。
- **卡住時**：把完整規格重新貼回去，並要求「只輸出變更表」。

#### 步驟 8：保存提示與決策紀錄

- **模式**：Check
- **學員操作**：在 `prompt-log-v1` 保存原始提示、LLM 回答摘要、人的修正與拒絕項目；在 `review-checklist-v1` 寫通過條件。
- **講師提示**：紀錄「為什麼採用」比紀錄「AI 說了什麼」更能交接。
- **預期結果**：三份完成物可回溯，未來可比較 LLM 版本或重新產生答案。
- **快速檢查**：另一個人能看懂哪些內容由 LLM 提出、哪些由人決定。
- **卡住時**：使用四欄句型：原建議／事實依據／人的決定／後續影響。

### 變化練習 / Solo Transfer

只把需求改為「每週彙整多筆回饋，先依 `needs_review` 分成待人工與可建立文件兩群」，要求 LLM 只補上批次處理的模組責任與兩個測試案例；不得直接加入 Iterator 或新欄位，除非它說明為何契約需要改變。

### 檢核 / Verification

- [ ] `workflow-spec-v1` 有模組清單、欄位映射、限制／失敗出口與測試案例四張表。
- [ ] 每一列都能對照 CH1-2 的輸入／輸出契約，未定義欄位被標記拒絕或需人工確認。
- [ ] `prompt-log-v1` 保存完整提示、契約摘要、限制與修正理由，不含 credential、token 或個資。
- [ ] `review-checklist-v1` 逐項標記保留／修正／拒絕，並有事實依據。
- [ ] 測試案例包含一般、需人工、型別錯誤三種路徑，且每次只改一個主要變因。
- [ ] 來源改成 Gmail 時，只修改輸入映射與受影響欄位，不破壞輸出契約與 Filter。

### 商業情境案例 / Case

阿凱要把 CH1-3 的成果交給雯姊審核。若是 Make 路徑，他附上 `scenario-v1` 與實際測試紀錄；若是離線路徑，他附上 `scenario-v1-offline-map` 與 `SIMULATED` 測試紀錄，並明確說明尚未在平台執行。雯姊不接受「AI 說這樣設計」作為理由，她要看每個模組的責任、欄位來源、限制與測試證據。這個案例讓 LLM 成為設計助理，而不是無法追責的自動決策者。

### 常見錯誤 / Pitfalls

1. **提示詞只有目標沒有契約**：LLM 自行補欄位與工具。修正是貼入必填／選填／型別與輸出格式。
2. **把 LLM 回答當成 Make 藍圖**：直接照著配置而不比對測試。修正是先產出 `workflow-spec-v1`，逐列標記保留／修正／拒絕。
3. **一次要求太多變更**：來源、條件、通知同時改。修正是一次只改一個變因，留下前後版本與理由。

### 檢核題 / Quiz

#### Q1

為什麼提示詞要寫「不得新增契約未定義的欄位」？

A. 讓回答變短。  
B. 避免 LLM 把合理但不存在的資料當成可用輸入，讓人能逐欄驗收。  
C. 讓 Make 自動產生 credential。  
D. 讓 Email 成為主軸。

**答案：B。**限制讓 LLM 的建議留在已知事實範圍內。

#### Q2

LLM 建議新增 `customer_phone`，但契約沒有這個欄位。你應該怎麼做？

A. 直接加入，因為看起來合理。  
B. 標記未提供／需人工確認，拒絕直接採用，並記錄是否需要回到契約設計。  
C. 刪除整份回答。  
D. 把欄位改成 `owner_email`。

**答案：B。**先保護契約邊界，再決定是否真的需要變更上游規格。
