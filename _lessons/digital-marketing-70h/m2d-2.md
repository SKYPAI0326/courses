## 1. 自動化在解決什麼問題

先看一個你可能很熟的場景。山徑咖啡的社群企劃每週一早上都做同一件事：

1. 把自家和兩個競品的貼文整理成一張表。
2. 檢查有沒有漏抄網址、數字有沒有抄錯。
3. 數每個品牌發了幾篇、哪一篇互動最高。
4. 寫一段摘要給店長。

每週的步驟一樣、資料長得一樣，只有內容不同。這種「**每週重複取資料、檢查、整理、起草**」的工作，就是自動化最適合接手的。你在公司每週整理報價單、彙整同事交來的資料，也是同一類工作。

但自動化不是「把整件事丟給機器」。這一節的單元摘要只有一句話，請記住它：

> **先畫清楚資料、規則、失敗去向與人工核准，再決定是否上平台。**

順序是先設計、後上平台。設計沒畫清楚就上平台，只是讓錯誤跑得更快。

### 1.1 兩個最基本的詞：觸發器與動作

- **觸發器（Trigger）**：讓流程「開始跑」的那件事。例如「每週一早上 9 點到了」、「有人上傳了一個新檔案」、「有人按下執行」。
- **動作（Action）**：流程開始後「要做的事」。例如「讀取檔案」、「把資料寫進試算表」、「寄一封信」。

一條流程 = **一個觸發器 + 後面一個或多個動作**。

### 1.2 一條流程的五個元件

光有觸發和動作還不夠，設計時要把五件事都寫出來：

| 元件 | 問自己的問題 | 山徑咖啡的例子 |
|---|---|---|
| 觸發 | 什麼事情發生時開始？ | 負責人每週一手動按下執行 |
| 輸入 | 流程拿到什麼資料？ | 一份競品貼文 CSV |
| 處理 | 拿到之後做什麼？ | 檢查、彙整、請 AI 起草 |
| 輸出 | 最後交出什麼？ | 一份待核准的摘要草稿＋錯誤清單 |
| 停止條件 | 什麼時候結束、什麼時候該停下來？ | 草稿交到核准者手上就結束；檔案讀不到就停 |

「停止條件」你在 2A-2（代理）和 2D-1（深度研究）都碰過：開始前就先講好什麼時候停。自動化流程也一樣，**沒寫停止條件的流程，碰到壞資料（例如 -3、空白網址）不會自己停，會一路往下走**。

設計時還有一個習慣要養成：**每一步都寫「收到什麼」和「交出什麼」**。上一步交出的東西，就是下一步收到的東西。寫得出來，流程才接得起來；寫不出來，就代表那一步還沒想清楚。

### 1.3 平台上的叫法（介面是英文，對照著看）

Make 和 Zapier 是兩個常見的自動化平台，不用寫程式，用拖拉方塊的方式把步驟串起來。它們用的詞不一樣，但對應的是同樣的概念：

| 概念 | Make 的叫法 | Zapier 的叫法 |
|---|---|---|
| 一整條流程 | 情境（Scenario） | Zap |
| 流程中的一步 | 模組（Module） | 步驟（Step） |
| 讓流程開始的那一步 | 觸發模組（Trigger）：一個情境只能有一個，而且要放在第一步 | Trigger：每個 Zap 由一個 trigger 開始 |
| 開始後要做的事 | 動作模組（Action）：可以放很多個 | Action：一個或多個 |
| 手動跑一次來測試 | Run once（按一次，只跑一次） | 設定時用一筆範例資料測試（test） |
| 讓它自動跑 | 設定排程（Scheduling） | 開啟 Zap（turn on），之後每次觸發事件發生就自動執行 |

不用背英文介面的位置。**選單位置、按鈕名稱會改版，實際位置以你操作當天的官方畫面為準**；你要帶走的是左邊那一欄的概念。


## 2. 哪些工作適合自動化，哪些要留給人

### 2.1 三個條件都符合，才適合自動化

1. **輸入穩定**：每次都會有、來源固定。（每週都有競品貼文資料）
2. **格式固定**：每次的欄位都一樣。（每次都是同樣六欄）
3. **結果可觀察、可判斷對錯**：做完之後，看得出來對不對。（「有效貼文 8 篇」可以回頭數一次確認）

缺一個就先別自動化。例如「這篇貼文的語氣適不適合我們品牌」——每次情況不同、沒有固定對錯，這類工作要**留給人判斷**。其他典型要留給人的：要不要對外發布、跟錢或客戶承諾有關的決定、例外情況怎麼處理。

### 2.2 每一步交給誰：規則、公式、AI、人

設計流程時，每一步都要決定「由誰做」。四種做事的角色，分工如下：

| 由誰做 | 適合做的事 | 例子 |
|---|---|---|
| 規則 | 有明確對錯的檢查 | 「網址不能空白」、「日期要長這樣 YYYY-MM-DD」 |
| 公式 | 計算 | 按讚＋留言＝互動合計 |
| AI | 跟語言有關的事：起草、摘要、改寫 | 把彙整結果寫成一段給店長看的文字 |
| 人 | 判斷與決定 | 核准這份摘要能不能寄出 |

最重要的一條：**檢查和計算不交給 AI。** AI 擅長寫字，但它可能把數字算錯、或把有問題的資料當成正常的寫進去。所以檢查用規則、計算用公式，**驗證放在 AI 之前**，AI 只拿到已經確認過的資料。

### 2.3 換個情境也通：費用報支

這套想法不只用在行銷。拿你熟悉的行政工作「費用報支」來套：

| 元件 | 內容 | 由誰做 |
|---|---|---|
| 觸發 | 同事上傳一張報支單 | — |
| 輸入 | 日期、金額、類別、單據照片 | — |
| 處理 1：驗證 | 金額是數字、日期在本月、類別在公司清單內 | 規則 |
| 處理 2：彙整 | 每人本月合計 | 公式 |
| 處理 3：起草 | 寫一段報支摘要給主管 | AI |
| 處理 4：核准 | 主管核准或退回 | 人 |
| 輸出 | 核准後送會計；退回時通知同事補件 | — |
| 停止條件 | 送到會計或退回給同事就結束 | — |

只要你能把一件工作拆成這張表，你就有能力設計它的自動化，不論是什麼產業。


## 3. 先看懂資料：CSV 與資料契約

### 3.1 CSV 是什麼

CSV 是一種最單純的表格檔：**每一行是一筆資料，同一行裡的欄位用半形逗號 `,` 隔開**。第一行通常是欄位名。很多系統（社群後台、電商後台、表單）都能匯出 CSV，自動化平台也很常讀它。

示範檔的前兩行長這樣：

```text
brand,published_at,url,caption,likes,comments
山徑咖啡,2026-10-13,https://example.com/posts/trail-101,"新手升級手沖壺前，先看出水穩定度。",128,14
```

- 第一行是六個欄位名：brand（品牌）、published_at（發布日期）、url（網址）、caption（貼文文字）、likes（按讚數）、comments（留言數）。
- 第二行是第一筆資料。caption 外面的雙引號，是為了讓文字裡就算有逗號也不會被切開。
- 兩個逗號中間什麼都沒有（例如 `,,`），或最後一個逗號後面沒東西，代表那一格是**空白**。

### 3.2 打開 CSV 的兩個小陷阱

**陷阱一：試算表會「自作主張」改格式。** 用 Excel 直接雙擊打開時，`2026-10-13` 這種日期可能被自動轉成日期格式，畫面上顯示成 `2026/10/13`。這樣一來，原本格式正確和格式錯誤的日期，在畫面上可能長得一模一樣，你就檢查不出來了。

**檢查格式時，請用純文字編輯器（記事本／文字編輯）打開 CSV**，看到的才是檔案裡真正的字。用 Google 試算表的話，可以從「檔案 → 匯入」上傳，匯入時取消勾選「把文字轉換成數字、日期」的那個選項（選項文字以畫面為準）。【待實機確認】

**陷阱二：中文變亂碼。** 如果 Excel 打開後中文變成亂碼，Windows 版 Excel 可改用「資料 → 從文字/CSV」匯入，或改用 Google 試算表匯入。

### 3.3 列號怎麼數（最容易寫錯的地方）

本課規定：**列號以試算表的列號為準，第 1 列是欄位名。** 所以第一筆資料在第 2 列，不是第 1 列。

| 試算表列號 | 內容 |
|---|---|
| 1 | brand,published_at,url,…（欄位名，不是資料） |
| 2 | 第 1 筆資料 |
| 3 | 第 2 筆資料 |
| … | … |
| 11 | 第 10 筆資料 |

最保險的做法：在試算表裡打開，**直接看最左邊灰色的列號**，不要自己從 1 開始數。Mac 的文字編輯沒有行號，Windows 記事本的行號只在下方狀態列（游標所在的「行」），所以列號請看試算表。

### 3.4 資料契約：事先講好「什麼樣的資料算合格」

**資料契約**就是流程和資料之間事先講好的規矩：資料要有哪些欄位、每個欄位要長什麼樣子。符合的才往下走，不符合的就是**壞資料**。

本單元的資料契約：

| 欄位 | 規矩 | 合格例子 | 不合格例子 |
|---|---|---|---|
| 全部 | 一定要剛好六欄：brand、published_at、url、caption、likes、comments | — | 少一欄、欄位名拼錯 |
| published_at | 格式是 YYYY-MM-DD（年-月-日，用半形減號） | 2026-10-13 | 2026/10/13、10-13 |
| url | 必填，不能空白 | https://example.com/posts/trail-101 | （空白） |
| likes | 非負整數：0、1、2…… | 128、0 | -3、1.2k、空白 |
| comments | 非負整數 | 14、0 | -1、空白、12.5 |

**拿著契約逐列檢查，這個動作就叫驗證。** 有幾個判斷原則：

- **只看契約，不猜。** 看到 `1.2k`，你可能會想「大概是 1200 吧」，但流程不能猜。它不符合「整數」，就是壞資料，要回到原始貼文查證後再修。
- **空白也是錯。** 留言數空白不等於 0；可能是漏抄，也可能真的是 0，流程無法判斷。
- **一列可能有不只一個錯。** 每個錯的欄位都要分開記一行。
- **caption 契約沒有規定**，內容寫什麼都不算錯。


## 4. 示範：山徑咖啡的六步可控流程

接下來用示範資料 `competitor-posts-practice.csv` 走一遍。這份資料有 10 筆貼文（試算表第 2～11 列），其中藏了兩筆壞資料。示範**沒有在平台上執行**，是用「紙上試跑」的方式，把資料一列一列走過流程。

### 4.1 先看設計圖

```text
【觸發】負責人每週一手動執行（不開自動排程）
   │
   ▼
步驟1 手動觸發 ─→ 步驟2 讀取 CSV ──讀不到／欄位不對──→ 【停止】通知負責人
                      │
                      ▼
                 步驟3 驗證 ──壞資料──→ 錯誤清單（不進彙整、不進 AI）
                      │ 通過驗證的資料
                      ▼
                 步驟4 彙整（有效貼文數、各品牌互動最高貼文）
                      │ 只有彙整值＋各品牌最高貼文原文與網址
                      ▼
                 步驟5 AI 起草
                      │ 草稿
                      ▼
                 步驟6 人工核准 ──退回──→ 依原因回到步驟 2／4／5
                      │ 核准
                      ▼
【停止條件】核准後的摘要存檔並寄給店長，本次執行結束
           （流程只到草稿與核准，永遠不自動對外發布）
```

### 4.2 六步流程表

流程表固定六欄：步驟、收到的欄位、做什麼、交出什麼、失敗去向、由誰做。

| 步驟 | 收到的欄位 | 做什麼 | 交出什麼 | 失敗去向 | 由誰做 |
|---|---|---|---|---|---|
| 1 手動觸發 | 本週的 CSV 檔名 | 負責人確認檔案已放好，按下執行 | 「開始執行」＋檔名 | 檔案還沒到：不執行，等檔案 | 人 |
| 2 讀取 CSV | 檔名 | 打開檔案，確認欄位剛好是那六欄，逐列讀出 | 每一列的六個欄位＋列號 | 檔案讀不到、欄位不是那六欄：整個流程停止，通知負責人 | 規則（平台模組） |
| 3 驗證 | 每一列的 brand、published_at、url、caption、likes、comments＋列號 | 依資料契約逐列檢查 | 通過的列；錯誤清單 | 壞資料寫進錯誤清單，停在這一步，不進彙整、不進 AI | 規則 |
| 4 彙整 | 通過驗證的列：brand、url、caption、likes、comments | 算每個品牌的有效貼文數；每篇算按讚＋留言，找出各品牌互動合計最高的一篇 | 彙整表：品牌、有效貼文數、最高貼文的網址、原文、互動合計；以及「本批共幾列、幾列未通過」 | 數字對不起來：停止，回步驟 4 重算 | 公式（本節先人工計算） |
| 5 AI 起草 | 彙整表＋各品牌最高貼文的原文與網址＋未通過列數 | 用固定的提示詞請 AI 寫摘要草稿 | 摘要草稿 | 草稿出現沒給它的數字或內容：退回步驟 5 重寫 | AI |
| 6 人工核准 | 摘要草稿＋彙整表＋錯誤清單 | 對照彙整表檢查草稿，決定核准或退回 | 核准後的摘要 | 退回：依原因回到步驟 2、4 或 5（見 4.6） | 人 |

注意第 3 步：**壞資料停下來，好資料繼續走。** 這批 10 筆有 2 筆壞的，另外 8 筆照樣進彙整和 AI 起草；壞的那 2 筆只會出現在錯誤清單裡。

### 4.3 步驟 3 驗證：逐列檢查，寫出錯誤清單

用純文字編輯器打開示範檔，逐列對照資料契約。大部分列都沒問題，有兩列有狀況：

```text
日常手沖,2026-10-18,,"新款濾杯開箱，留言告訴我們最想測哪種豆。",173,24
日常手沖,2026-10-19,https://example.com/posts/daily-304,"週日直播：新手器具問答。",-3,12
```

第一行的日期後面緊接兩個逗號 `,,`，代表網址是空白的；第二行的按讚數是 -3。對照試算表左邊的列號，它們分別在第 10 列和第 11 列。

**錯誤清單**（四欄：列號、欄位、原因、停在哪一步）：

| 列號 | 欄位 | 原因 | 停在哪一步 |
|---|---|---|---|

### 4.5 步驟 5 AI 起草：只給通過驗證的資料

**不要把整份 CSV 直接貼給 AI。** AI 只收到彙整值，以及各品牌互動最高那篇有效貼文的原文與網址。理由有兩個：壞資料不能混進去；AI 拿到原始數字可能會自己亂算。

示範提示詞（直接複製到 AI 工具使用）：

```
你是咖啡器具選品店「山徑咖啡」的社群企劃助理。
請根據下面的自家與競品貼文彙整，寫一段給店長看的每週競品摘要。

【資料說明】
- 資料期間：2026-10-13 至 2026-10-19 的競品貼文
- 這是已經檢查過的資料：本批共 10 列，8 列通過檢查，2 列未通過（日常手沖 2 列），未通過的資料沒有放進下面的彙整
- 互動合計＝按讚數＋留言數

【彙整】
1. 山徑咖啡：有效貼文 3 篇。互動最高：「三種注水速度對風味的影響。」互動合計 211，網址 https://example.com/posts/trail-103
2. 拾光咖啡：有效貼文 3 篇。互動最高：「本週會員日第二杯半價。」互動合計 276，網址 https://example.com/posts/time-203
3. 日常手沖：有效貼文 2 篇。互動最高：「辦公室也能完成的五分鐘手沖流程。」互動合計 160，網址 https://example.com/posts/daily-301

【要求】
- 用繁體中文，200 字以內，分成「本週重點」和「可以參考的做法」兩段

- 提到日常手沖時，要註明「有 2 列資料未通過檢查，排名可能不完整」
```

### 4.6 步驟 6 人工核准點

人在迴路（Human-in-the-loop）的意思是：流程中間留一個位置給人做決定，**人沒點頭，流程就不往下走**。核准點要寫清楚四件事：

| 項目 | 山徑咖啡的寫法 |
|---|---|
| 負責人 | 社群企劃（本流程的負責人） |
| 核准後 | 摘要存進共用資料夾「每週競品摘要」，並寄給店長 |
| 退回到 | 草稿寫錯或語氣不對 → 步驟 5；數字對不上彙整表 → 步驟 4；懷疑原始資料有問題 → 步驟 2 |
| 未核准時 | 草稿、彙整表、錯誤清單都保留，標「未核准」；不寄出、不發布 |

**另一個常見的核准點：內容發布流程。** 如果你設計「AI 寫貼文 → 自動發到粉專」，中間一定要有人工核准：AI 起草 → 人核准 → 才排程發布。退回時回到起草那一步；沒核准時草稿留著、不發。粉專一旦發出去就收不回來，所以「發布」這個動作永遠留給人決定。

### 4.7 重跑起點：錯在哪，從哪裡重來

流程出錯後，不用每次都從頭跑。原則是：**從「第一個需要改變結果的步驟」開始重跑**，前面已經確認沒問題的步驟不用重做。

| 錯誤類型 | 例子 | 怎麼處理 | 重跑起點 |
|---|---|---|---|
| 資料錯誤 | 第 10 列網址空白、第 11 列按讚 -3 | 回原始貼文查證，修正 CSV 來源檔 | 步驟 2 讀取 CSV（檔案變了，要重讀、重新驗證） |
| 檔案錯誤 | 讀不到檔案、欄位名不對 | 重新匯出或放對檔案 | 步驟 2 讀取 CSV |
| 計算錯誤 | 互動合計加錯 | 重算 | 步驟 4 彙整（驗證結果沒變，不用重驗） |
| 起草錯誤 | AI 寫了沒提供的數字、語氣不對 | 調整提示詞，重新起草 | 步驟 5 AI 起草 |

為什麼要分開？如果只是 AI 語氣不對，卻從頭讀檔、驗證、彙整，既浪費時間，又可能在重做時引入新的錯誤。反過來，如果是資料改了，卻只從步驟 5 重跑，AI 用的就還是舊的彙整，結果會是錯的。

（小提醒：因為這條流程由人手動觸發，「從步驟 2 重跑」實際操作上就是負責人再按一次執行，讓流程讀取修正後的檔案。）

示範沒有在平台上跑，所以平台狀態寫：**尚未在平台執行**。


## 5. 設計圖能證明什麼，執行紀錄能證明什麼

這兩樣東西證明的事情不一樣，請分清楚：

| | 能證明 | 不能證明 |
|---|---|---|
| 流程設計圖（你今天交的） | 流程已經規劃好：步驟、欄位、錯誤去向、核准點都想清楚了 | 平台上真的照這樣跑過 |
| 平台的真實執行紀錄 | 這條路徑在平台上實際跑過，壞資料真的走到錯誤路徑 | 設計本身是否周全 |

### 如果你有 Make 帳號：用 Run once 測試

Run once 是在情境（scenario）編輯畫面上**手動執行一次**的按鈕，按一次只跑一次，適合用來測試。測試方法：

1. 照你的六步流程表，在 Make 建好對應的模組。
2. 用**同一份測試資料**（示範 CSV 或練習 CSV）按 Run once。
3. 確認兩件事：**壞資料有走到錯誤路徑**，以及**正確資料只走到「草稿」**，沒有被寄出或發布。
4. 確認無誤後，平台狀態改寫為「已用 Run once 測試」，並保留執行紀錄的畫面。

各模組的欄位要怎麼對應、按鈕在畫面哪裡，**請以你操作當天的 Make 官方畫面為準**，這一節不教點擊位置。

**要不要開啟排程（讓它每週自動跑），由帳號負責人決定。** 測試通過不等於可以自動上線。

### 面試時怎麼講

沒有帳號、只交設計圖，一樣是完整的作品，關鍵是**講清楚做到哪裡**。例如：

> 「我設計了一條競品貼文週報流程，六個步驟，驗證放在 AI 之前。我用一份 11 列的測試資料逐列走過，抓出 3 筆不符合資料契約的資料，並為不同錯誤設定了重跑起點和人工核准點。這份設計目前尚未在平台執行。」

誠實說「尚未在平台執行」，比說「我做過自動化」更可信。面試官要看的，是你能不能把一件工作拆成可控的流程。

| 名詞 | 一句話 |
|---|---|
| 觸發器（Trigger） | 讓流程開始的事件 |
| 動作（Action） | 流程開始後要做的事 |
| 停止條件 | 什麼時候結束、什麼時候該停下來 |
| 情境（Scenario） | Make 對「一條流程」的叫法 |
| 模組（Module） | Make 對「流程中一步」的叫法；觸發模組只能有一個，放第一步 |
| Zap | Zapier 對「一條流程」的叫法，由一個 trigger 開始，再接一個或多個 action |
| Run once | Make 裡手動執行一次的按鈕，用來測試 |
| CSV | 用逗號分隔欄位的純文字表格檔，第一行通常是欄位名 |
| 資料契約 | 事先講好資料要有哪些欄位、每欄長什麼樣 |
| 驗證 | 拿資料契約逐列檢查資料 |
| 彙整 | 把通過驗證的資料算成摘要數字 |
| 人在迴路（Human-in-the-loop） | 流程中留位置給人決定，人沒點頭就不往下走 |
| 人工核准點 | 人做決定的那一步：誰核准、核准後去哪、退回哪、沒核准留下什麼 |
| 重跑起點 | 出錯後從哪一步重新跑；從第一個需要改變結果的步驟開始 |

### 本講義參考的官方說明（2026-11 查閱）

- Make，Types of modules：https://help.make.com/types-of-modules（一個情境只能有一個觸發模組，且須放在第一個；動作模組可以有多個、放在任何位置）
- Make，Scenario settings：https://help.make.com/scenario-settings（用 Run once 手動執行時，只會執行一個循環）
- Zapier，Learn key concepts in Zap workflows：https://help.zapier.com/hc/en-us/articles/8496181725453-Learn-key-concepts-in-Zap-workflows（Zap 是連接應用程式的自動化流程；trigger 是啟動 Zap 的事件；action 是觸發後執行的事件）

工具介面變動快，本講義教的是用法與判斷，按鈕名稱與位置以你操作當天的官方畫面為準。

## 卡住時

- **Mac 版 Excel 找不到「從文字/CSV」：** Mac 版 Microsoft 365 要走「資料 → 取得資料（Power Query）→ Text/CSV」，16.57 以上版本才有；找不到就改用 Google 試算表匯入。
- **用「從文字/CSV」匯入後中文還是亂碼：** 在匯入畫面的「檔案原點（File Origin）」選「65001：Unicode (UTF-8)」。
