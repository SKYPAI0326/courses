## 1. 起點：事件送出去之後，還有兩個問題

7-3 你已經做到「按鈕被按 → 資料層出現 `line_join` → GTM 觸發 → GA4 收到」。你可能注意到，每次在練習頁重新整理後都要先按「接受全部」才操作。這堂要回答那個按鈕背後的事。

事件送得出去之後，還要多判斷兩件事：

1. **使用者同不同意？** 這位訪客有沒有同意「分析用途」或「廣告用途」？沒同意的話，代碼該怎麼做？→ 這是**同意模式**（第 2～6 節）。
2. **是不是同一筆？** 同一次預約，如果瀏覽器（Meta 像素）送了一次、伺服器（轉換 API）又送了一次，平台會不會算成兩筆？→ 這是**事件去重**（第 7～8 節）。

兩個問題都管「數字可不可信」：第一個讓數字合乎使用者的選擇，第二個讓數字不灌水。


## 2. 同意模式：四個主要項目各管什麼

**同意模式（consent mode）**：把「使用者同意了什麼」傳給 Google 代碼，讓代碼依此調整「要不要存 Cookie」「要送什麼資料」。它是傳遞同意狀態的機制，不是同意橫幅本身。

### 2.1 四個主要項目

| 項目 | Google 官方說明（意譯） | 白話 | 山徑咖啡例子 |
|---|---|---|---|
| `ad_storage` | 啟用與**廣告**相關的儲存，例如 Cookie | 可不可以為了廣告**存** Cookie | 存下「這位訪客是從某則廣告點進來的」 |
| `analytics_storage` | 啟用與**分析**相關的儲存，例如 Cookie，用來算造訪時間長度等 | 可不可以為了分析**存** Cookie | GA4 記住「同一位訪客這次停留多久、第幾次來」 |
| `ad_user_data` | 設定是否同意把**使用者資料送給 Google**，用於線上廣告 | 可不可以把資料**送**給 Google 做廣告 | 預約轉換的資料能不能送給 Google 廣告 |
| `ad_personalization` | 設定是否同意**個人化廣告** | 可不可以拿來做**個人化**廣告，例如再行銷 | 看過溪線 700 的人，之後能不能再看到它的廣告 |

### 2.2 分不清楚時，用這個拆法

四個名稱都是「前半＋後半」：

- **前半說「什麼用途」**：`ad_` = 廣告；`analytics_` = 分析。
- **後半說「做什麼事」**：
  - `_storage` = **存**（在瀏覽器存 Cookie 之類的東西）
  - `_user_data` = **送**（把使用者資料送給 Google）
  - `_personalization` = **用**（用來做個人化廣告）

所以一口氣念：「**廣告存、分析存、廣告送、廣告用**」。只有一個是分析，其餘三個都是廣告。這堂你實際動手設定的只有 `analytics_storage`。

### 2.3 另外三個項目（知道就好）

| 項目 | 管什麼 | 例子 |
|---|---|---|
| `functionality_storage` | 網站功能需要的儲存 | 記住語言設定 |
| `personalization_storage` | 個人化需要的儲存 | 影片推薦 |
| `security_storage` | 安全需要的儲存 | 登入驗證、防詐騙 |

練習頁只送前四項，這三項本單元不測。


## 3. 基本模式與進階模式

| | 基本模式 | 進階模式 |
|---|---|---|
| 使用者還沒回應橫幅時 | Google 代碼**不載入** | Google 代碼**先載入**，同意狀態預設為拒絕 |
| 使用者拒絕時 | **不送任何資料**給 Google | 送出**不使用 Cookie** 的訊號 |
| 使用者同意時 | 載入代碼，送完整資料 | 送完整資料 |
| 模型補估 | 只能用一般模型 | 可用針對該廣告主的模型（較細） |

**哪一種比較好？沒有標準答案。** 模式由**網站的政策**決定（法務、隱私政策、公司對風險的態度），不是 GTM 的技術預設，也不是你個人可以替網站決定的。量測練習包的原則是：

> 先依網站政策決定基本模式或進階模式……沒有政策來源時先標「待確認」，不要代替網站決定。

**練習頁用的是進階模式的做法**：一載入就先送出四項預設「拒絕」，接著照樣載入你的 GTM 容器。容器 ID 有效時，不會因為預設拒絕就不載入。

### 3.1 行為建模：小網站多半輪不到

進階模式下，GA4 有機會用「行為建模」補估拒絕者的行為。但 Google 說明的資格門檻要**同時**達到：

1. 拒絕 `analytics_storage` 的事件，**每天至少 1,000 筆，至少 7 天**；
2. 過去 28 天中**至少 7 天**，每天至少有 **1,000 位**同意分析儲存（`analytics_storage` 為同意）的使用者。

而且 Google 也說，達到門檻不保證一定會套用。山徑咖啡這種在地小店、你們組的巷口晨光，每天大概沒有上千位訪客，所以**別把「進階模式能補估」當成選進階模式的理由**。


## 4. 順序與 GTM 裡的四個位置

### 4.1 正確順序只有一種

```text
同意預設（default）→ 載入代碼 → 使用者選擇 → 同意更新（update）
```

預設一定要在任何代碼讀取同意狀態**之前**送出。如果代碼先跑、預設才到，代碼在那一瞬間根本不知道使用者有沒有同意。

練習頁的實際程式就是這個順序：頁面一載入、在載入 GTM 之前，先送

```js
gtag('consent', 'default', {
  ad_storage: 'denied',
  analytics_storage: 'denied',
  ad_user_data: 'denied',
  ad_personalization: 'denied'
})
```

按橫幅按鈕時，再送 `gtag('consent', 'update', …)`：

| 你做的事 | 四項狀態 | 橫幅標題變成 |
|---|---|---|
| 剛打開或重新整理頁面 | 四項都是 `denied`（預設） | 同意模式練習 |
| 按「接受全部」 | 四項更新為 `granted` | 已選擇：接受全部 |
| 按「只保留必要」 | 四項維持 `denied`（也會送一次更新） | 已選擇：只保留必要 |

練習頁**沒有「部分接受」**。另外，同意的預設與更新**不會**出現在頁面右下角的事件監看區，要到 Tag Assistant 才看得到。

### 4.2 GTM 裡跟同意有關的四個地方

| 位置 | 是什麼 | 這堂要不要動手 |
|---|---|---|
| **Consent Initialization 觸發條件**（同意初始化） | GTM 裡**最早**觸發的觸發條件，比 Initialization 還早。每個網頁容器都內建一個「Consent Initialization - All Pages」。用來掛「設定同意預設」或同意管理工具（CMP）的代碼。 | 不用。練習頁已經自己在 GTM 之前送了預設。你只要知道：真實網站若用 GTM 設預設，就掛在這裡。 |
| **內建同意檢查**（Built-In Consent Checks） | Google 代碼（含 GA4 事件代碼）本身就會看同意狀態、自動調整行為。代碼的同意設定裡會列出它內建檢查哪些項目。 | 只看，不改。 |
| **額外同意檢查**（Additional Consent Checks） | 你另外加的條件：**指定的項目全部為同意，代碼才執行**。 | **要動手**：在 `line_join` 事件代碼加 `analytics_storage`。 |
| **同意總覽**（Consent Overview） | 在代碼清單集中看「哪些代碼設了同意、哪些沒設」。 | 選做：開來看一眼。 |

**為什麼 Google 代碼不加額外同意，事件代碼要加？** 量測練習包的設計是：Google 代碼保留內建檢查（進階模式下拒絕時仍會以不使用 Cookie 的方式運作），只在事件代碼加「額外同意 `analytics_storage`」。這樣你在 Tag Assistant 會清楚看到差別：拒絕時，事件代碼**不觸發**；同意時才觸發。這是課堂練習的設計，真實網站要照網站政策決定每支代碼的設定。


## 5. 實作一：`line_join` 三種同意情境測試

預計時間：設定約 10 分鐘、測試與記錄約 20 分鐘。

### 5.1 在事件代碼加額外同意

GTM 介面語言不同、改版後，選單名稱可能略有差異；以下中文後面附英文原文，畫面以實際為準。

1. 打開 GTM，進入你的容器工作區。
2. 左側點「**代碼**」（Tags），在清單中點你 7-3 建的 `line_join` GA4 事件代碼。
3. 點「**代碼設定**」（Tag Configuration）區塊進入編輯。
4. 往下找到「**進階設定**」（Advanced Settings），點開。
   - 這就是你擔心「藏很深」的地方：它在代碼設定的**最下面**，要先點開「進階設定」才看得到。
5. 點開「**同意聲明設定 (BETA)**」（Consent Settings）。你會看到兩區：
   - 「**內建同意聲明檢查**」（Built-In Consent Checks）：列出這支代碼本身就會看的項目。**不用改**，截圖留著就好。
   - 「**額外同意聲明檢查**」（Additional Consent Checks），有三個選項：
     - 未設定（Not set）：預設值，不做額外檢查。
     - 不需要額外同意聲明（No additional consent required）：表示你檢查過了，這支代碼不需要額外同意。
     - **需要額外同意聲明才能觸發代碼**（Require additional consent for tag to fire）← 選這個。

![GTM 代碼編輯畫面：進階設定 → 同意聲明設定 (BETA)，內建同意聲明檢查與額外同意聲明檢查三個選項](assets/handouts/m7-4/gtm-同意聲明設定.png)

*GTM 網頁版，以既有的 GA4 事件代碼為例，2026-11-12 截圖；截圖時沒有修改或儲存。*

6. 選好後會出現「**新增必要的同意**」（+ Add required consent），點它，輸入或選擇 `analytics_storage`。
   - 一個字一個字對：全小寫、中間是底線、`analytics` 有 s。
7. 按右上角「**儲存**」（Save）。
8. **Google 代碼不要動**：不加額外同意，保留內建檢查。

**練習 `comparison_open` 的同學**：課堂示範是對 `comparison_open` 事件代碼做一模一樣的設定，步驟相同。

### 5.2（選做）打開同意總覽

1. 左側「**管理**」（Admin）→「**容器設定**」（Container Settings）。
2. 在其他設定（Additional Settings）勾選「**啟用同意總覽**」（Enable consent overview），儲存。
3. 回到「代碼」清單，上方會多一個同意總覽的圖示（盾牌形狀），點開可以集中看每支代碼的同意設定。【待實機確認】
4. 確認 `line_join` 出現在「已設定同意」那一側，並看到它需要 `analytics_storage`。

### 5.3 重新開啟預覽

改完設定一定要**重新按「預覽」**（Preview），舊的預覽視窗不會套用新設定。【待實機確認】

1. 工作區右上角按「**預覽**」。
2. 在 Tag Assistant 輸入練習頁網址（記得後面有 `?gtm=GTM-你的ID`），按連結（Connect）。
3. 練習頁開好後，頁首應顯示「GTM 練習容器：GTM-（你的 ID）……」。如果顯示「尚未載入 GTM」，回去檢查網址：`GTM-` 後面要接 4～10 個大寫英文或數字，不能是範例的 X。

**本單元只用預覽，不需要發布（提交）容器。**

### 5.4 三種情境，各做一次

**每種情境開始前都要重新整理練習頁。** 重新整理會讓四項回到預設拒絕，這樣三種情境才不會互相干擾。

| 情境 | 你要做的事 |
|---|---|
| A 未選擇 | 重新整理 → **不要按**橫幅任何按鈕 → 按「推送加入 LINE 事件」一次 → 到 Tag Assistant 看結果、截圖 |
| B 接受全部 | 重新整理 → 按「接受全部」→ 按「推送加入 LINE 事件」一次 → 看結果、截圖 |
| C 只保留必要 | 重新整理 → 按「只保留必要」→ 按「推送加入 LINE 事件」一次 → 看結果、截圖 |

> 小提醒：情境 A 做完，**直接重新整理**再進情境 B。不要在 A 的頁面上補按「接受全部」，否則同一頁面裡混了兩種狀態，紀錄會看不清楚。

### 5.5 在 Tag Assistant 看哪裡

每個情境看三個地方：

1. **同意狀態**：左側事件清單裡，名稱含「**Consent**」的事件就是同意的預設或更新。
   - 最早那筆 Consent → 點開看「API 呼叫」（API Call），四項應該都是 `denied`。這是**預設**。
   - 情境 B、C 會多一筆較晚的 Consent → 那是**更新**。
   - 另一個看法：點開任一 Google 代碼，在輸出（Output）區選「**Consent**」分頁，「**On-page Default**」欄是預設、「**On-page Update**」欄是更新。
   - 如果 Consent 分頁整個是空的，表示頁面沒有實作同意模式（檢查網址或預覽有沒有連上）。
2. **事件代碼是否觸發**：左側點 `line_join` 那一筆事件 → 看「**代碼**」（Tags）分頁：
   - 出現在「**已觸發的代碼**」（Tags Fired）→ 有觸發。
   - 出現在「**未觸發的代碼**」（Tags Not Fired）→ 沒觸發。點開可以看原因，應該跟同意有關。
3. **Google 代碼狀態**：點較早的事件（頁面載入時那幾筆），看 Google 代碼是否在「已觸發的代碼」。

**預期結果：**

| 情境 | `analytics_storage` | `line_join` 事件代碼 | Google 代碼 |
|---|---|---|---|
| A 未選擇 | 預設 `denied`，沒有更新 | **不觸發** | 已觸發（依內建檢查，拒絕時不使用 Cookie） |
| B 接受全部 | 預設 `denied` → 更新 `granted` | **觸發** | 已觸發 |
| C 只保留必要 | 預設 `denied` → 更新仍是 `denied` | **不觸發** | 已觸發（同 A） |

情境 B 觸發後，也可以到 GA4 **DebugView** 看 `line_join` 有沒有收到；A、C 不應出現新的 `line_join`。

### 5.6 停止條件與回復位置

出現下面任一狀況，**這份設定就不能發布**，要回去修：

| 停止條件 | 代表什麼 | 回復位置 |
|---|---|---|
| 情境 A 或 C（拒絕）時，`line_join` 事件代碼**仍然觸發** | 額外同意沒設好（沒選「需要額外同意」、項目打錯字、或忘了儲存／重開預覽） | `line_join` 事件代碼 → 進階設定 → **同意設定** |
| 同意預設**晚於**代碼載入（Consent 事件出現在代碼觸發之後，或 Tag Assistant 提示代碼在預設設定前就讀了同意狀態） | 預設送得太晚 | 真實網站：把設定預設的代碼掛到 **Consent Initialization** 觸發條件；練習頁本身已先送預設，若在練習頁看到這狀況，先確認網址正確、重開預覽，仍然發生就截圖請講師看 |

修完 → 儲存 → 重新按「預覽」→ 三種情境**全部重測**，不是只重測出錯那一個。

## 7. Meta 像素、轉換 API 與去重

### 7.1 Meta 像素是什麼

**Meta 像素（Meta Pixel）**：放在網站上的一段 JavaScript，用來做三件事：**量測轉換**、**最佳化廣告投放**、**建立自訂受眾**（例如「預約過試握的人」）。第八模組 8-4 做 Meta 廣告時，網站來源的自訂受眾就靠它或轉換 API。

### 7.2 標準事件

Meta 預先定義了一批事件名稱，叫**標準事件**。用標準名稱，Meta 才看得懂這是什麼行為。本單元要認得這八個：

| 標準事件 | Meta 說明（意譯） | 山徑咖啡可能對應 |
|---|---|---|
| `ViewContent` | 瀏覽你在意的頁面（商品頁、到達頁） | 看溪線 700 商品頁 |
| `Search` | 進行搜尋 | 站內搜尋「手沖壺」 |
| `AddToCart` | 商品加入購物車 | 溪線 700 加入購物車 |
| `InitiateCheckout` | 進入結帳流程（尚未完成） | 按「前往結帳」 |
| `Purchase` | 完成購買或結帳流程；**必填 `value` 與 `currency`** | 溪線 700 付款成功 |
| `Lead` | 完成註冊 | 留下資料索取型錄 |
| `Contact` | 透過電話、簡訊、Email、聊天等聯絡商家 | 按「LINE 詢問」 |
| `Schedule` | 預約到你的門市 | **完成 20 分鐘試握預約** |

不在清單裡的行為，可以用**自訂事件**。但能對到標準事件就先用標準事件。

**名稱一個字都不能錯**：`Schedule` 開頭大寫 S，不是 `schedule`，也不是 GA4 的 `booking_complete`。兩邊是**兩套名稱**，你的去重卡就是把它們對起來的那張表。

### 7.3 透過 GTM 安裝像素的五個原則

這堂不實際安裝，但去重卡和企劃書要寫得出原則：

1. **先確認**：資料來源（哪個網站、哪個事件）、**像素 ID**、誰有權限。沒有權限就停在規格。
2. **優先用官方整合或審核過的範本**（例如 GTM 社群範本庫中經過檢查的），少用自己貼的程式碼。
3. **自訂 HTML 代碼要先經審查**：自訂 HTML 可以執行任何程式，貼之前要有人看過內容與來源。
4. **事件由「成功狀態」觸發**：預約完成、付款成功才送；不是按下按鈕就送。並在 Meta 事件管理工具的「**測試事件**」（Test Events）核對有沒有收到（畫面以實際為準）。
5. **Meta Ads Data Advisor 只是輔助**：這是 Chrome 擴充功能，原名 **Meta Pixel Helper**，Meta 已改名。它的圖示亮了，只代表「頁面上有像素在跑」，**不代表參數正確、也不代表去重正確**。

### 7.4 轉換 API：伺服器那一頭

**轉換 API（Conversions API）**：由**伺服器**把事件直接送給 Meta，不經過使用者的瀏覽器。瀏覽器可能被擋廣告工具擋、網路斷掉，伺服器端比較穩，所以很多網站兩端都送。

問題來了：同一筆預約，像素送一次、伺服器送一次 → 如果 Meta 不知道是同一筆，就會算成**兩筆預約**，成效被灌水。

### 7.5 去重的規則

**去重（deduplication）**：讓 Meta 認出「這兩筆是同一件事」，只算一次。Meta 建議的做法要**兩組都對上**：

| 要相等的東西 | 像素（瀏覽器端） | 轉換 API（伺服器端） |
|---|---|---|
| 事件名稱 | 事件名稱，例如 `Schedule` | `event_name`，例如 `"Schedule"` |
| 事件 ID | `eventID` | `event_id` |

- 兩端送到**同一個像素 ID**，且在第一筆送達後 **48 小時內**，Meta 會捨棄後到的重複事件。
- **`eventID` 和 `event_id` 是同一個值的兩種寫法**：瀏覽器端 JavaScript 習慣「駝峰」（`eventID`，大寫 ID、沒有底線），伺服器端習慣「底線」（`event_id`，全小寫）。欄位名不同，**裡面填的值必須一模一樣**。

像素端長這樣（`eventID` 放在第四個位置，跟事件參數分開）：

```js
fbq('track', 'Schedule', {}, {eventID: 'BK-20261112-0042'});
```

伺服器端送的事件裡則有：

```text
event_name: "Schedule"
event_id:   "BK-20261112-0042"
```

### 7.6 唯一 ID 從哪裡來：最重要的一條

**唯一 ID 要由「預約系統」或「訂單系統」產生，兩端共用同一個；不能讓像素和伺服器各自產生一個。**

為什麼？如果瀏覽器自己亂數產生 `A123`、伺服器又自己產生 `B456`，兩個 ID 不同，Meta 會當成兩件事，去重完全失效。

只有「真正完成這筆預約的系統」知道「這是第幾號預約」，它產生的編號（預約編號、訂單編號）才能同時交給頁面上的像素和伺服器。

**練習頁沒有預約編號**，所以在去重卡上這一格要寫：「預約系統應產生預約編號；**待系統提供，尚未實際驗證**」。這不是偷懶，是正確的判斷。


## 8. 實作二：去重卡

### 8.1 先看示範卡：山徑咖啡溪線 700 線上購買

練習頁沒有交易，所以這張示範**只做規格**。順便看 GA4 電商事件的規則，因為 `purchase` 兩邊都要送。

**GA4 電商事件的規則（GTM 版）：**

- 五個常用電商事件：`view_item`（看商品）、`add_to_cart`（加入購物車）、`begin_checkout`（開始結帳）、`purchase`（購買）、`refund`（退款）。都要從「**成功狀態**」送出。
- `purchase` 和 `refund` **必須有 `transaction_id`**（交易編號）。
- 有送 `value`（金額）就要一起送 `currency`（幣別）。
- 用資料層推送新的電商資料前，先推一次 `ecommerce: null`，清掉上一筆殘留的值。
- **同一筆交易只送一次**（例如使用者重新整理感謝頁，不能再送一次 `purchase`）。

| 欄位 | 示範：溪線 700 線上購買 |
|---|---|
| 網站行為與成功時機 | 顧客買溪線 700；**訂單完成頁確認交易成功時**（不是按「付款」按鈕時） |
| GA4 事件 | `purchase`（推送前先送 `ecommerce: null`） |
| Meta 標準事件 | `Purchase` |
| 唯一 ID 來源 | **訂單系統**產生的訂單編號；GA4 `transaction_id`、像素 `eventID`、轉換 API `event_id` 三處共用同一個值 |
| 像素欄位 | `fbq('track', 'Purchase', {value: 2380, currency: 'TWD'}, {eventID: 訂單編號})` |
| 轉換 API 欄位 | `event_name: "Purchase"`、`event_id: 訂單編號`、`event_time`、`action_source: "website"`、`event_source_url`、`user_data`、`custom_data`（`value`、`currency`） |

| 時間 | 誰 | 講什麼 |
|---|---|---|
| 0:00–0:30 | 組員 1 | 我們的產品與這次測的事件；**註明「使用山徑咖啡練習頁，練習環境」** |
| 0:30–2:30 | 組員 2、3 | 沿著那條線走一次，每格指著截圖 |
| 2:30–3:30 | 組員 4 | 反例與「只保留必要」的結果 |
| 3:30–4:00 | 組員 1 | 還沒驗證的部分（例如 Meta、唯一 ID）與下一步 |

### 10.4 回饋

講師依「**事件名稱、觸發條件、證據一致，同意情境有記錄**」講評，不安排學員互評。

**（選用）實測後請 AI 找缺口。** 把你們的追蹤規格與驗證紀錄**全文**貼給 ChatGPT、Claude 或 Gemini（任一），用這段提示：

```
以下是我們小組的追蹤規格與驗證紀錄。請只使用我提供的內容，
依「事件名稱、觸發條件、變數與參數、正反例、預覽證據」五項判準，
列出最多三個不一致的地方或待補的證據，並指出出現在哪一行。
不要推測平台是否會通過，也不要補寫我沒提供的內容。

（貼上規格與紀錄全文）
```

AI 只幫你找缺口；**平台是否通過，由你們依實際畫面判定。**

### 10.5 放進企劃書「成效指標與追蹤」第 3 頁

第 5 段「成效指標與追蹤」：

| 頁 | 內容 | 本單元動到嗎 |
|---|---|---|
| 第 1 頁 | 三個代表旅程的事件（標出關鍵事件，附一個待驗證假設） | 不動 |
| 第 2 頁 | UTM 命名表 | 不動 |
| 第 3 頁 | **事件、觸發條件、參數與驗證證據** | **本單元更新** |

第 3 頁要放：

- 巷口晨光三個事件的規格；
- 練習頁的實測路徑與證據截圖（標註練習環境）；
- 同意情境結果（三種情境，一句話＋截圖編號即可）；
- 規劃付費廣告的組：另附去重卡。


## 11. 面試時怎麼說「我做過什麼」

你擔心去重卡只是紙上作業。分清楚「做過」和「規格」，反而是加分：

> 「我在 GTM 幫 GA4 事件代碼設了額外同意 `analytics_storage`，用 Tag Assistant 測三種同意情境，確認使用者拒絕時事件代碼不觸發、同意後才觸發，每個情境都有截圖紀錄。
> Meta 那邊我沒有實際帳號，所以我寫的是去重規格：把 GA4 的 `booking_complete` 對到 Meta 的 `Schedule`，像素的 `eventID` 和轉換 API 的 `event_id` 要用預約系統產生的同一個編號。卡片上我標了哪些已驗證、哪些還沒，等拿到預約系統就能照卡驗證。」

**實際做過的**：同意設定、三情境測試、資料層事件與 GA4 收件、去重規格判斷。
**規格未驗證的**：Meta 像素安裝、轉換 API、Meta 測試事件裡的去重結果。


## 12. 卡住時查這裡

| 狀況 | 可能原因 | 怎麼做 |
|---|---|---|
| 找不到「同意聲明設定」 | 沒展開「進階設定」 | 代碼設定最下方 → 進階設定 → 同意聲明設定 |
| 改了設定，結果沒變 | 沒儲存，或沒重新按「預覽」【待實機確認】 | 儲存 → 工作區重按「預覽」→ 重新連練習頁 |
| 拒絕時事件代碼還是觸發 | 選成「不需要額外同意」或「未設定」；`analytics_storage` 打錯 | 回同意設定逐字檢查 → 重開預覽 → 三情境全部重測 |
| 接受全部後事件代碼還是不觸發 | 先按了 LINE 才按接受；或觸發條件本身有問題 | 照順序：重新整理 → 接受全部 → 再按 LINE；並確認 7-3 的觸發條件仍正常 |
| Tag Assistant 看不到 Consent 事件 | 練習頁沒載入你的容器 | 看頁首是否顯示你的容器 ID；檢查 `?gtm=` 網址 |
| 頁面事件監看區看不到同意更新 | 正常，練習頁本來就不列 | 改到 Tag Assistant 看 |
| `comparison_open` 沒出現 | 比較表原本就展開 | 先收合再展開，或重新整理 |
| 重新整理後預覽斷線 | Tag Assistant 連線中斷 | 回 GTM 重按「預覽」 |
| 組員 5～6 人，有人沒分到上台段落 | 四分鐘分配表以 4 人排 | 多的組員分擔沿線講解的其中幾格，或接手「還沒驗證的部分與下一步」 |
