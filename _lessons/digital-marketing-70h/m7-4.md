# 同意模式、Meta 像素與事件去重
讓量測依使用者選擇運作，也讓同一筆轉換只被平台計算一次。
學習目標：能說明同意模式四種主要同意項目各控制什麼、基本與進階模式的差別，以及同意模式不能取代隱私政策與法律判斷｜能用練習頁與 Tag Assistant 測試三種同意情境，記錄預設、更新與代碼行為｜能說明 Meta 像素標準事件，以及像素與轉換 API 同送時怎麼去重，並寫出一張去重卡

## 量測要同時回答可不可以送與是不是同一筆

事件送出後，要判斷使用者是否同意分析或廣告用途，以及兩端是否為同一筆。本節留下同意與去重紀錄。

## 同意模式把使用者選擇交給 Google 代碼

同意模式（consent mode）把使用者同意狀態傳給 Google 代碼，讓代碼調整儲存與傳送。[Google 同意模式概念](https://developers.google.com/tag-platform/security/concepts/consent-mode)（2026-11 查證）。四種主要項目如下：

- `ad_storage`：廣告用途的儲存，例如 Cookie。
- `analytics_storage`：分析用途的儲存，例如造訪時間長度。
- `ad_user_data`：是否把使用者資料送給 Google 作線上廣告用途。
- `ad_personalization`：是否用於個人化廣告，例如再行銷。

`functionality_storage`、`personalization_storage`、`security_storage` 另管功能、個人化與安全用途。基本模式在回應前不載入 Google 代碼，拒絕便不送資料；進階模式先載入並預設拒絕，拒絕時送無 Cookie 訊號，同意後送完整資料。模式由網站政策決定，不是技術預設。

進階模式下，GA4 可能用行為建模補估拒絕者行為，但須同時達到：拒絕 `analytics_storage` 的事件每天至少 1,000 筆、連續 7 天；過去 28 天中至少 7 天，每天至少 1,000 位同意分析儲存者。小流量網站多半達不到。[行為建模資格](https://support.google.com/analytics/answer/11161109)（2026-11 查證）。

順序是「同意預設 → 載入代碼 → 使用者選擇 → 同意更新」。Consent Initialization 最早觸發；Google 代碼有內建同意檢查，其他代碼可設額外同意檢查，指定項目全為同意才執行；「同意總覽」可集中檢查。[GTM 同意設定](https://support.google.com/tagmanager/answer/10718549)（2026-11 查證）。同意模式不能取代同意管理工具（CMP）、隱私政策或法律判斷；Google 政策適用歐洲經濟區、英國與瑞士，台灣義務由組織依法確認。[政策說明](https://support.google.com/google-ads/answer/16724512)（2026-11 查證）。

## Meta 事件與共用唯一 ID 避免重複計算

Meta 像素（Meta Pixel）是網站 JavaScript，用來量測轉換、最佳化廣告及建立自訂受眾。[Meta 像素入門](https://developers.facebook.com/documentation/meta-pixel/get-started)（2026-11 查證）。標準事件有 `ViewContent` 瀏覽頁、`Lead` 完成註冊、`Schedule` 預約到門市、`Contact` 聯絡、`AddToCart` 加入購物車、`InitiateCheckout` 開始結帳、`Purchase` 購買且帶 `value` 與 `currency`、`Search` 站內搜尋；其餘可自訂。[標準事件](https://developers.facebook.com/docs/meta-pixel/reference)（2026-11 查證）。

透過 GTM 安裝時，先確認資料來源、像素 ID 與權限，優先用官方整合或審核範本；自訂 HTML 先經審查。事件由成功狀態觸發，並在「測試事件」核對，畫面以實際為準。Meta Ads Data Advisor（原名 Meta Pixel Helper）只作輔助，圖示正常不代表參數與去重正確。

轉換 API（Conversions API）由伺服器把事件送給 Meta。兩端同送時，去重（deduplication）要求像素事件名稱等於 `event_name`、像素 `eventID` 等於 `event_id`；Meta 捨棄 48 小時內的重複事件。唯一 ID 由訂單或預約系統產生並共用，不能各生一個。[Meta 去重](https://developers.facebook.com/docs/marketing-api/conversions-api/deduplicate-pixel-and-server-events)（2026-11 查證）。

GA4 電商事件從成功狀態送出：`view_item` 瀏覽商品、`add_to_cart` 加入購物車、`begin_checkout` 進入結帳、`purchase` 交易成功、`refund` 退款完成；後兩者要有 `transaction_id`，送 `value` 時要有 `currency`。新電商資料前先送 `ecommerce: null` 清除舊值；同一交易只送一次。[GA4 電商量測](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce?client_type=gtm)（2026-11 查證）。

延伸理解即可：Google 代碼閘道（Google tag gateway for advertisers）用自有網域載入代碼，可透過 CDN（分散內容的網路）、負載平衡器（分配請求的設備）或網頁伺服器設定；伺服器端代碼（server-side tagging）在自有伺服器執行容器再轉送平台。兩者需要工程與主機，不取代同意設定。[代碼閘道](https://developers.google.com/tag-platform/tag-manager/gateway)、[伺服器端代碼](https://developers.google.com/tag-platform/tag-manager/server-side/intro)（2026-11 查證）。

## 山徑咖啡示範：測試比較表並設計購買去重

示範使用[預約練習頁](assets/practice/booking-practice.html)、[量測練習包](assets/datasets/measurement-practice-kit.md)與[山徑咖啡品牌包](assets/datasets/simulated-brand-pack.md)：前者測同意，品牌包示範去重；練習頁沒有交易。

替 `comparison_open` 設定額外同意 `analytics_storage` 並預覽。每種情境前重新整理，記錄「情境｜操作順序｜四項狀態（預設／更新）｜事件代碼是否觸發｜Google 代碼狀態｜截圖編號｜停止條件是否觸及｜回復位置」。

- 未選擇：直接展開；四項預設為 `denied`、無更新；事件代碼不觸發，Google 代碼依內建檢查運作。
- 接受全部：按橫幅再展開；四項由 `denied` 更新為 `granted`；事件代碼觸發。
- 只保留必要：按按鈕再展開；四項更新後仍為 `denied`；事件代碼不觸發。

練習頁在預設拒絕後仍載入 GTM，屬進階模式。若拒絕時事件代碼仍觸發，或預設晚於代碼載入，就停止發布；回到事件代碼「同意設定」或 Consent Initialization 修正。

去重卡欄位是「網站行為與成功時機｜GA4 事件｜Meta 標準事件｜唯一 ID 來源｜像素欄位｜轉換 API 欄位｜必要參數｜重複測試｜失敗反例｜驗證位置｜目前狀態」。溪線 700 交易成功時，GA4 用 `purchase`、Meta 用 `Purchase`；訂單系統產生共用 ID，像素送 `eventID`，API 送相同 `event_id`，必要參數是 `transaction_id`、`value=2380`、`currency=TWD`。重新整理不重送，付款失敗不送；到 GA4 DebugView 與 Meta「測試事件」驗證，目前寫「規格已定，尚未實際驗證」。

```text
dataLayer.push({ ecommerce: null });
dataLayer.push({ event: 'purchase', ecommerce: {
  transaction_id: '[訂單系統產生的唯一編號]', value: 2380, currency: 'TWD',
  items: [{ item_name: '溪線 700', price: 2380, quantity: 1 }]
} });
```

## 用加入 LINE 與完成預約建立自己的紀錄

用 `line_join` 事件代碼要求額外同意 `analytics_storage`，在三種情境各按一次加入 LINE，填相同八欄。由 Tag Assistant 判定；觸及停止條件時回到同意設定修正。

把 `booking_complete` 對應 Meta `Schedule`，用相同十一欄寫去重卡。練習頁沒有預約編號，要判斷由哪個系統產生唯一 ID；缺少時寫「待系統提供，尚未實際驗證」。重複測試涵蓋重新整理，反例涵蓋缺必填欄位。

> 參考方向：接受全部時，額外要求 `analytics_storage` 的 `line_join` 事件代碼才應觸發；另外兩種情境應保留未觸發證據。預約去重卡應把成功送出、共用 ID、`Schedule`／`event_name=Schedule`、`eventID`／`event_id` 與待實測狀態連成同一條規格。

## 模組作業：一個點擊的旅程

作業把量測決策表、追蹤規格與 GA4 收件整合成事件路徑。每組 4～6 人，沿用原組。

### 個人準備

用約 10 分鐘分配組內三個事件；人數多於三人時可共用。補齊操作、網站訊號、觸發條件、變數、事件名稱、參數、正反例與可用權限。缺席者下次上課前補進簡報附錄，註明姓名與日期。

### 小組討論

用約 25 分鐘實測一個事件。有網站者用測試環境；其餘在練習頁網址加 `?gtm=` 與容器 ID。記錄操作、資料層事件、代碼、參數、GA4 收件、一個反例及「只保留必要」結果。

### 上台分享

依組別編號或講師抽籤，每組 4 分鐘、換場 1 分鐘。展示「使用者操作 → 網站訊號 → GTM 觸發條件 → GA4 收件 → 畫面證據」；使用練習頁者註明練習環境。

### 回饋

講師依「事件名稱、觸發條件、證據一致，同意情境有記錄」講評，不安排學員互評。實測後可交給 AI 依五項判準指出最多三個缺口；平台是否通過由小組依畫面判定。

```text
檢查這份追蹤規格與驗證紀錄。
依事件名稱、觸發條件、變數與參數、正反例、預覽證據五項判準，列出最多三個不一致處與待補證據；只使用提供內容。

[貼上追蹤規格與驗證紀錄全文]
```

### 放進企劃書

更新企劃書「成效指標與追蹤」第 3 頁：放三個事件規格、實測路徑與證據、同意情境結果；規劃付費廣告者另附去重卡。格式依[企劃書指南](assets/datasets/group-project-guide.md)整理。
