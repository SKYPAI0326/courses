# Learner Task Contract

> 本檔沿用舊檔名 `learner-action-contract.md`，是課程系統唯一的學員路徑來源。它把「為什麼做」與「如何做、如何確認」放在同一個最小任務模型；其他 skill 只負責產出、呈現或驗證，不另造同義契約。

## Core learner task

每個單元都必須讓學員從一個與課型及學習目標相符、可理解且可取得輸入的問題，走到一個可觀察的成果，並知道成果的用途與驗收方式。工具或整合課可使用真實工作問題與下游使用者；概念、數學、語言或設計課可使用合理情境、判斷任務、推導或作品，不得為了填欄位虛構公司與交接者。這個任務模型先於頁面、卡片、步驟標籤與機器掃描。

### 生成前先凍結的契約

正式交接前逐項確認下表。設計期間可保存明示缺口的草稿；缺口阻擋受影響的產製，不阻擋素材製作或無相依工作。空白、placeholder、只有抽象名詞或「之後提供」都算 `BLOCKED`；不以文案、標籤或講師口頭補充代替。

| 欄位 | 必須說清楚的內容 |
|---|---|
| 學習者與情境 | 學員現在扮演誰，或處於哪個學科／創作情境，面對什麼任務 |
| 問題與後果 | 現在卡在哪裡；若不處理，理解、操作或作品會受到什麼影響 |
| 起始材料 | 學員能直接開啟、複製或輸入的檔案、資料、畫面或值；取得方式與備援 |
| 目標完成物 | 本節留下的檔案、畫面、設定、決策、測試紀錄或交付物；名稱、位置、格式或版本 |
| 成果用途與後續使用 | 誰會在什麼地方使用或更新成果；若沒有下游，寫明學員如何自行驗收與何時可再使用 |
| 第一個動作 | 學員拿著哪份材料，做哪個不需猜測的動作 |
| 第一個可觀察結果 | 動作完成後應看到的畫面、值、檔案或狀態；不符合時回到哪裡 |
| 失敗時的回復位置 | 現象、原因、回修位置、重跑起點、資料是否清除、安全停止狀態 |

`Concept` 可把完成物寫成決策矩陣、分類結果或短 rationale；若沒有工具錯誤，回復欄寫 `N/A — 概念判斷錯誤時回到哪個例子或規則`。`Integration / Capstone` 必須把起始材料與用途對應到前課能力、實際需要的上游材料、驗收與修訂路徑。

## 教學因果鏈

契約填妥後，教案與講義沿用同一組事實，依課型調整篇幅，不改變因果順序：

```text
學習問題與用途
→ 起始材料
→ 完成物預覽與用途
→ 本次需要的概念與判斷
→ 一筆完整示範（輸入／處理／中間結果／完成品）
→ 第一個動作與可觀察結果
→ 同步練習或判斷
→ 適用時的條件變化或轉移練習
→ 驗收、修復與下一次使用
```

每次轉段都要能回答：「剛才完成或看見了什麼，所以現在要做什麼，目的是什麼？」`Demo`、`Together`、`Solo`、`Check`、`Stage` 只能作為導航，不能承擔這段因果。

## 各角色的唯一責任

| 角色 | 只負責的動作 | 失敗時交回 |
|---|---|---|
| `course-designer` | 凍結契約，將契約事實寫入教案，補足教學與操作證據 | 上游大綱、素材或環境 |
| `build-course-page` | 從教案呈現契約；不改寫或發明技術事實 | `course-designer` |
| `course-reviewer` | 引用教案／HTML 的實際位置，判斷契約是否可讀、可跟做 | 產出該角色 |
| `course-validator` | 用實際 learner-facing 頁面做冷讀、平台重跑與證據驗證 | 對應上游角色 |

## 最小驗證

### 30 秒入口測試

遮住教師筆記、Blueprint、作者狀態與角色標籤，只看學員會先看到的內容。記錄學員所需時間與提示；30 秒是快速診斷的參考，並非所有學科的硬性期限。核對：

1. 我正在處理什麼情境或學科問題？
2. 這個問題為什麼值得處理？
3. 我手上的第一份材料是什麼，怎麼取得？
4. 我要留下什麼成果，名稱、位置或格式是什麼？
5. 這個成果如何驗收，何時可以再次使用？
6. 我第一步要做什麼，做完應看到什麼？沒看到要回哪裡？

這是核心契約的快速驗證，不是另一份 checklist。必要起點需要猜測或講師補充時，回到正文或依賴修正；本測試不取代完整跟做。

### 最低放行語義

| 狀態 | 只代表什麼 | 不能代表什麼 |
|---|---|---|
| `MACHINE_CHECKED` | 結構、連結或確定性掃描通過 | 學員看得懂、平台可用或可授課 |
| `MACHINE_READY_PENDING_HUMAN` | 機器階段所需證據已整理，學員冷讀、平台重跑或人工判斷仍待完成 | `LEARNER_READ`、`PLATFORM_VERIFIED` 或 `HUMAN_READY` |
| `LEARNER_READ` | 冷讀者能依頁面與材料開始、判斷、修復並完成 | 所有平台方案與真人授課已驗證 |
| `PLATFORM_VERIFIED` | 指定帳號、方案與工具路徑已實際重跑 | 學員敘事或整門課已通過 |
| `HUMAN_READY` | 所有適用的機器、學員、平台與人工證據均通過 | 之後不需重新驗證 |

核心內容或素材缺失為 `BLOCKED`；只缺真人證據為 `MACHINE_READY_PENDING_HUMAN`／`PENDING_HUMAN`。可以明確交付已完成的設計、建置或機器檢查，不能把這些階段成果稱為已教會或已可授課。`LEARNER_READ` 要有真人完整跟做，AI 與作者模擬只列各自證據；`HUMAN_READY` 還需適用的理解、遷移、連續課、平台及人工判斷。

## 反補丁與反膨脹規則

- 新問題先判斷是契約缺欄位、產出遺失、呈現遺失，還是驗證遺失；只能修正唯一責任層。
- 若新條文與本檔已有欄位或流程同義，合併或改寫原條文，不新增第二套名稱。
- 每項規則都要能指出負責角色、輸入、可觀察證據與失敗回復；不能改變決策的敘述刪除。

## 正式正文與版本交接

每單元一份 `_lessons/{slug}/{unit_id}.md`；正式正文放在 `<!-- learner-content:start -->` 與 `<!-- learner-content:end -->` 之間。內部契約、能力矩陣、素材製作狀態與教師備註放在標記之外。完整示範、練習及答案必須在正文內，不能散落於教師區。單獨使用 handout-designer 時亦指定同一份正式來源。

既有教案可先用明確小節範圍指定來源並完成內容審查；改製時整理成標記區，不因未套新標記而刪除有用內容。正式正文由 designer／handout-designer 負責，reviewer 先做內容審查，再由 builder 轉製。缺素材由總籌指定製作者、輸入、成品路徑與驗證，不在角色間無限退件。

內容審查須定位來源版本、正文範圍、逐項證據、問題與結論；HTML 完成後另核對保真。機器格式採 course-validator 的 evidence-format.md；同一份 evidence.json 供 builder、總籌、導覽與驗證引用。更改教材或素材後，舊 hash 的相關證據失效；排版變更可附影響分析並重新核對新版本，不直接沿用 PASS。
