## 1. 系統定位

這套系統解決的是「課程內容由單流程一次寫到底 → 無品質閘門 → 不成熟堆積」的問題。

透過**多角色分工 + 依課程實際範圍的檢核點 + 結構化交接**，讓未來新課與既有課改版都有可重複的 SOP，跨課程一致性可控，單次產出的品質可驗證。

系統設計跑過三類型試飛驗證：skill-operation（Make 定時抓網頁）、concept（SEO 搜尋意圖）、programming（Python 讀 Sheets）。三支講義路徑見文末「pilot 實例索引」。

## 3. 正式工作流與交接

| 階段 | 主責與產物 | 相依與驗證 |
|---|---|---|
| G1 大綱 | PM：起點診斷、補救、能力進展與單元矩陣 | 核對已有需求；未知且影響設計的資訊才詢問 |
| G2 正文與內容審查 | designer／handout：唯一正式正文；指定製作者完成素材；reviewer 記 content | 逐項核對解釋、完整示範、練習回饋、能力增量、句意與順序，綁來源版本 |
| G3 HTML 與保真 | builder／lesson-writer：先代表頁，再依實測結果擴大；reviewer 記 fidelity | 內容審查先於 HTML；保留核心表格、推理、答案及素材；跑技術檢查與適用風險審查 |
| G4 教學與技術驗收 | validator 整理實際證據；ops 執行技術檢查 | 入口、完整跟做、理解遷移、連續課及適用平台分開記錄；真人待驗可交付已完成階段 |
| G4.5 註冊 | register：密碼、登錄、COURSES、入口、gate | 可在授權內準備試作註冊，不代表教學放行 |
| G5 發布就緒 | 總籌合併正式狀態與技術結果 | 發布按當次授權；技術已備妥不能稱學員已學會 |

Part 與單元數依能力進展決定。G2／G3 按適用批次重複，G4 可先跑代表性範圍；不能以單一頁結果替未測分支放行。使用 `_gates-template.md` 記錄並引用 evidence.json，不要求使用者重答已知定位，也不能替真人填寫驗收結果。

素材缺失時，總籌須指定製作者（可為當前執行者）、輸入、成品路徑及測試；設計與素材製作可以相互修訂，核心缺件未解不能交給 HTML 現編。

`course-run` 執行本表。角色分工不等於代理派遣；預設單一執行者。外部模型、付費服務、公開發布依當次授權，沒有外部工具仍可完成本機設計、建置與驗證。

## 7. 已知系統盲點與應對

### 盲點 1：檢核員檢不到視覺品質

HTML 結構合規（all BLOCKER/MAJOR pass）**不等於**排版好看。Pilot A 第一版全部通過 reviewer，但人眼看是「排版亂七八糟」。

**應對**：G3-pilot 人眼驗收是**必要關卡**，不能靠 reviewer 替代。未來若要自動化，需 Chrome MCP + 截圖 + vision 模型（Phase 3 議題）。

### 盲點 2：Subagent 無法使用 `/` slash command

Agent tool 派遣的 subagent context 獨立，**不能叫 `/build-course-page`**。解法：subagent 的 prompt 必須指示它「讀 `~/.claude/skills/build-course-page/SKILL.md` 並自行執行 Step D0.5-D5」。

### 盲點 3：試跑包定義在各課型有差異

- skill-operation 的「試跑包」= 可匯入就能跑的 workflow JSON
- concept 的「試跑包」= 能讓學員模擬跑一次完整流程的題庫 + 策略範本
- programming 的「試跑包」= 複製到本機就能跑的程式碼包

PM/設計師在不同類型下產出的試跑包規格需按上面三種範本填，不能混用。

### 盲點 4：Pilot A 第一版產出品質不良的根因

第一版用了 5 種彩色背景 box 堆疊（concepts-strip/case-block/assets-box/quiz-block/hands-on-box）造成視覺噪訊、11 階 font-size、grid auto-fit 產孤兒。根治方式：取法既有 36h 課程的 section-driven 設計語彙（見 §5）。
