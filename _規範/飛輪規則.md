# 飛輪規則（錯誤轉改進）

錯誤、學員卡關或課堂經驗發生時，先分流再動手。每一圈都要落在產出端實際會讀的地方；本檔只放分流、日誌用法與已機器化檢查的指標，不收原則。

---

## 分流

每次事故依序判斷，停在第一個符合的步驟：

1. **違反既有規範**（`_規範/learner-action-contract.md`、`_規範/course-content-substance.md`，或負責該成品的 skill、範本）→ 修正該實例，不新增條文。
2. **可由機器檢查** → 寫進 `docs/lint-page.py` 或 `docs/` 下的腳本，在下方「已機器化」留一行指標。
3. **只屬於某門課或某個工具**（軟體預設值、錯誤訊息對應、某課的試跑包做法）→ 把修正做進該課的講義或試跑包，並在知識庫日誌記一則經過；不寫成通用規範。
4. **跨課程都適用、既有規範沒有涵蓋** → 修改產出端會讀的地方：上述規範檔、負責的 skill、範本或範例；與既有內容同義時合併改寫，不另立新條。是否修改由使用者決定。

經驗與案例記在知識庫日誌 `~/Library/Mobile Documents/com~apple~CloudDocs/01-PROJECTS/知識庫/知識庫/日誌/`（一天一檔，每則寫情境／發生什麼／我的判斷），是使用者、Claude、Codex 的共同記憶。

- 設計或修改課程前，搜尋日誌中該課名稱或相近情境；引用時標出日期，並註明是使用者親寫的經驗，還是標「來源：互動」的 AI 整理。
- 課程任務結束時，列出本次可記的案例（一句話 + 建議落點：屬於上方分流哪一步、要改哪個檔），由使用者勾選；收下的追加到當天日誌，標「來源：互動」。這類條目的「我的判斷」留空待使用者填寫；AI 的看法寫在「發生什麼」並標「AI 建議」，不代寫使用者的判斷。要改規範、skill 或範本的，由使用者當場決定。

## 已機器化（只留指標）

- **密碼關卡**：`bash docs/audit-gates.sh`，偵測 placeholder hash、雙重 gate、K key 與 `inject_gate.py` 不一致、任何密碼都通過。新課上線前、`inject_gate.py` 改完都要跑。
- **push 後確認遠端收到**：`bash docs/safe-push.sh`，比對本地與遠端 HEAD，並檢查 open PR 是否含最後一個 commit；跑完才通知可以 merge。
- **複製按鈕定位**：機器檢查見 `docs/lint-page.py`；人類規範見 `_規範/design-tokens.md` §3。
- **學員頁不得出現的教案內部字眼**：機器檢查見 `docs/lint-page.py` 的 `check_internal_course_terms`（WARN）；正當用法見 `_規範/design-tokens.md`「教案內部字眼防火牆」。
