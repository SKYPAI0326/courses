# 講義改寫 SOP — PM 規格制

> 本檔是**既有課程講義整課改寫**的流程真相源：怎麼診斷、怎麼設計、誰寫規格、誰承作、怎麼檢查、怎麼上線。
> 視覺規則仍以 `design-tokens.md` 與 `docs/lint-page.py` 為準；「低原理、高操作」課程的內容組織見 `操作型講義.md`。
> 初版由 2026-11-01 `gen-ai-36h` 全課 28 頁改寫萃取（`courses/gen-ai-36h/_review/2026-11-01/`）。2026-11-05 依 `digital-marketing-70h` 退件修訂：初版的頁面骨架是為 AI 操作課寫的，被原樣套到原理型課程，52 頁通過所有檢查卻沒有教概念（`courses/digital-marketing-70h/_review/2026-11-05/diagnosis.md`）。這次修訂改的是機制，不是加規則。

## 0. 何時採用

### 適用
- 整門課或整個 Part 要重寫，不只是改措辭。
- 課程型態不限。同一門課的不同章節可以屬於不同教學型態，在步驟 1 逐一判定。

### 不適用
- 只修錯字、局部措辭：用文案流程即可。
- 沒有素材包的課：先補素材，否則承作模型會自行編造案例。
- 新開課：走 `課程製作團隊系統手冊.md`。

## 1. 機制總則

### 1.1 教學契約（唯一的全域原則）

每一頁都要讓「具備指定背景的學員」讀完答得出五題：

1. 這一頁要學什麼？
2. 為什麼現在要學？（接住前面哪個概念、解決什麼問題）
3. 每個新出現的概念、方法、名詞、任務是什麼？（第一次出現就說清楚，再拿來用）
4. 怎麼用？
5. 做完我得到什麼？

其他規則都從這五題推出來，或屬於某一種教學型態。發現新問題時，先看它違反契約的哪一題，不另立全域規則。

### 1.2 規則必附前提

規格書與本檔的每一條規則都寫出「為什麼有這條」與「什麼情況不適用」。套到新課程時，逐條檢查前提是否成立；前提不成立就不用，不是把規則改個說法照搬。

### 1.3 規則分層

課程目標（使用者指定）＞ 教學契約 ＞ 頁面設計卡 ＞ 形式規則（字數、標題區、限制語、提示詞寫法……）。兩條衝突時上層優先，規格書要明寫這個順序。形式規則容易用腳本檢查，承作者和檢查者都會偏向它；明寫順序是為了不讓量得到的規則蓋過量不到的目標。例：字數超過上限時，先精簡重複敘述與表格，不刪概念解說和示範中「為什麼這樣判斷」的理由（70h 退回時，承作為了壓字數，先刪的正是理由段）。

### 1.4 發現問題時：先找漏洞在哪一層，再修

1. 用同一個問題類型掃全部頁面，確認範圍。
2. 判斷是哪一層讓它過關：課程目標沒說到、教學契約沒涵蓋、設計卡設計錯、承作沒照卡，還是檢查沒攔到。
3. 在那一層修。和型態無關的失誤才寫進教學契約；和型態有關的，改該型態的講授順序（第 4 節）；只有個別頁面錯，就只修那一頁。
4. 檢查方式也要回頭看：檢查若只是對照我們自己的規格，規格的漏洞一定一起漏掉。

### 1.5 規則修剪

每完成一門課，回頭看本檔與該課規格書的規則：已經被教學契約或某一層檢查涵蓋的單獨規則，刪掉。規則清單只該在確認是新失誤類型時變長。

## 2. 角色分工

| 角色 | 由誰擔任 | 負責 |
|---|---|---|
| 產品經理（PM） | Claude（主 session） | 盤點、型態判定草案、設計卡、規格書、檢查、寫入與上線 |
| 承作者 | GPT-5.6 Sol（reasoning effort high），經 Codex 執行 | 依規格書與設計卡改寫學員正文，頁尾附自我檢查與事實核對 |
| 使用者 | 課程負責人 | 確認課程目標、教學型態、大綱、樣頁；平台方案取捨；合併 main 與跳過檢查等不可逆操作 |

承作模型只拿到簡短說明時產出不合格，拿到詳細規格書就合格，所以由 PM 寫規格。改寫時不套用 course-* 技能（部分條文會推高編號）。

## 3. 流程

| 步驟 | 做什麼 | 完成判準 |
|---|---|---|
| 0 盤點 | 跑代理指標（識別碼密度、限制語數…）；**逐頁寫保留清單**：現在這頁教了什麼、哪些定義、例子、方法是正確的 | 問題清單與保留清單都有；保留清單裡的內容，改寫後若刪掉要寫理由 |
| 1 型態判定 | 逐模組（必要時逐頁）判定教學型態（第 4 節），寫出學員要帶走的是理解、判斷、操作還是整合 | **使用者確認** |
| 2 大綱與設計卡 | 重寫模組名、單元標題；每頁一張設計卡（第 5 節） | **使用者確認**大綱方向後才改正式檔 |
| 3 落筆層 | 確認學員正文的唯一來源（例如 `_lessons/<slug>/`）與 HTML 怎麼產生；HTML 若曾被直接修改，記下會被覆蓋的部分 | 有一個明確的來源檔與轉製方式 |
| 4 規格書 | 依第 6 節寫；同型態的模組可以合寫 | 設計卡、素材、規則（附前提）、交付格式齊全 |
| 5 樣頁 | **每種型態先做一組樣頁**（例：第一個概念型模組、第一頁操作型單元），承作 → PM 檢查 → 學員視角試讀 → 使用者審 | 使用者審過；通過的頁面放進規格書當範例。審出的問題依 1.4 修到對應層再進下一步 |
| 6 批量承作 | 其餘頁面交給承作者；彼此獨立的模組可並行 | 每頁有學員正文＋自我檢查＋事實核對 |
| 7 PM 檢查 | 依第 7 節分層檢查 | 有明確問題才退回，**最多一次** |
| 8 寫入與轉製 | 寫進來源檔、更新 meta 與首頁卡片；轉製 HTML；lint 與改版前比對 | lint 不新增問題；只有預期的頁面被修改 |
| 9 commit | 逐檔 stage；搜尋索引只收本次頁面；改寫前的備份不進 repo | 只含本次檔案 |
| 10 上線 | 在乾淨的臨時 worktree 合併到 main，重建索引與 sitemap 後 push | push 檢查通過，Pages 部署完成 |

## 4. 教學型態與講授順序

講授順序由型態決定，不由本檔預設一種。下表是起點；新課程遇到不合的型態，在步驟 1 和使用者一起定義，再補進本表。

| 型態 | 學員要帶走 | 講授順序 | 前提 | 例 |
|---|---|---|---|---|
| 概念型 | 能說明一個理論或原理，並用它判斷情境 | 要回答的問題 → 理論名稱與出處 → 定義與特徵 → 生活例子 → 常見誤解 → 放到工作上 → 案例示範 → 練習 | 學員沒有學過這個理論 | 70h 消費者心理學 |
| 方法型 | 能用一套框架或步驟完成分析 | 要解決的問題 → 方法是什麼、為什麼有效 → 步驟 → 案例示範 → 練習 | 方法有可教的步驟與判斷依據 | STP、搜尋意圖分析 |
| 操作型 | 能在工具或平台完成一件任務 | 工作情境與任務 → 完成後長什麼樣 → 步驟 → 驗證結果 → 常見錯誤 | 原理少，學員靠實作學會；見 `操作型講義.md` | gen-ai-36h、GA4 設定 |
| 整合型 | 能把前面的成果組成一份決策或企劃 | 回顧手上的成果 → 決策框架 → 示範 → 作業 | 前面模組的成果已經存在 | 整合企劃、期末發表 |

「第一段寫工作情境」只屬於操作型；概念型與方法型的第一段寫這一節要回答的問題，案例到示範段才出現。

## 5. 頁面設計卡

每頁一張，寫在規格書或派工單裡。承作照卡寫，PM 照卡檢查。

| 欄位 | 內容 |
|---|---|
| 標題、副標 | — |
| 型態 | 第 4 節其中一種 |
| 先備 | 學員進這一頁時已經學過什麼，寫出是哪一頁的哪個成果或概念；PM 要打開那一頁確認真的教過（70h：m7-2 要學員複製 GA4 代碼 ID，全課卻沒有一頁教建立 GA4 資源） |
| 學習目標 | 學員讀完能說明／判斷／操作什麼，用動詞寫；頁面上保留給學員看 |
| 必教內容 | 必須教到的概念、定義要點、方法步驟、術語（附原文）；PM 寫，承作逐項教到 |
| 新名詞 | 這頁第一次出現的名詞，各在哪裡定義 |
| 保留 | 從保留清單帶過來的內容 |
| 完成物 | 由學習目標推出；完成物不能取代學習目標 |
| 示範與練習資料 | 示範用哪一批資料；練習用**另一批**資料或另一個對象（同一方法、換資料），兩者都寫出來 |
| 素材與來源 | 素材檔、查證過的來源連結 |
| 要修正的說法 | 舊頁面錯誤或過時的說法 |

## 6. 規格書必備內容

範本：`courses/digital-marketing-70h/_review/2026-11-05/改寫規格書-共通-v2.md` 與 `派工單-P1-M1.md`（概念型）；`courses/gen-ai-36h/_review/2026-11-01/part34/改寫規格書-Part3-4.md`（AI 操作型）。

1. **規則順序**（1.3）與**教學契約**（1.1）原文。
2. **設計卡**（第 5 節）。
3. **素材表**：每頁用哪些素材檔。事實以素材與答案檔為準，現有正文只用來理解案例與保留內容。
4. **共通規則**（每條附前提；套用新課程時逐條確認）：

| 規則 | 為什麼 | 不適用時 |
|---|---|---|
| 先引入，再使用：概念、方法、任務、名詞第一次出現時，先說清楚是什麼、為什麼現在需要、用在什麼對象、做完得到什麼 | 教學契約第 2、3 題；70h 出現「突然開始講步驟」 | 無 |
| 小節標題寫內容；轉場自然寫，不套固定句型與固定小節名稱 | 固定接句與固定標題讓每頁讀起來像同一個模板 | 無 |
| 案例第一次出現時附人物或資料表；正文用內容稱呼，不用檔名或證據 ID | 學員看不懂內部代號 | 沒有案例的頁面 |
| 練習不先給答案：先給「要做出什麼」；參考寫法用「> 參考方向：…」寫在練習最後，轉製成預設收合；練習資料只給原始材料，不附練習要學員判斷的欄位（角色、分類、結論）或「這支持…」的判斷句 | 先看答案就不會自己想；70h 試讀：參考答案緊接題目、練習資料先標好角色，學員只是在抄 | 純示範頁 |
| 示範是練習的完整範本：示範用本頁教的判準下判斷（判準沒滿足就寫「部分」或「未知」），示範表的欄位就是練習要交的欄位；練習換一批資料 | 70h 試讀：判準、示範、參考說法不一致，學員無法自我校正；練習資料和示範相同，照抄就能交 | 頁面沒有示範或沒有練習 |
| 不出現課程自創代碼、章節編號、英文狀態碼；**專業術語保留**，第一次出現寫「中文（原文）」並定義 | 代碼是噪音，術語是學習內容；70h 曾把術語當噪音刪掉 | 學員要在介面輸入的平台名詞保留原文並附中文 |
| 每小節最多一句限制語，其餘改正面寫法 | 限制語堆疊讓頁面像禁令清單 | 安全、法規警示 |
| 提示詞以動詞開頭，不用「你是…」 | 動詞開頭的指令較清楚 | 頁面沒有提示詞 |
| 每次開新對話或換工具，寫明要貼什麼；檔案交給 AI 的方式寫清楚 | 學員不知道要貼什麼 | 學員不使用 AI |
| 不補造數字、價格、人物、評論；示範不寫真實公司 | 承作模型會自行編造 | 引用經典研究時以描述代替品牌名 |
| 第一個 `##` 之前只放標題、副標、學習目標（一行，「｜」分隔）、本節完成物 | 轉製程式只轉 `##` 內容 | 依該課轉製方式調整 |

5. **型態附加規則**（只在前提成立時放進規格書）：

| 規則 | 前提 |
|---|---|
| 核對交給 AI：要 AI 附出處、列出沒有依據的句子；學員只抽看 3 處以內 | 課程以「學員指揮 AI 完成工作」為核心（例 gen-ai-36h） |
| 看執行結果也交給 AI，學員只看 AI 列出的不一致 | 同上；若讀結果本身是要教的技能（例 GA4 報表），改成學員先讀，再問 AI 漏看什麼 |
| 單人可完成：「請同伴」改成開新對話請 AI 扮演 | 課程不安排分組 |

6. **有狀態的流程加資料分配表**：每頁送進工具的是哪幾筆、預期結果是什麼、哪些留到後面。預算、時程這類會累計的數字也要列（例：廣告測試第幾輪、已花多少、剩多少），否則示範與練習的金額會互相矛盾。
7. **平台事實裁定**：素材互相矛盾時，以實際跑過的設定為準。介面位置只寫素材或官方說明能支持的部分，其餘標「畫面以實際為準」。
8. **交付格式**：`# 標題`、副標、`學習目標：…`、`本節完成物：…`、各 `##` 小節；頁尾「## 自我檢查」（逐項對照設計卡的必教內容、每個 `##` 第一段引入了什麼）與「## 事實核對」。只寫指定的輸出檔，不 git add、不 commit、不詢問使用者、不用 course-* 技能。

派工時明確指定承作模型：`codex exec -m gpt-5.6-sol -c model_reasoning_effort=high -s workspace-write`。

## 7. 檢查分層

每一層攔不同的失誤，不互相取代。

| 層 | 誰做 | 攔什麼 | 什麼時候 |
|---|---|---|---|
| 機械檢查 | 腳本 | 和型態無關的硬項：代碼、套路句、字數、lint、設計卡上的術語有沒有出現、案例出現位置 | 每頁 |
| 照卡檢查 | PM | 承作有沒有照設計卡的學習目標、必教內容與講授順序寫；PM 閱讀時用學員的四個問題讀每個 `##` 的第一段：在做什麼、為什麼現在做、拿什麼做、做完得到什麼；**逐欄比對示範產出與練習要交的欄位**；練習資料有沒有先寫出答案 | 每頁 |
| 學員視角試讀 | `course-sim-learner`（方法：`course-sim-trial` skill）；沙盒放在 repo 外，派工不寫預期會發現什麼 | 規格本身的漏洞中，讀者照做時會碰到的：判準、示範、參考前後不一致；練習照抄示範就能交；名詞沒定義；步驟要猜 | **只跑樣頁**，每頁一次，在交使用者審之前；批量頁不跑 |
| 樣頁關卡 | 使用者 | 前三層都漏掉的問題，尤其是敘事：開場有沒有引入、為什麼現在做這件事；確認型態與講授順序對不對 | 每種型態第一次出現時 |

- **學員視角試讀的盲點**：AI 讀者會從標題與前文自己推出「為什麼要做」，對開場沒有引入這類敘事問題不敏感（2026-11-05 實測：70h 修正前的 m1-2，使用者退件的「拆頁面沒有引入」沒有攔到，但攔到判準不一致與練習等於示範兩個主要問題）。它是樣頁人工審核的補充，不能取代人工審核。
- **試讀結果怎麼用**：阻斷與主要問題要在交使用者審之前修掉；同一類問題依 1.4 掃全部頁面，修到設計卡或講授順序那一層。次要問題列入修改清單，不擋關。不重跑第二輪試讀。

- **預設不做**：雙模型盲評、多輪冷讀、用評分尺打分、批量頁的模擬試讀。這些沒有停止條件，每輪都會找到新的小問題，改變不了交付決定。
- **例外**：有狀態的自動化流程（例如 Make、GTM），請一位評分者依實際設定逐步推演一次資料狀態。
- **新增任何驗證前先問**：它能改變交付決定嗎？不能就不做。

## 8. 必須先問使用者的事

- 課程目標、教學型態判定、大綱方向（模組名、標題、完成物）。
- 每種型態的樣頁。
- 平台方案取捨；提出方案與證據，交使用者裁決。
- 不可逆或略過保護的操作：合併 main、`--no-verify`、刪檔、修改別人未追蹤的檔案。

其他事項（措辭、規則細節）由 PM 決定，記在該課的改寫記錄表。

## 9. 常見坑

| 坑 | 症狀 | 做法 |
|---|---|---|
| 規則脫離前提被搬用 | 操作課的「第一段寫工作情境」套到原理課，案例先上、概念沒教 | 1.2、第 4 節 |
| 只盤點缺點 | 改寫把原本正確的定義、術語、例子一起刪掉 | 步驟 0 保留清單 |
| 完成物取代學習目標 | 學員做得出表格，卻說不出理論是什麼 | 設計卡兩欄分開 |
| 只對照自己的規格檢查 | 規格漏掉的問題，腳本與 PM 一起漏掉 | 第 7 節分層；樣頁關卡 |
| 補丁式加規則 | 每發現一個問題就加一條全域規則 | 1.4、1.5 |
| HTML 與上游脫節 | HTML 被直接改過，從上游重轉會蓋掉 | 步驟 3 先定落筆層 |
| 轉製程式缺陷 | 只轉部分頁時證據檔被整份覆蓋；練習順序時數錯 | 改寫前先用一頁在複本上試轉，比對外殼與元件 |
| 跨頁狀態矛盾 | 已處理的資料被重貼、故障練習與路線不一致 | 第 6 節第 6 項分配表 |
| 練習洩漏答案 | 範例、參考寫法、素材編號透露答案 | 練習不先給答案；素材本身的洩漏另案修素材 |
| 混合工作區 | 別人有未提交修改；索引、sitemap 重建混入他人內容 | 改寫前備份別人改過的檔；逐檔 stage；索引只收本次條目 |
| push 檢查擋下 | 未追蹤檔違規、索引與工作區不一致 | 在乾淨 worktree 合併與 push |
| 驗證成癮 | 一個上午只完成三分之一 | 第 7 節「預設不做」 |
