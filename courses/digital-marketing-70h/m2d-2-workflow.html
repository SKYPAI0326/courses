單元 2D-2

設計可控的 AI 自動化工作流

AI 產出若要進入日常工作，必須先說清楚資料從哪裡來、每一步交出什麼，以及錯誤時在哪裡停止。這節課用 Make.com／Zapier 的共同邏輯設計一份可檢查的工作流規格；沒有平台帳號也能完成主路徑。

學習目標 OUTCOMES
能用觸發器、動作、輸入與輸出說明一條自動化流程如何運作
能為 AI 步驟指定資料欄位、輸出格式與人工核准點，不讓模型自行補造來源
能完成一份六步工作流規格，包含錯誤通知、停止狀態與重跑起點

CONCEPT · 自動化基礎

觸發器 + 動作：自動化的兩個積木

Make.com 和 Zapier 都基於同一個邏輯：當某件事發生（觸發器），自動執行一個或多個動作。每個動作還要說明接收哪些欄位、產生哪些欄位，下一步才不需要猜資料在哪裡。

類比
就像條件句：「如果收到新的 Google Form 填寫，那麼把資料新增到 Google Sheet，同時發送確認 Email 給填寫者，並且在 Slack 通知你的團隊」——這就是一個有三個動作的自動化流程。Make.com 讓你用視覺介面設計這個條件句。
Make.com
以 scenario 和 module 組成視覺流程。Trigger 負責帶入資料，後續 module 依序搜尋、轉換或執行動作。平台介面、額度與可用 module 會更新，實作時應以 Make 官方 module 說明為準。
Zapier
以 Zap 組成流程；一個 trigger 啟動流程，後面接一個或多個 action。後續欄位可引用前一步的動態資料；實作前先查閱 Zapier 官方說明，再確認帳號可用的 App、事件與方案限制。
FLOW 1 · 內容自動發佈

AI 生成 → 內容自動發佈流程

以下是一個實際可以在 Make.com 設計的自動化流程：每天早上從 Google Sheet 取出當日預定的貼文主題，呼叫 AI API 生成文案，等待人工審核後自動發佈到社群。

每日社群內容自動化流程 Make.com + Claude API + Buffer
觸發器
每天 08:00，排程觸發流程啟動
↓
Google Sheets
讀取當日對應的「主題」「訴求」「關鍵詞」欄位資料
↓
Claude API
以讀取的資料填入 Prompt 模板，呼叫 AI 生成文案草稿，輸出 JSON 格式（含標題、內文、hashtag）
↓
Google Sheets
把 AI 生成的草稿寫回 Sheet 的「AI 草稿」欄，並更新狀態為「待審核」
↓
Email / Slack
通知負責人「今日草稿已生成，請審核後在 Sheet 中將狀態改為『已核准』」
↓
觸發器（Watch）
監控 Sheet，當狀態欄出現「已核准」時觸發下一步
↓
Buffer / 社群平台
把已核准的文案排程到 Buffer，在指定時間發佈到 IG / FB
→
注意流程中的「人工審核」節點是刻意設計的，不是可以省略的步驟。全自動發佈（AI 生成直接上線）在品牌行銷中風險太高——一個錯誤的事實或不適當的語氣直接公開，比節省那幾分鐘審核更貴。
FLOW 2 · 報告自動生成

數據 → AI 分析 → 報告自動生成

每週或每月報告常包含重複的取數、欄位整理與版型填入。以下流程把可重複的處理交給自動化；實際省時要把人工審閱、錯誤處理與維護時間一起記錄，不能先承諾固定分鐘數：

週報自動生成流程 GA4 / Meta → Make.com → Claude → Google Docs
排程觸發
每週一早上 07:00 自動啟動
↓
GA4 API
自動拉取上週的核心指標：工作階段數、跳出率、轉換數、流量來源分佈
↓
Meta API
拉取廣告投放數據：花費、觸及、點擊率、轉換成本
↓
Claude API
投入數據，生成：本週亮點（3 條）、異常項目（需關注）、下週建議行動（2-3 條）
↓
Google Docs
自動填入週報模板：數字圖表 + AI 分析文字，生成可直接分享的週報文件
↓
Email 通知
把週報連結發送給相關人員，附上「請確認 AI 分析是否符合實際情況」
DECISION · 什麼適合自動化

把固定處理交給流程，把品牌判斷留給人

先看任務是否有穩定輸入、固定格式與可觀察結果。符合這三項的資料處理適合自動化；需要品牌立場、創意取捨或關係判斷的工作，應保留人工決策。

適合自動化 不適合自動化（需要人工）
固定格式的週報、月報數據整理 涉及品牌立場的策略決策
新訂閱者的歡迎 Email 序列 危機處理和負面評論的回應
表單填寫後的確認通知 需要品牌聲音精準把控的重要對外文案
社群數據的定期採集和彙整 需要創意判斷的活動企劃方向
根據用戶行為觸發的個人化推薦 與 KOL / 媒體的溝通和關係維護
💡
自動化的邊界原則：資訊流轉和格式處理可以在通過測試後自動執行；判斷、品牌聲音和創意決策需要人在迴路中（Human-in-the-loop）。人工核准點要寫出負責人、核准後去向與退回位置，不能只放一個「待確認」狀態。
AI 接口 · 一個自動化情境設計

「每週競品摘要」可控 workflow 設計範本

先追一筆資料：「山徑咖啡」的貼文資料從 CSV 進入 Validate，確認日期、網址、讚數與留言數都符合規則後，才交給 Aggregate 計算；AI 只接收彙整結果，不接收可自行推測的空白。這份示範不要求 AI 猜平台 endpoint，也不依賴未確認的 scraping 服務。

把這段貼進 ChatGPT 或 Claude
請幫我設計一個 Make.com workflow，需求如下： 【目標】每週一上午 9:00 自動產出「上週競品社群動態摘要」並寄到我信箱 【輸入】我有權使用的競品貼文 CSV，欄位為 brand、published_at、url、caption、likes、comments 【需要的資訊】各品牌上週發文數、依已提供數字計算的互動最高貼文、可由文字證據支持的主題變化 【輸出格式】Gmail 信件，含「品牌名 + 數據 + 互動冠軍貼文連結 + AI 一句話觀察」 請輸出： (1) Workflow 結構圖（用文字描述每個 module 與連線） (2) 每個 module 的輸入／輸出欄位、資料型別、必填值與空值處理 (3) 給 AI module 的 prompt（讓 ChatGPT module 寫摘要的指令） (4) 人工核准點、錯誤通知、重跑起點與停止條件 先以我提供的 10 筆測試資料設計，不自行新增 scraping、付費 API 或未確認的第三方服務。
參考完成品：六步工作流規格

Workflow 結構圖（6 個 module）

① Manual trigger（先用測試檔）
　↓
② Google Drive / Sheet（讀取核准 CSV）
　↓
③ Validate（檢查必填欄、日期與空值；失敗走錯誤路徑）
　↓
④ Aggregate（依品牌計算已提供數據）
　↓
⑤ AI module（只根據彙整資料產生摘要草稿）
　↓
⑥ Draft + human approval（先存草稿，核准後才寄送）

關鍵欄位設定

• 輸入契約：日期為 ISO 8601；likes／comments 為非負整數；url 不可空白
• 驗證失敗：停止主流程，寄出含列號與錯誤欄位的通知，不讓壞資料進 AI
• AI module：模型名稱在開課日由帳號可用清單選擇；輸出固定 JSON schema
• 寄送：先建立 Gmail 草稿，人工核准後才送出；主旨日期由資料期間自動產生

ChatGPT module 的 prompt

你是品牌觀察員。下面是 {{brand_name}} 上週 7 天的 IG 貼文資料：
{{posts_json}}

請輸出 100 字內摘要，含：
(1) 發文頻率（幾篇）
(2) 依 likes + comments 合計找出的互動數最高貼文主題與連結
(3) 觀察到的調性變化（如新主題、新商品線索）

請只用 JSON 給的資料，不要推測未提及的事情。

需要人工檢查的 stop point

• 先以 10 筆測試資料手動執行，逐欄核對計算結果
• 摘要若引用 CSV 沒有的事實，退回草稿並記錄錯誤樣本
• 缺欄、空檔或 API／模組失敗時停止寄送，保留原始輸入與錯誤紀錄；修正後從 Validate 重新跑

這份參考答案的用途是核對資料契約與分流，不是證明平台已經建置。你的文件必須保留六個步驟，並把測試資料中兩筆錯誤的停止位置寫清楚。
自動化設計四項最低證據：輸入／輸出資料契約、測試資料、人工核准、錯誤通知與重跑起點。先手動觸發通過，再開排程；任何一步無法證明資料正確，就停止對外發布。
PRACTICE · 完成工作流規格

先找出壞資料，再畫六步流程

剛才的示範已把一筆有效資料帶到 Validate。現在換你檢查完整 CSV，將會造成錯誤的資料擋在 AI 之前，再把每一步的責任寫進 competitor-summary-workflow.md。

步驟你要完成的內容
1. 檢查輸入確認六個欄位存在；日期使用 YYYY-MM-DD；url 不可空白；likes／comments 必須是非負整數。
2. 記錄錯誤寫出錯誤列、欄位、原因與狀態 NEEDS_FIX。錯誤資料不得進 Aggregate。
3. 畫六步規格依 Manual trigger、Read CSV、Validate、Aggregate、AI draft、Human approval 建表，每一步填輸入、輸出與失敗去向。
4. 鎖定 AI 輸出摘要只可引用貼文數、互動最高貼文及 caption 可支持的主題；缺資料時輸出 INSUFFICIENT_DATA。
5. 設定核准草稿狀態為 APPROVAL_PENDING；負責人核准後改為 APPROVED，才能進入寄送出口。
6. 寫重跑起點資料錯誤修正後從 Validate 重跑；AI 引用不存在的事實時從 AI draft 重跑。
✓
完成檢查：你應找出一筆缺少 url、另一筆 likes 為負數。兩筆都停在 Validate；其餘資料才能進 Aggregate。文件還要包含六步流程、人工核准負責人、兩個重跑起點，以及「尚未在平台執行」的狀態說明。

若你有 Make.com 帳號，可把同一份規格用 Run once 測試；Make 官方 scenario 說明列出 Run once 與排程執行的差異，實際頻率仍受帳號方案影響。執行截圖與 history 紀錄是額外的平台證據，不能用設計文件代替。
