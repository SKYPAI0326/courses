0. 先看這一頁：你今天要做完什麼

上一單元（7-2）結束時，你的紀錄長這樣：練習頁推送的四個事件，在網站和 Tag Assistant 都看得到，但 GA4 那一欄還寫著「待下一節建立事件代碼」。原因很單純：GTM 看見了訊號，但還沒有人把訊號轉交給 GA4。

這一單元就是把「轉交」這段接起來。做完之後，你手上會有：

完成物 內容 誰做
GA4 事件代碼設定與收件紀錄 comparison_open、booking_start、booking_complete 三列 跟著講師示範做，GA4 欄填你自己 DebugView 看到的實際結果
同一份紀錄的第四列 line_join 一列，含關鍵事件標記與 placement 自訂維度 你自己完成
捲動門檻實測（不算在完成物裡） 垂直 25% 捲動觸發，看「捲動深度門檻」變數的值 跟著做

每一個事件，你都要做同一組「三件套」，再做同一組「三層驗收」：

三件套（在 GTM 裡建）            三層驗收（證明資料真的走完全程）
┌─────────────────┐            第 1 層 網站推送：練習頁右下角「事件監看區」多一筆
│ 1. 資料層變數     │  ← 取參數   第 2 層 GTM 觸發：Tag Assistant 顯示代碼觸發 1 次
│ 2. 自訂事件觸發條件│  ← 決定何時 第 3 層 GA4 收件：DebugView 看到事件與參數
│ 3. GA4 事件代碼   │  ← 送去 GA4
└─────────────────┘

通過標準只有一句話：正例觸發一次＋反例沒有觸發＋DebugView 的事件與參數正確。

你會擔心「變數、觸發條件、代碼三個畫面來回切、選單又深」，所以第 4 節會用 comparison_open 把每個按鈕的位置一步一步寫出來；第 6 節做 line_join 時，只要照同一條路線換掉名稱就好。

1. 開工前五分鐘檢查

每次開始操作（包括中途重新整理練習頁之後），都先過一遍這張清單。很多「收不到」都是這裡漏了一步。

  • [ ] 練習頁網址帶著自己的容器 ID： https://skypai0326.github.io/courses/courses/digital-marketing-70h/assets/practice/booking-practice.html?gtm=GTM-你的ID 頁首應顯示「GTM 練習容器：GTM-（你的 ID）。請開啟 GTM 預覽模式後操作下方互動。」 如果顯示「尚未載入 GTM」，代表 ID 打錯或還是範例的 GTM-XXXXXXX。
  • [ ] GTM 開的是同一個容器：GTM 畫面上方的容器 ID 和網址裡的一樣。把後四碼抄到紀錄裡。
  • [ ] 預覽已連線：在 GTM 按右上角「預覽」，Tag Assistant 顯示已連線（Connected）。
  • [ ] 按了「接受全部」：練習頁左下角的「同意模式練習」橫幅，標題要變成「已選擇：接受全部」。 為什麼一定要按？練習頁一載入就把 analytics_storage 等四項設成拒絕（denied）。Google 的 DebugView 說明寫明：使用者沒有授予 Analytics Cookie 同意時，偵錯模式不會顯示任何事件。練習頁每次重新整理都會回到拒絕，所以每次重新整理都要再按一次。
  • [ ] GA4 開的是自己在 7-2 建的資源，不是第六模組那個官方示範帳戶。
→
一個很容易忘的規則：在 GTM 改了任何設定（新增變數、改觸發條件、改代碼）之後，要**再按一次「預覽」**重新連線，練習頁才會用到最新的設定。不重按，你測到的還是舊版本。【待實機確認】

2. 先判斷：這個互動需要自訂事件嗎？

2-1 自訂事件是什麼

GA4 有些事件會自動收（例如 page_view）；自訂事件是你為了某個特定的業務行為，自己取名、自己設定的事件。例如「點擊加入 LINE」對山徑咖啡是重要的轉換，但 GA4 不會知道這件事，只能由你設定。

2-2 建之前，先查「加強型評估」已經收了什麼

GA4 網頁資料串流的「加強型評估」會自動收下面這些事件（Google 官方說明，2026-11 查證）：

事件 什麼時候收 重點參數
page_view 每次頁面載入 page_location 等
scroll 使用者第一次捲到頁面約 90% 深度 —
click（外連點擊） 點到會離開目前網域的連結 link_url、link_domain、outbound 等
file_download 點到常見檔案格式的下載連結 file_name、link_url 等
form_start 工作階段中第一次與表單互動 form_id 等
form_submit 提交表單 form_id 等

（要確認自己資源有沒有開：GA4「管理 → 資料收集和修改 → 資料串流 → 點你的網頁串流 → 加強型評估」。）

判斷原則：現有事件已經能回答你的問題，就沿用，不要再建一個一樣的，否則同一個行為會被算兩次。

→
小提醒：練習頁的預約表單是一般的 HTML 表單，所以你在 DebugView 裡可能會看到加強型評估自動送出的 form_start 或 form_submit。那不是你建的事件，不用緊張；在紀錄的備註寫一句「另見加強型評估 form_start／form_submit」即可。這也正是第 3 節要你「先確認新增是否必要」的原因。

2-3 四種互動，各用什麼訊號

互動 優先用的訊號 次選 不要只靠
按鈕 網站在「動作成功時」推送的資料層事件 穩定的點擊 ID 或 Class，搭配「點擊－所有元素」觸發條件 按鈕文字（文案一改，追蹤就斷）
表單 網站在「送出成功」的程式裡推送的資料層事件（AJAX 或客製表單都用這招） 「表單提交」觸發條件；或成功後一定進入唯一感謝頁時，用網址判斷 只看按了送出鈕（沒填完被擋下也算一次）
捲動 先看加強型評估的約 90% scroll 夠不夠 不夠才用「捲動深度」觸發條件，設你真正需要的門檻 設一個跟 90% 重複的門檻
外部連結 先看加強型評估的 click（已有 link_url、link_domain） 現有參數不夠時才補設定 —

幾個細節，之後你幫自己的產品規劃時會用到：

  • 「表單提交」觸發條件有兩個勾選項（Google 官方說明）：
    • 「等待代碼」：讓表單送出的動作先等一下，等相關代碼啟動（或等到逾時）再繼續，避免頁面跳走時代碼來不及執行。
    • 「檢查驗證」：只在表單成功提交時啟動；不勾的話，使用者每次「嘗試」送出都會啟動。
    • 可以用表單的 ID（GTM 內建變數「表單編號」）限定只追某一張表單。
    • 如果表單是由網頁程式處理、不換頁（AJAX 或客製表單），改由網站在成功回呼裡推送資料層事件。
  • 用感謝頁網址判斷：只有在「送出成功後一定會進入一個唯一的感謝頁」時才適用。而且要測一次「在感謝頁按重新整理」，看會不會重複算一次。

套到練習頁：練習頁的按鈕和表單都已經寫好「成功時推送資料層事件」（表單由頁面程式處理、不換頁、沒有感謝頁），所以本單元四個事件全部用資料層事件，用的是「自訂事件」觸發條件。這是最穩定的做法，不會因為改了按鈕文字或版面就失效。

3. 命名：先查 Google 的建議事件，再自己取名

3-1 順序

  1. 先查 GA4 建議事件（recommended events）。Google 已經替常見行為取好名字，例如 generate_lead（提交表單或索取資訊）、begin_checkout（開始結帳）、purchase（完成購買）。有對應的就沿用名稱，並照規定帶參數（每個事件的規定參數，在官方建議事件頁點事件名稱進開發人員文件查）。沿用的好處是 GA4 的部分報表與功能認得這些名稱。
  2. 沒有對應時才自訂名稱，並遵守命名規則（Google 官方，2026-11 查證）：
    • 開頭必須是英文字母。
    • 只能用英文字母、數字、底線，不能有空格。
    • 避開保留名稱（例如 page_view、session_start、user_engagement 等，清單 Google 會更新）。
    • 大小寫視為不同：line_join 和 Line_Join 在 GA4 是兩個不同的事件。
  3. 既有的 form_submit 已經能表達的，先問自己「真的需要再多一個嗎？」

3-2 山徑咖啡怎麼辦

山徑咖啡的事件名稱已經寫在品牌包第 11 節（事件規格），課堂上照抄原名，不改：

事件名稱 中文說明 觸發時機 參數 標為關鍵事件
comparison_open 開啟三款手沖壺比較表 比較表由收合變成展開時 page_type、product_count 否（過程事件）
booking_start 開始填寫試握預約 預約表單第一個欄位首次取得焦點時 form_id、page_type 否（漏斗起點）
booking_complete 完成試握預約 表單通過必要欄位檢查並送出時 form_id、preferred_slot 是
line_join 點擊加入 LINE 加入 LINE 按鈕被點擊時 placement、page_type 是

3-3 你們組的巷口晨光怎麼辦（課後帶回去用）

單元頁提醒「各組自己的產品先查建議事件」。巷口晨光的主要轉換是「完成隔日早餐預訂」。替它命名時，照這個思路：

  • 顧客說「我想前一天選好，早上不用在櫃前想太久」，所以「完成預訂」是最重要的那一個事件。
  • 打開 GA4 建議事件清單，問自己：這個預訂在線上付款嗎？
    • 如果線上就付款，它更像「完成購買」，去看 purchase 和它的規定參數。
    • 如果只是預留、到店才付錢，它更像「提交資訊／表單」，去看 generate_lead。
    • 兩者都對不上，才自己取名（例如 preorder_complete），並照 3-1 的規則檢查。
  • 這是你們組要做的決定，沒有標準答案；把「查過哪個建議事件、為什麼選或不選」寫在模組作業的追蹤規格裡，這本身就是面試時講得出來的判斷。

4. 示範：用 comparison_open 走完一次三件套

這一節請跟著講師在你自己的容器裡做一次。做完一次，後面三個事件都是同一條路。

名稱對照卡（做的時候放旁邊）

GTM 和 GA4 的選單是中文介面，但有幾個名稱容易對不上，先對好：

你在講義看到 畫面上的位置或文字
資料層變數 GTM 左側「變數」→「使用者定義的變數」區塊的「新增」→ 類型「資料層變數」
自訂事件觸發條件 GTM 左側「觸發條件」→「新增」→ 類型「自訂事件」
GA4 事件代碼 GTM 左側「代碼」→「新增」→ 類型「Google Analytics：GA4 事件」
關鍵事件 GA4 繁體中文說明與介面可能寫作「重要事件」（英文 key event），是同一件事
自訂維度 GA4「管理 → 資料顯示 → 自訂定義」→「自訂維度」分頁

建議的命名方式（讓自己找得到）

GTM 裡的每個項目都有一個「顯示名稱」，這個名字只給人看，取得清楚可以大幅減少來回找的時間：

  • 資料層變數：直接用鍵值本身，例如 page_type、product_count。
  • 觸發條件：自訂事件 - comparison_open
  • 代碼：GA4 事件 - comparison_open

步驟 1｜建資料層變數（page_type、product_count）

練習頁按下「開啟比較表」時推送的是：

{event: 'comparison_open', page_type: 'booking_practice', product_count: 3}

event 這個鍵會交給觸發條件用；其他兩個鍵（page_type、product_count）是參數，要各建一個資料層變數把值取出來。

  1. GTM 左側點「變數」。
  2. 往下找到「使用者定義的變數」區塊，按右邊的「新增」。
  3. 點「變數設定」方框，選「資料層變數」。
  4. 「資料層變數名稱」欄位填：page_type
    • 這裡必須和推送的鍵值逐字相同：全小寫、底線、不能多空格。打成 page-type，變數就會是空的。
    • 「資料層版本」維持預設的版本 2。

  1. 左上角把這個變數命名為 page_type，按「儲存」。
  2. 重複一次，建立 product_count。
→
page_type 只要建一次。booking_start 和 line_join 也會用到它，到時候直接選這個變數，不要再建第二個。

步驟 2｜建自訂事件觸發條件

  1. GTM 左側點「觸發條件」→ 右上「新增」。
  2. 點「觸發條件設定」方框，選「自訂事件」。
  3. 「事件名稱」填：comparison_open（逐字照抄規格，全小寫）。
  4. 「使用規則運算式比對」不要勾。
  5. 「這項觸發條件的啟動時機」選「所有的自訂事件」（預設就是）。

GTM 網頁版，2026-11-12 截圖；截圖時只開新增畫面，按「捨棄變更」離開，沒有儲存。

  1. 命名為 自訂事件 - comparison_open，儲存。

為什麼不勾規則運算式（regex）？勾了之後，你填的字會被當成「比對規則」，而不是「完整名稱」。一個典型的錯誤是填 .*（代表「任何事件」），這會把 GTM 自己的系統事件也一起算進來，代碼就會在不該觸發的時候觸發。

另外，Google 在 2026-10-08 的更新說明寫道：gtag('config') 指令現在會以 gtag.config 事件出現在資料層，使用萬用字元自訂事件觸發條件的容器，可能因此讓代碼觸發。所以本課一律「填完整名稱、不勾 regex」。

步驟 3｜建 GA4 事件代碼

  1. GTM 左側點「代碼」→ 右上「新增」。

  2. 點「代碼設定」方框，選「Google Analytics：GA4 事件」。

  3. 評估 ID：選你 7-2 建好的 Google 代碼，或直接填你的 G- 開頭評估 ID（在 GA4「管理 → 資料收集和修改 → 資料串流 → 你的網頁串流」可以看到）。

  4. 「事件名稱」填：comparison_open（逐字照抄規格原名）。

  5. 展開「事件參數」，按「新增參數」，一列一個參數：

    事件參數（左欄，送到 GA4 的參數名稱） 值（右欄，點積木圖示選變數）
    page_type {{page_type}}
    product_count {{product_count}}

    右欄不要用打的，點旁邊的積木圖示，從清單選步驟 1 建好的變數，比較不會打錯。

  6. 往下點「觸發條件」方框，選 自訂事件 - comparison_open。

  7. 命名為 GA4 事件 - comparison_open，儲存。

步驟 4｜預覽：正例一次、反例不觸發

  1. 在 GTM 按「預覽」（改過設定就要重按），連上練習頁。
  2. 在練習頁按「接受全部」。
  3. 正例：按「開啟比較表」一次。
    • 練習頁右下角事件監看區：多一筆「第 N 筆：comparison_open　page_type=booking_practice、product_count=3」。
    • Tag Assistant：左側事件清單出現 comparison_open，點它，GA4 事件 - comparison_open 出現在「已觸發的代碼」（Tags Fired），觸發 1 次。【待實機確認】
    • 在 Tag Assistant 的「變數」（Variables）分頁，看 page_type、product_count 有沒有值。【待實機確認】
  4. 反例：按「收合比較表」。
    • 練習頁說明寫得很清楚：收合時不推送。所以監看區的序號不會增加，代碼的觸發次數也不會增加。
    • 兩個都沒變，反例就通過。

步驟 5｜GA4 收件：DebugView

  1. GA4 進入「管理 → 資料顯示 → DebugView」。
  2. 左上角「偵錯裝置」若有多台，選你正在測的那一台。
  3. 時間軸上會出現 comparison_open（通常幾秒內），點它，右側列出參數，確認 page_type = booking_practice、product_count = 3。
  4. 再到「報表 → 即時」看一眼，事件名稱也應該出現在事件計數的卡片裡。
  5. DebugView 沒有出現：在紀錄的 GA4 欄寫「待排查」，接著看第 8 節的排查表，不要空著。

到這裡，comparison_open 這一列三層都證明了，可以寫進紀錄。

5. 示範：booking_start 與 booking_complete

做法完全相同，只是名稱、參數，以及正反例怎麼設計不一樣。

booking_start（開始填寫預約）

  • 推送：{event: 'booking_start', form_id: 'trial_booking', page_type: 'booking_practice'}
  • 新建變數：form_id（page_type 沿用）。
  • 觸發條件：自訂事件，事件名稱 booking_start。

7. GA4 收尾：關鍵事件與自訂維度

7-1 標記關鍵事件（星號）

  1. GA4「管理 → 資料顯示 → 事件」。
  2. 在「近期事件」清單找到事件（例如 line_join），按事件名稱旁邊的星號，星號變成實心就是標好了。

要知道的條件（Google 官方，2026-11 查證）：

  • 需要資源的「編輯者」或更高角色。你在 7-2 自己建的資源，你是管理員，沒問題。
  • 事件要先出現在這份清單裡才按得到星號。DebugView 看到了，不代表事件清單也已經出現。
  • 標好之後，標準報表最多要 24 小時才會反映；即時報表則在事件發生後幾分鐘內更新。標記只影響標記之後的資料，不會回頭改過去的資料。

7-2 註冊自訂維度（placement）

為什麼要做這一步？參數送進 GA4 之後，在 DebugView 就看得到；但要在報表裡用它來分組、篩選（例如「哪個位置的 LINE 按鈕被點最多」），要先把它註冊成自訂維度。

  1. GA4「管理 → 資料顯示 → 自訂定義」。
  2. 選「自訂維度」分頁，按「建立自訂維度」。
  3. 填寫：
    • 維度名稱：placement（不能用連字號）。
    • 範圍：事件。
    • 說明：選填，例如「加入 LINE 按鈕所在位置」。
    • 事件參數：placement（逐字等於代碼裡的參數名稱）。
  4. 按「儲存」。

儲存前再看一次：「範圍」和「事件參數」儲存後就不能改。填錯只能另建一個，而一般資源的事件範圍自訂維度上限 50 個（刪除後還要等 48 小時才能補新的），所以不要隨手亂建。

建好後，約 24～48 小時才能在報表裡用。示範的 preferred_slot 也是同樣做法。

7-3 分清楚「設錯了」還是「還沒到時間」

你最擔心的是這件事，所以用一張表把它分開。原則是：越前面的層級，越即時；只要前面的層級對了，後面沒出現多半是在等時間。

9. 捲動門檻實測（垂直 25%）

這段不算在完成物裡，但它能幫你看懂「資料層事件」和「GTM 自己偵測的觸發條件」差在哪。

練習頁的「三款手沖壺的使用與保養說明」長內容區，頁面明寫「內容刻意寫長，不會推送任何事件」。所以等一下如果有東西觸發，那一定是 GTM 自己偵測到的捲動，不是網站推送的。

步驟

  1. 開啟內建變數：GTM「變數」→「內建變數」區塊按「設定」→ 勾選「捲動深度門檻」。
  2. 建觸發條件：觸發條件 → 新增 → 類型「捲動深度」→ 勾「垂直捲動深度」→ 選「百分比」→ 填 25 → 命名 捲動深度 - 25%，儲存。
  3. 套到講師指定的測試代碼：代碼名稱與事件名稱以講師當天指定為準；參數 scroll_depth_threshold 的值點積木圖示，從清單選「捲動深度門檻」（英文介面為 Scroll Depth Threshold）。這個測試代碼只留在工作區，不發布。
  4. 重按預覽，練習頁按「接受全部」，往下捲。

你會觀察到的

  • 監看區不會多任何一筆（長內容區不推送事件）。
  • Tag Assistant 左側會出現一筆捲動深度事件（Scroll Depth，資料層裡的名稱是 gtm.scrollDepth），點開看測試代碼是否觸發，並在「變數」分頁確認「捲動深度門檻」的值是 25。
  • 同一頁、同一個門檻只會觸發一次；要再測就要重新載入頁面。
  • 一載入就觸發了？ Google 說明：如果載入時，指定的深度已經在畫面裡看得到，就算沒捲動也會觸發。練習頁的頁首約佔全頁 23%，螢幕高一點、或縮小瀏覽器字級，25% 就可能一開頁就在畫面內。這時：
    • 記錄你的視窗環境（例如「筆電 14 吋、瀏覽器全螢幕、縮放 100%」）。
    • 把門檻提高（例如 50%），再測一次。

為什麼門檻不要設 90%

加強型評估已經自動收約 90% 的 scroll。你再設一個 90%，就是重複算同一件事。門檻要對應一個問題，例如「有多少人至少讀到保養說明的前段」，才設 25% 或 50%。

13. 延伸設定（時間夠或課後再做）

這兩項會長期影響資源的資料，缺權限或不確定就不要硬做，在紀錄寫「負責人」與「待處理項目」即可。

13-1 排除內部流量

用途：公司自己人（或你自己測試）的流量，不要混進正式報表。

  1. GA4「管理 → 資料收集和修改 → 資料串流」→ 點網頁串流 →「進行代碼設定」→「顯示更多」→「定義內部流量」→「建立」。
  2. 填規則名稱；traffic_type 值預設為 internal；選 IP 比對方式並填 IP。
  3. 再到「管理 → 資料收集和修改 → 資料篩選器」建立「內部流量」篩選器，選「排除」。
  4. 狀態先選「測試」：這時資料只會被標記、不會被排除，可以先確認規則抓得對不對。
  5. 確認無誤才改成「有效」。
→
有效之後是永久的：被排除的資料不會被處理，之後也救不回來。只是想在某張報表暫時隱藏資料，應該用報表篩選器，不是資料篩選器。

13-2 連結 Search Console

用途：在 GA4 裡看到「Google 自然搜尋查詢」與「到達網頁」的資料，對接你在 SEO 模組學的內容。

  1. GA4「管理 → 產品連結 → Search Console 連結」→「連結」。
  2. 選要連結的 Search Console 資源 → 選網頁資料串流 → 檢查後提交。

權限條件兩個都要有：GA4 資源的編輯者，而且是 Search Console 資源的已驗證擁有者。一個網頁串流只能連一個 Search Console 資源。練習頁不是你的網站，所以課堂上多半是記錄「負責人：網站擁有者；待處理：驗證 Search Console 擁有權後連結」。

「表單完成我沒有用點擊送出按鈕來算，因為漏填被擋下的那一下也會被算進去；我用網站在通過檢查後才推送的事件。」

你手上的紀錄表和截圖，就是作品集裡的證據。

15. 自我檢核

做完後，試著不看講義回答：

  1. 練習頁的「收合比較表」為什麼是 comparison_open 的好反例？
  2. 你的 placement 變數在 Tag Assistant 是空的，第一個要查什麼？
  3. DebugView 看到 line_join，但事件清單裡沒有，星號按不到。這是設錯了嗎？紀錄要寫什麼？
  4. 為什麼自訂事件觸發條件不勾規則運算式？
  5. 巷口晨光的「完成隔日早餐預訂」，你會先去建議事件清單裡看哪一兩個？取決於什麼？
參考答案
  1. 因為收合時網站不推送事件，正確的設定下，監看區序號和代碼觸發次數都不會增加；如果有增加，就是觸發條件設錯。
  2. 資料層變數的「資料層變數名稱」是否和推送的鍵 placement 逐字相同。
  3. 不是。DebugView 證明到第 3 層。紀錄寫證據層級（第 3 層）與複核時間，之後回來標星號。
  4. 勾了會把填的字當比對規則；填 .* 之類的萬用條件會把系統事件（包括 2026-10-08 起的 gtag.config）也算進去，代碼會誤觸發。
  5. 看預訂是否線上付款：線上付款看 purchase；只是預留、到店付款看 generate_lead；都對不上才自訂名稱。

16. 下一單元

7-4「同意模式、Meta 像素與事件去重」會用到你今天建好的兩個代碼：講師示範替 GA4 事件 - comparison_open 設定額外同意 analytics_storage，你則用 GA4 事件 - line_join 練習，測「未選擇、接受全部、只保留必要」三種情境。今天按「接受全部」才看得到 DebugView，下一單元會解釋這背後的原因。

模組作業「一個點擊的旅程」要上台展示一個事件「從點擊、預覽模式到 GA4 即時報表」的路徑，今天的 line_join 就是最現成的展示素材。

17. 卡住時

  • 事件已在 DebugView 出現，但還沒出現在「近期事件」清單、星號按不到：可以在「管理 → 資料顯示 → 事件」點「+ 建立事件」，輸入事件名稱並開啟「標示為重要事件」切換鈕，GA4 收到該事件後就會當成重要事件。這個做法需要「行銷人」或更高角色。
