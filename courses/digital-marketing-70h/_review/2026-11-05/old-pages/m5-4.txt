ON-PAGE ELEMENTS · 頁面元素
### 五個標籤，送給 Google 的信號
<title>
清楚、精簡、獨特地描述頁面。沒有固定字數上限，也不必硬把關鍵字塞在最前面；搜尋結果會依裝置寬度截斷，Google 也可能依頁面內容改寫 title link。
meta desc
用一到兩句話提供準確、獨特且與頁面相符的摘要。Google 沒有規定固定長度，會依裝置截斷，也可能改用頁面內容生成 snippet；不要把 150–160 字元當成通過標準。
H1
用一個清楚、最突出的主標題建立頁面主題。H1 可與 Title 相近但不必完全相同；避免多個同等突出的主標讓讀者與搜尋系統無法辨識主題。
H2 / H3
次標題要反映內容層級與讀者問題。自然使用受眾真的會搜尋的詞與相關概念，不追求關鍵字密度，也不使用「LSI Keywords」作為排名公式。
URL
簡短、可讀、能描述內容，單字以連字號分隔。例：/seo-guide/ 而非 /post?id=1234。不要只為塞關鍵字改動穩定 URL；既有 URL 調整還需規劃重新導向。

SEMANTIC SEO · 語意優化
### 不只關鍵字密度，是語意完整性
內容重點不是達到某個關鍵字密度，而是讓讀者與搜尋系統清楚理解你在回答什麼問題。寫作前先問：「這個受眾要完成任務，還需要哪些子題、證據與限制？」不要為了看起來完整而重複同義詞。
🔍
語意優化實作方法：搜尋目標關鍵字，觀察目前結果頁出現的頁型與讀者問題，再回到自己的頁面判斷哪些子題確實需要補充。搜尋結果或「People Also Ask」只能提供研究線索；沒有頁面事實或讀者需求支持的題目，不必為了看起來完整而全部加入。
📝
使用讀者的語言：可自然帶入同義詞與相關概念，例如談 SEO 時視內容需要使用「搜尋引擎最佳化」「自然搜尋流量」「搜尋結果」，但不需要列滿所有變體。每個詞都要服務讀者理解。
FAQ SCHEMA · 結構化資料
### 先問是否適用：FAQ Schema 實作
FAQPage JSON-LD 可描述頁面上的真實問答內容，但不保證出現 rich result。Google 目前通常只讓知名、權威的政府與健康網站顯示 FAQ rich results；一般商業網站不應把它當成擴大搜尋版面的策略。只有頁面真的呈現相同問答、且符合政策時才使用。
FAQ Schema 範本（JSON-LD）
<script type="application/ld+json">{  "@context": "https://schema.org",  "@type": "FAQPage",  "mainEntity": [    {      "@type": "Question",      "name": "沒有瑜伽經驗也能使用入門系列嗎？",      "acceptedAnswer": {        "@type": "Answer",        "text": "可以。入門系列不要求既有瑜伽經驗，內容依序包含呼吸、暖身、基礎體式與收操。"      }    }  ]}</script>
這段 JSON-LD 只能在頁面 A 確實顯示同一組問題與回答時使用。若可見頁面沒有問答，正確做法是先補上讀者看得到的內容，或暫時不建立 FAQPage，而不是只把答案藏在結構化資料裡。

        Meta：給沒有瑜伽經驗的初學者。了解在家觀看的入門系列如何帶你完成呼吸、暖身、基礎體式與收操。
        H1：給初學者的線上瑜伽課程入門
        H2：入門系列會練習哪些內容／開始前要準備什麼
        FAQ：沒有瑜伽經驗也能使用入門系列嗎？可以。入門系列不要求既有瑜伽經驗，內容依序包含呼吸、暖身、基礎體式與收操。

### 從共同改寫，退去提示後自己交付
D

一起做：仍使用頁面 A。兩人各寫一版 Meta，交換標出每句引用的 FACT，再共同選出能說清楚入門內容、又沒有新增承諾的一版。無法標示來源的句子先刪除，不用較華麗的措辭掩蓋缺口。
S
獨立驗收：改做 brief 的頁面 B，不複製頁面 A 文字。把目標查詢、搜尋意圖、引用事實、Title、Meta、H1、兩個 H2、FAQ 判斷、排除或待補主張與兩項採用理由寫入 onpage-seo-rewrite.md。任何可發布句子若無法回指工作表或 FACT，退回修正。
