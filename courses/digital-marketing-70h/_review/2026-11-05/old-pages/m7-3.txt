學習目標 OUTCOMES
能依實際 dataLayer、穩定屬性或 ID 建立按鈕與表單追蹤，不靠易變的文字猜 selector
能依量測問題選擇捲動節點，並先排除 Enhanced Measurement 已收集的事件
能先比對 GA4 建議事件與命名限制，再建立一致且可驗證的自訂事件
CUSTOM EVENTS · 四種常見自訂追蹤
### GTM 實作，四種最常用的自訂追蹤
01
按鈕點擊追蹤
觸發條件：所有元素點擊 + 篩選條件
GTM 設定步驟
先確認網站是否能在成功互動時推送 dataLayer event；能做到時優先用事件契約
若只能監聽 DOM，再用 Preview 讀取實際 Click ID、Classes 與其他穩定屬性
建立只命中目標元素與頁面的條件；按鈕文字可能因改版或語系改變，不宜單獨使用
建立 GA4 Event tag，事件名稱與參數依團隊事件字典填寫
事件參數建議
cta_name：使用不隨畫面文案變動的識別值；若只能取 Click Text，要記錄其易變風險
button_location：依實際頁面區域填入一致值，例如 hero_section
只有報表分析需要的參數才建立自訂維度，並先確認沒有傳送個人識別資訊
02
表單送出追蹤
觸發條件：表單提交（Form Submission）
GTM 設定步驟
啟用內建變數：Form ID、Form Classes
新增觸發條件 → 表單提交
需要延遲離頁等待 tag 時才啟用 Wait for Tags；需要排除被取消的無效提交時啟用 Check Validation
用實際 Form ID／Classes 限定表單，並另查這個事件是否真的代表後端提交成功
常見問題
AJAX 或客製表單不一定會產生 GTM 可用的 Form Submission；應由成功 callback 推送 dataLayer event
只有真的成功後會進入唯一感謝頁時，才可用該 URL 作為成功證據，並測試重新整理是否重複計數
03
自訂捲動深度追蹤
觸發條件：捲動深度
GTM 設定步驟
新增觸發條件 → 捲動深度
勾選「垂直捲動深度」
先寫出要回答的問題，再選少數有意義的百分比或元素可見節點
若 Enhanced Measurement 的約 90% scroll 已足夠，就不要另建重複事件
事件參數建議
scroll_depth_threshold：{{Scroll Depth Threshold}}，值須與本次量測設計一致
不同節點的人數差只能描述觀察；要判斷放棄原因，還需分眾、頁面內容或使用者研究證據
04
外部連結點擊追蹤
觸發條件：連結點擊 + 外部網域篩選
GTM 設定步驟
先在 GA4 資料串流確認 Enhanced Measurement 是否已啟用出站點擊
用 DebugView 測試既有 `click` 事件及 link_url、link_domain 是否已滿足需求
只有需要額外業務分類且既有參數不足時，才建立自訂事件或補參數
發布前確認同一次點擊沒有同時送出兩套意義相同的事件
應用場景
追蹤用戶點擊合作夥伴連結
追蹤社群媒體連結點擊
事件參數 link_url：{{Click URL}} 記錄去哪了
NAMING CONVENTION · 事件命名規範
### 好的命名，讓報告自己說話
GA4 的事件名稱會直接出現在報告中。如果命名不一致，同一個行為可能被拆成多個名稱。命名前先查自動收集與建議事件；都不適用時，再依 GA4 限制與團隊字典建立自訂名稱。
📋
命名順序：先沿用 GA4 規定的建議事件名稱與參數；需要自訂時，名稱以字母開頭，只用英文字母、數字與底線，不含空白，並避開保留名稱與前綴。團隊可再約定小寫與一致語序，但不能覆蓋官方名稱。
❌ CTA Button Click
✓ 待查事件字典與建議事件
❌ Form Submitted
✓ 先查既有 form_submit
❌ PDF download clicked
✓ 先查既有 file_download
❌ 電話點擊
✓ phone_click（自訂例）
AI 接口 · 自訂事件 GTM 設定指引
### 從共同案例完成可驗收的事件規格
有網站時使用實際頁面；沒有網站或 GTM 權限時，開啟GA4 × GTM 共用量測練習包 Part 2，沿用「預約體驗」按鈕、Consent 與故障 trace。兩條路都要留下 measurement-decision.md；離線案例只能標 CONFIG REVIEW PASS，不能冒充平台已驗證。
1
先找事件來源，再決定 selector用 DevTools 與 Tag Assistant 檢查互動時是否已有 dataLayer event。若沒有，再查看實際元素的 ID、class 或 data-* 屬性是否唯一且穩定；看到屬性值不代表它天然就是可靠 selector，需用 Preview 做正例與反例測試。
2
決定是否需要自訂 event_name先查 Enhanced Measurement、自動收集與建議事件，再對照團隊事件字典。只有現有事件無法表達需求時才新增，並記錄名稱、參數、觸發時機與負責人。
3
填好 prompt 後，在 GTM Preview 模式驗證再 PublishAI 給的設定步驟照做完，一定要先開 GTM Preview + GA4 DebugView 確認事件有觸發、參數有值，再按 Publish。跳過驗證直接 Publish 是最常見的錯誤。

(4) Publish 前的停止條件、回復方式與證據截圖清單

先決條件：先確認既有 GA4 事件沒有表達這個行為。若網站已在成功動作推送 dataLayer event，就直接以該事件建 Trigger；若沒有，selector 先標成待查，不能只從按鈕文案推測。
1. Variables → 只啟用本次驗證需要的 Click／Page 變數；商品 ID 只有 dataLayer 已提供時才建立 Data Layer Variable
      2. Triggers → 用實測的 dataLayer event 或穩定屬性限定頁面與目標元素，並準備一個不應觸發的反例
      3. Tags → 建立 GA4 Event，套用團隊核准的事件名稱與參數；沒有來源的值留待查
      4. Preview → 分別做正例、反例與同意情境，在 Tag Assistant 核對觸發次數和參數，再到 DebugView 確認同一事件只出現一次
Publish 前檢查：(1) 接受／拒絕／部分接受符合政策 (2) Tag 未誤觸發到其他頁面 (3) 參數值正確且沒有 undefined (4) 事件未與 Enhanced Measurement 重複
C 軌完成結果：故障 trace 的 Consent default 出現太晚，而且 denied 狀態仍觸發 generate_lead；修復位置分別是 Consent Initialization 與事件 tag 的 consent checks。measurement-decision.md 的狀態填 CONFIG REVIEW PASS，平台證據欄填 PENDING。
通過條件是完成檔案能指出來源、正例、反例、同意狀態、修復位置與目前證據等級。若輸入沒有 DOM／dataLayer 證據，正確答案是列出待查資料，不是產生一個看似完整的 selector。
GTM 自訂事件心法：先有 Consent default／update，再 Preview 三種同意情境，最後才由核准者 Publish。沒有來源的參數留白，不讓 AI 猜。
