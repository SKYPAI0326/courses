# 隱私與進階：同意模式、Google 代碼閘道、伺服器端與 Meta 轉換 API
事件能送出只是起點，還要依使用者選擇控制傳輸，並避免同一行為被重複計算。
本節完成物：山徑咖啡的同意設定與去重決策

## 先讓量測遵守使用者選擇

上一頁完成三個自訂事件，這一頁集中處理同意模式。同意介面把預設與更新狀態傳給 Google 代碼，GTM 據此決定標籤行為；組織仍要確認隱私政策、資料用途與法律。

同意模式 v2 包含 `analytics_storage`、`ad_storage`、`ad_user_data`、`ad_personalization`。基本模式在同意前不載入 Google 代碼；進階模式先載入並送出無 Cookie 訊號。Google 的歐洲使用者同意政策涵蓋歐洲經濟區、英國與瑞士；其他義務由組織確認。[Google 同意模式概念](https://developers.google.com/tag-platform/security/concepts/consent-mode)與 [Google Ads 政策說明](https://support.google.com/google-ads/answer/16724512)（2026-11 查證）。

順序是先建立預設狀態，再載入標籤，使用者選擇後更新。練習頁測試「未選擇、接受全部、只保留必要」，記錄四項狀態、預期行為與證據。本節只在這裡處理同意模式。

## 進階傳輸選項解決不同問題

Google 代碼閘道（Google tag gateway，原名第一方模式）用自有網域載入代碼與傳送量測資料，需要自有網域及 CDN、負載平衡器或網頁伺服器。[Google 代碼閘道說明](https://developers.google.com/tag-platform/tag-manager/gateway)（2026-11 查證）。

伺服器端代碼先讓資料進入組織控制的容器，再決定轉送平台；它需要主機、部署與維運。[GTM 伺服器端代碼介紹](https://developers.google.com/tag-platform/tag-manager/server-side/intro)（2026-11 查證）。

GTM 自 2025-04 起會在特定 Google Ads／Floodlight 情境先載入完整 Google 代碼；自 2026-10-08 起，設定會以 `gtag.config` 出現在資料層。萬用自訂事件觸發條件要排除它。[GTM 版本資訊](https://support.google.com/tagmanager/answer/4620708)（2026-11 查證）。

## 山徑咖啡示範：同意、資料層與去重

本頁材料分工如下：

| 材料 | 用途 |
|---|---|
| 三個事件設定 | 測試不同同意狀態的標籤行為 |
| 練習包同意情境 | 練習正常順序與故障修復 |
| 品牌包購買事件 | 設計瀏覽器端與伺服器端去重 |

先開 [山徑咖啡預約練習頁](assets/practice/booking-practice.html) 與 [GA4 × GTM 共用量測練習包](assets/datasets/measurement-practice-kit.md)。頁面載入時先送 `consent default`，四項都是 `denied`；按「接受全部」後送 `consent update`，四項改為 `granted`；按「只保留必要」則送更新並維持四項 `denied`。重新整理會回到尚未選擇的預設狀態。這段固定行為用來觀察同意更新順序，正式網站仍要依實際政策與同意介面設計各用途。

再看購買事件。電商資料層每次送出新物件前，先推送 `ecommerce: null` 清空舊資料，再推送 `purchase` 與品牌包定義的 `transaction_id`、`value`、`currency`，避免舊值殘留；`items` 只示範 GA4 電商格式，不是山徑咖啡品牌包已定義的必填參數。練習頁沒有真實交易，因此只寫契約，不假造購買結果。

Meta Pixel 與轉換 API 同送一筆購買時，瀏覽器端 `eventID`、伺服器端 `event_id` 及事件名稱要一致才能去重。[Meta 轉換 API 去重說明](https://developers.facebook.com/docs/marketing-api/conversions-api/deduplicate-pixel-and-server-events)（2026-11 查證）。山徑咖啡由訂單系統產生共用唯一 ID；缺少成功訊號與 ID 來源時先寫規格，維持待實測。

## 換你做：完成同意與去重決策

用練習頁填三種同意情境表：重新整理後不選，記錄四項預設拒絕；按「接受全部」，記錄四項同意；再次重新整理後按「只保留必要」，記錄四項拒絕。每列附 Tag Assistant 的狀態、代碼與事件證據，再依故障紀錄重排操作順序。

再為 `purchase` 寫去重卡：發生時機、唯一 ID 來源、兩端欄位、事件名稱、重複測試、付款失敗反例與資料層清空。常見卡關是把工具當法律結論、兩端各生 ID，或重新整理就再送購買；修法是分開政策與技術責任，由訂單系統提供共用 ID，並以交易狀態控制送出。

## 模組作業：一個點擊的旅程

### 個人準備

每人帶上三個事件與追蹤規格。用 10 分鐘選一個事件，補齊觸發條件、變數、事件名稱、參數、正例與反例；另寫可用的網站、容器與 GA4 權限。

### 小組討論

用 25 分鐘實測一個事件。有網站的組在測試環境預覽；沒有網站的組開啟 [山徑咖啡預約練習頁](assets/practice/booking-practice.html)，在網址加入 `?gtm=` 與自己的容器 ID。記錄互動、資料層事件、代碼觸發、參數與 GA4 即時報表；再補一個反例。

### 上台分享

每組 4 分鐘展示「一個點擊的旅程」：使用者操作、網站訊號、GTM 成立條件、GA4 收件與畫面證據。沒有正式網站權限的組要註明成果來自練習頁。

### 回饋

講師依「事件名稱、觸發條件、驗證證據三者一致」講評。也可在實測完成後，把追蹤規格與驗證紀錄的全部文字貼進新對話，請 AI 依同一判準指出最多三個缺口；平台是否通過仍由小組依實測畫面判定。

```text
檢查這份追蹤規格與驗證紀錄。依事件名稱、觸發條件、變數與參數、正反例、預覽證據五項判準，列出最多三個不一致處與需要補的證據；只使用貼上的內容。
```

### 放進企劃書

依 [小組企劃書範本](assets/datasets/group-project-guide.md)，把三個事件的追蹤規格、實測的一個事件路徑、同意設定與去重決策放進「成效指標與追蹤」段。下一個廣告模組會使用這些可信事件判斷該不該投、要看哪個關鍵事件；課堂練習頁證據只代表練習環境。
