單元 6-1

GA4 建置：帳號架構與介面導覽

GA4 是 Google Analytics 目前的分析平台世代。這節課從帳號架構、資料串流到必要設定建立操作地圖；介面名稱與位置可能依權限或版本調整，應以功能目的和驗證結果為準。

學習目標 OUTCOMES
能說明 GA4 的三層帳號架構（帳戶/資源/資料串流）及各層的功能
能在 GA4 介面中找到並說明五大功能區塊的用途
能依自己的練習軌完成 GA4 基礎設定檢核，並區分已驗證、待處理與不適用
1
先選共同起點：A 軌使用自己的 GA4 資源；B 軌登入 Google Analytics demo account 練習報告與探索；C 軌使用 GA4 × GTM 共用量測練習包。三軌都建立 ga4-setup-check.md；B／C 軌只能記錄介面觀察與設定決策，不得宣稱完成自己的帳號建置。
ACCOUNT STRUCTURE · 帳號架構

三層架構，分清楚才不會亂

GA4 的帳號結構分三層，每層有不同的功能範疇。理解這個架構，能避免「資料跑到哪裡去了」的常見困惑。

帳戶
Account
最高層，通常對應一個組織或公司。管理用戶權限（誰可以看哪些資料）、連結 Google Ads 帳號、管理帳單。一個 Google 帳號可以建立多個 GA4 帳戶。
資源
Property
對應一個品牌或產品線。資源包含所有報告、事件設定、受眾建立。一個帳戶可以有多個資源（如：官網和 App 各一個資源）。
資料串流
Data Stream
資料進入 GA4 的入口。每個網站或 App 是一個資料串流。在這裡取得追蹤代碼（G-XXXXXXXX）安裝到網站。一個資源可以有多個串流（Web + iOS + Android）。
INTERFACE OVERVIEW · 介面導覽

GA4 左側選單，五大功能區

🏠
首頁
智能摘要與快速洞察。GA4 會自動標記異常數據和趨勢。是每次進入 GA4 的第一站。
📊
報告
預建報告：流量獲取、參與度、營利、留存率、客層。日常數據查看的主要區域。
🔍
探索
自訂分析工具：漏斗、路徑、區隔重疊等。可以回答「標準報告無法回答的問題」。
📣
廣告
連結 Google Ads 後的廣告效益分析、歸因模型比較、觸達程度報告。
⚙️
管理
帳戶設定、資源設定、事件與關鍵事件管理、產品連結、受眾建立。建置期最常使用的區域。
BASIC SETUP · 基礎設定清單

安裝完代碼後，還要做這五件事

1
延長資料保留期到 14 個月
預設只保留 2 個月的事件數據（探索分析用）。路徑：管理 → 資源設定 → 資料保留 → 選擇 14 個月。
2
排除內部流量
避免自己測試網站的行為污染數據。路徑：管理 → 資料串流 → 設定 → Google 代碼 → 定義內部流量 → 填入辦公室 IP。
3
把重要事件標記為關鍵事件
先建立或確認能代表重要行為的事件（如 purchase、generate_lead），再到管理 → 資料顯示 → 事件，將它標記為「關鍵事件」。若要用於 Google Ads 出價，再由這個 GA4 關鍵事件建立 Google Ads conversion；兩個名詞不能混用。
4
連結 Google Search Console
讓 GA4 能看到 SEO 關鍵字搜尋數據。路徑：管理 → 產品連結 → Search Console 連結 → 選擇 GSC 資源。
5
驗證追蹤代碼是否正常運作
安裝後先用 Google tag 的測試／Tag Assistant 檢查連線，再用 GA4 DebugView 或即時報告確認事件與參數。瀏覽器擴充套件不是唯一驗證方式，也不能取代事件內容檢查。
💡
建議使用 GTM 安裝 GA4：透過 Google Tag Manager 管理 GA4 代碼，可以不修改網站程式碼就新增或調整追蹤設定。M7 會詳細講解 GTM 操作。
AI 接口 · GA4 建置自我檢核

三行設定描述 → AI 給你「正常 vs 該檢查」清單

第一次建 GA4 最容易遺漏 key event、UTM 追蹤、跨網域與權限確認。下面 prompt 讓 AI 依你的描述整理待檢查項目；實際選單與資料仍要由帳號畫面驗證。Realtime 與 DebugView 用來先確認資料正在收集，許多標準報表與探索則可能需要 24–48 小時處理，兩者不能混成同一個等待門檻。核對：Google Analytics：確認資料是否正在收集。

把這段貼進任意生成式AI
我正在檢查 GA4，請把「當下可驗證」與「需要等待報表處理」分開列出。 【網站類型】[企業官網 / 電商 / 部落格 / Landing Page] 【主要轉換目標】[註冊 / 購買 / 預約 / 下載] 【已設定的事件】[列出你能想到的] 【還沒處理的事】[誠實寫] 請輸出檢核表 + 紅綠燈標示 + 期望即時報告會看到什麼資料。
可接受的參考輸出

| 項目 | 狀態 | 怎麼確認 |
|---|---|---|
| 基本追蹤代碼 | 🟢 實測後判定 | 即時報告與 DebugView 看得到自己的測試事件 |
| 主要事件標為 key event | 🟡 需確認 | Admin → Data display → Events → 標記關鍵事件 |
| Google Ads conversion | 🟡 投放才需要 | 確認帳號連結後，由 GA4 key event 建立或匯入 |
| 跨網域追蹤 | 🟡 有多個網域才適用 | 實測跨網域流程，確認 session 與來源沒有異常重啟 |
| UTM 參數測試 | 🟡 需測試連結 | 使用已記錄的 UTM 連結進入，再檢查流量獲取報告 |
| 內部流量過濾 | 🟡 需依環境設計 | 先在測試狀態驗證，不直接啟用可能誤刪資料的過濾器 |

第一批資料的判讀原則：先用可重現的測試動作確認事件名稱、參數與觸發次數。出現 0 或異常高低的數字時，回到 DebugView、GTM Preview 與過濾條件查證，不用固定百分比直接判定原因。

先用 Realtime／DebugView 檢查事件是否送達，再為可能需要 24–48 小時處理的標準報表記錄複核時間。若當下沒有事件，不要用「報表還在處理」略過 Tag ID、觸發條件、同意狀態與 Preview 連線檢查。
GA4 建置心法：裝完不等於驗證完成。事件要在 DebugView 重現、重要事件要標成 key event；需要廣告最佳化時，才再建立 Google Ads conversion。UTM、跨網域與內部流量依實際環境測試。
PRACTICE · 三軌共同設定檢核

同一份完成物，誠實標示證據層級

請建立 ga4-setup-check.md，先寫練習軌、資料來源與你能使用的權限，再逐項記錄帳戶／資源／資料串流、資料保留、內部流量、key event、Search Console 連結與追蹤驗證。每一項只能填「已驗證」「待處理」或「不適用」，並附理由；不要把 AI 建議直接填成綠燈。

依權限選擇練習軌

A｜真實環境軌：用自己的資源完成檢核，為每個「已驗證」留下畫面、設定路徑或測試紀錄編號。事件必須在 DebugView 或即時報告重現，才能把平台狀態寫成 PLATFORM VERIFIED；尚未出現就維持 PENDING。

B｜Google Demo 軌：找到首頁、報告、探索、廣告與管理五個區域，記錄哪些資料可以查看、哪些管理設定沒有權限修改。你能證明的是介面與報告觀察，不是自己的網站已安裝。

C｜離線案例軌：把練習包的「日日沖煮」當作單一網域電商：主要 key event 是 purchase，尚未提供辦公室 IP、Search Console 所有權或 DebugView 紀錄。這些項目都應寫「待處理」，並補上需要的權限與下一個驗證動作。

獨立驗收：互評者隨機抽兩項「已驗證」，必須能打開對應證據；再抽一項「待處理」，必須看得到所缺權限、負責人與檢查日期。A 軌依真實證據選 PLATFORM VERIFIED 或 PENDING；B／C 軌一律維持 PENDING。

請保留這份 ga4-setup-check.md。進入 M7 時，將練習軌、GA4 可用條件與平台狀態帶入 measurement-decision.md；這是 readiness 交接，不代表 GTM 已安裝或通過驗證。

完成的是可追溯的設定檢核，不是把清單全部塗綠。找不到證據時保留待處理，反而比猜測平台狀態更接近真正的量測工作。
