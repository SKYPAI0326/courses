單元 5-5

技術 SEO：讓 Google 能順暢爬取

最好的內容，如果 Google 爬不到、載入太慢、在手機上破版，排名就是空談。技術 SEO 是 SEO 的地基，確保搜尋引擎能順暢理解並索引你的網站。

學習目標 OUTCOMES
能說明 Core Web Vitals 三項指標的意義與及格門檻，並指出改善方向
能識別常見的技術 SEO 問題（301、Canonical、HTTPS、robots.txt），並說明各自的用途
能用 Google Search Console 的「網址審查」和「Core Web Vitals」報告，診斷基本技術問題
CORE WEB VITALS · 核心網頁指標

Google 的使用者體驗評分卡

Core Web Vitals（CWV）用來衡量真實使用者的載入、互動與視覺穩定體驗。Google 目前建議的良好門檻是 LCP 2.5 秒內、INP 200 毫秒內、CLS 0.1 內；PageSpeed Insights 的欄位結果以過去 28 天資料的第 75 百分位判定。這些訊號是搜尋與使用體驗的一部分，不能把單一 Lighthouse 分數換算成排名升降。開課時請核對 Google Search Central 的 CWV 說明與PageSpeed Insights 資料定義。

LCP
Largest Contentful Paint
最大內容渲染
良好：≤ 2.5 秒
頁面上最大的視覺元素（通常是首圖或 Hero 區塊）載入完成所需時間。影響因素：圖片大小、伺服器回應速度、阻擋渲染的 JS。
INP
Interaction to Next Paint
互動到下一次渲染
良好：≤ 200ms
用戶點擊/輸入後，頁面多快給出視覺回饋。取代舊指標 FID。影響因素：JS 執行負擔、主執行緒阻塞。
CLS
Cumulative Layout Shift
累積版面移動
良好：≤ 0.1
頁面載入過程中，元素「突然跳位」的程度。影響因素：未設定尺寸的圖片、動態插入廣告、字體載入導致排版跳動。
🔧
診斷工具：PageSpeed Insights 可同時查看可取得的欄位資料與單次實驗室診斷，Search Console 的「Core Web Vitals」報告可看 URL 群組趨勢，Chrome DevTools Lighthouse 適合重現與除錯。三者用途不同，不能用單次分數取代真實使用者資料。
TECHNICAL CHECKLIST · 技術清單

網站健康度，六個必查項目

🔒
HTTPS 加密：所有正式頁面都應通過 HTTPS。HTTP 會造成瀏覽器安全警示，也無法提供完整的傳輸保護；確認憑證有效、HTTP 正確轉址到 HTTPS，且頁面沒有 mixed content。
📱
行動裝置相容：Google 使用行動版內容進行索引。以 Chrome DevTools／Lighthouse、真實手機與 Search Console 的網址審查交叉檢查，確認主要內容一致、沒有水平溢出，文字與操作元件可用；不要再引用已下線的 Mobile-Friendly Test。
🗺️
XML Sitemap：把希望被發現的 canonical URL 列入 sitemap 並提交 GSC，協助 Google 發現網站內容；提交不保證每個 URL 都會被抓取或索引。CMS 是否自動產生及更新 sitemap，須依實際版本檢查。
🤖
robots.txt：控制哪些頁面允許爬蟲抓取。確認沒有意外封鎖重要頁面（常見錯誤：Disallow: / 封鎖整個網站）。網址格式：yoursite.com/robots.txt
🔗
內部連結結構：用一致、可爬取的連結讓重要頁面能從相關導覽或內容被找到，並檢查沒有其他頁面連入的孤立頁。點擊層級要依網站規模與任務設計，不套用固定三次門檻。
🖼️
圖片優化：依實際顯示尺寸提供 srcset／sizes，視相容性使用 WebP 或 AVIF，並為有資訊意義的圖片撰寫描述用途的 alt；裝飾圖使用空 alt。檔案大小要以畫質、裝置與連線實測決定，不用固定 KB 或塞入關鍵字。
REDIRECTS & CANONICAL · 重定向與標準化

避免重複內容：Canonical 與 301

常見的 HTTP 狀態碼與 SEO 影響
301
永久重定向——當內容確定搬到新位置時使用；Google 將目標 URL 視為 canonical 的強訊號。應直接指向最相關的新位置並避免不必要的 redirect chain。Google 官方 redirect 說明
302
臨時重定向——內容只是暫時改到另一個位置時使用；Google 通常仍把來源 URL 當作 canonical 訊號。不能簡化成「完全不傳遞權重」，重點是移動是否永久以及希望搜尋結果保留哪個 URL。
404
頁面不存在——內容已移除且沒有合理替代頁時，回傳 404 或 410 是正確結果；若內容搬家且有清楚對應的新頁才設 301。大量重要 URL、soft 404 或錯誤內部連結需要診斷，但不能看到 404 就一律導向首頁。Google 官方排錯說明
Canonical
偏好的代表版本——多個 URL 相同或非常相似時，可用 rel="canonical" 表明偏好；它是強訊號，但 Google 仍會綜合 redirect、sitemap、內部連結與內容選擇代表 URL。一般重複內容不等於遭到懲罰。Google 官方 canonical 說明
💡
行銷人的重點：技術 SEO 的大部分工作是開發或 IT 的職責。行銷人需要能診斷問題、提出需求，而不是親自修改 server 設定。學會用 GSC 和 PageSpeed Insights 診斷，再交給技術團隊處理。
AI 接口 · 技術 SEO 報告寫給工程師

PageSpeed 截圖 → AI 翻成可發工單的需求

行銷人最常卡在「我知道技術 SEO 有問題、但不知道怎麼跟工程師說」。下面這個 prompt 讓你貼 PageSpeed Insights 與 GSC 數據，AI 翻成「工程師看得懂、可立刻動工」的工單。

1
取得 PageSpeed 數據前往 pagespeed.web.dev，輸入你的網站首頁 URL，分開記錄真實使用者欄位資料與 Lighthouse 實驗室數據。行動版與桌機版都要保留，不用單次分數推定排名影響。
2
取得 GSC 索引數據進 Google Search Console → 索引 → 網頁。記下「已索引」「未建立索引」頁數、主要原因與一個代表 URL。沒有 GSC 或權限不足時先標記阻塞，不讓 AI 猜。
3
填入下方 prompt，取得可直接傳給工程師的工單把你最重要的 3-5 個轉換頁面 URL 也填進去——AI 會依重要性排序修復優先序，讓你知道先修哪頁 ROI 最高。
把這段貼進 ChatGPT 或 Claude
請扮演技術 SEO 顧問，把下面的數據翻譯成工程師看得懂的工單。 【PageSpeed 主要警告】 - LCP（Largest Contentful Paint）：[X 秒] - CLS（Cumulative Layout Shift）：[X] - INP（Interaction to Next Paint）：[X 毫秒] - 其他 Lighthouse 分數: [Performance / Accessibility / Best Practices / SEO] 【GSC 涵蓋範圍狀態】 - 已索引：[X 頁] - 已排除：[X 頁] / 主要排除原因：[列出 top 3] - 已發現尚未索引：[X 頁] 【最重要的轉換頁面 URL】 [填入 3-5 個] 請輸出： (1) 3 個最該優先查證的問題（依轉換頁重要性、受影響 URL 數與重現證據排序） (2) 每個問題的「工單格式」：標題 / 已知證據 / 影響假設 / 重現步驟 / 期望結果 / 驗收標準；不要憑空估排名損失或工時 (3) 哪些是行銷端可自己處理、哪些需要工程師分別列出 (4) 修完後如何驗收（哪天再跑一次 PageSpeed + GSC 看什麼指標變化）
參考工單｜先寫證據，再寫影響假設

3 個優先修的問題

1. LCP 4.2s（良好門檻為 2.5s 內）：首屏圖片候選尺寸、格式或載入優先順序可能不當，需用 waterfall 查證
2. GSC 顯示 856 個重複 URL 的 canonical 狀態需要抽樣，先比較使用者宣告與 Google 選擇的代表 URL
3. CLS 0.18（良好門檻為 0.1 以下）：橫幅載入可能造成版面位移，需在可重現頁面確認

工單 #1（LCP 圖片優化）

標題：[SEO] 首屏 LCP 圖片載入優化
已知證據：行動版測試的 LCP 為 4.2s；需再核對 Search Console 欄位資料與受影響 URL 群組
影響假設：首屏圖片可能降低使用者體驗；無法僅由這個數值推算排名會下降幾名
重現：開 PageSpeed Insights 跑 / 連線、檢查首屏 hero image 大小
期望：依裝置與連線測試選擇合適尺寸及 WebP／AVIF；LCP 主圖不使用 lazy loading，修正後以相同條件重測
驗收：在同一 URL、裝置條件與測試方式下重跑；記錄 LCP 與頁面視覺是否正常。工時由工程師評估

工單 #2（Canonical 處理）

標題：[SEO] 抽查重複 URL 的 canonical 訊號
已知證據：GSC 顯示 856 個 URL 屬重複／canonical 相關狀態；尚未確認哪些是預期排除
影響假設：使用者宣告、內部連結、sitemap 與 Google 選擇的 canonical 若不一致，可能讓希望曝光的版本不易被選為代表 URL
重現：用網址審查抽查 5 個代表 URL，逐一記錄 declared canonical、Google-selected canonical、HTTP 狀態、內部連結與 sitemap
期望：只有真正相似的頁面才合併訊號，所有 canonical 指向可索引且最適合使用者的代表 URL
驗收：部署後重新抓取代表 URL，確認頁面原始碼、HTTP header、內部連結與 sitemap 訊號一致；GSC 尚未更新時保留待追蹤，不設定流量必升的門檻
工時與風險：由工程師確認 CMS template 影響範圍後評估

分工建議

• 行銷可自做：整理重要 URL、確認偏好的代表版本、標記哪些 GSC 排除屬預期，並提供原始圖片與版位需求
• 需工程師：修改 CMS canonical 邏輯、redirect 與圖片載入策略，並評估 template 影響範圍

驗收時程：部署後先用相同條件重跑實驗室測試與原始碼檢查；欄位資料、重新抓取與 GSC 報告依各自更新時間另列追蹤日期，不用單一截止日承諾排名結果。

合格工單必須把「已知證據」與「影響假設」分開，提供可重現步驟及不依賴排名保證的技術驗收。AI 不知道 CMS、部署流程與受影響範圍；缺資料時保留待查，由工程師估工。
技術 SEO 行銷人的角色：診斷 + 翻譯 + 驗收，不是親自改 server。把工程師當合作夥伴，給他們「可直接 estimate」的工單比給他們「我的 SEO 排名變差」更有效。
