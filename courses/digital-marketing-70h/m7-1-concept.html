GTM 四元素：容器、代碼、觸發條件、變數

01

報表收得到資料，起點是一列可執行的追蹤規格

GA4 報表只有在網站真的送出事件後才會有資料。行銷人因此要先說清楚三件事：收什麼行為、什麼時候收、值從哪裡取得。這份事前約定叫做追蹤規格；完成後，網站人員知道要提供什麼訊號，設定者知道如何收件，驗收者也知道怎樣算通過。

一列完整規格要同時描述使用者操作、網站訊號、觸發條件、變數、送往 GA4 的事件與參數，以及正例與反例。正例是應出現事件的操作；反例是不應出現事件的相近操作。兩者成對，才能抓出漏送與過度觸發。網站還沒有現成訊號時，規格也可成為工程需求單，明列時機、欄位、型別、來源、個資邊界與驗收方式。

02

GTM 四元素把一筆行為送到正確目的地

Google 代碼管理工具（Google Tag Manager，GTM）是在網站安裝一次容器程式碼後，透過網頁介面集中管理追蹤代碼的工具。Tag Manager 基本概念（2026-11 查證）。它的四個核心元素可用一家線上書店的「加入購物車」理解：

  • 容器（Container）：裝在一個網站或 App 上的一整套代碼、觸發條件、變數與設定，容器 ID 以 GTM- 開頭。例：書店官網使用一個網頁容器。
  • 代碼（Tag）：決定把什麼資料送到哪裡，例如 Google 代碼（Google tag）、GA4 事件代碼、Google Ads 代碼或 Meta 像素。例：把加入購物車事件送往指定 GA4 資源。
  • 觸發條件（Trigger）：決定什麼時候執行代碼。例：網站確認商品加入購物車時才觸發。
  • 變數（Variable）：提供判斷或送出時要讀取的值。例：商品分類與商品數量。

四者的關係是：「在這個容器裡，當觸發條件成立時，代碼讀取變數並送出資料。」容器裝錯網站，整套設定不會出現；代碼目的地錯，資料會進錯資源；條件過寬會誤送；變數來源錯則得到空值。

變數分為兩類。內建變數由 GTM 提供，常見的有點擊 ID、點擊 Class、點擊文字、網頁網址、表單 ID 與捲動深度門檻。資料層變數則讀取網站交給 GTM 的值。內建變數清單（2026-11 查證）。資料層（dataLayer）是網站把事件與參數交給 GTM 的 JavaScript 資料結構；行為發生時可用 dataLayer.push() 推送 {event: 'add_to_cart', product_count: 1}。資料層要在容器程式碼之前宣告。資料層說明（2026-11 查證）。

代碼優先選用 GTM 內建範本；自訂 HTML（Custom HTML）只用在沒有合適範本時，並先檢查程式碼的安全與效能。自訂代碼說明（2026-11 查證）。

03

觸發類型與發布流程決定設定何時生效

同一個容器會遇到不同互動，因此設定前要先選對觸發條件。網頁瀏覽適合頁面載入；點擊分成所有元素與只限連結；表單提交監看送出；捲動深度監看百分比或像素門檻；自訂事件在資料層出現指定 event 名稱時觸發；初始化（Initialization）讓需提早載入的代碼位於一般頁面觸發之前；同意初始化（Consent Initialization）則早於所有代碼，用來設定同意預設。點擊觸發條件、自訂事件觸發條件、同意初始化（2026-11 查證）。

直接安裝追蹤時，每次調整通常都要修改網站程式碼；GTM 安裝好 <head> 與 <body> 的兩段容器程式碼後，多數代碼與觸發條件可在介面管理。它也提供預覽模式（Preview）：用 Tag Assistant 連線測試分頁，查看事件、代碼觸發狀態與變數值。每次發布會留下版本，可回到舊版本；正式核准流程只屬於 Tag Manager 360，標準版以使用者權限控管，最後由有發布權限的人發布。版本與核准說明（2026-11 查證）。新增資料層事件與同意管理工具仍會需要工程協作。

完整流程依序是：建立帳戶與容器 → 網站安裝兩段容器程式碼 → 設定同意預設 → 建立代碼與觸發條件 → 使用者選擇後更新同意 → 預覽驗證 → 發布。下一節會建立資源、容器與 Google 代碼並操作預覽；再下一節建立事件代碼；模組最後集中設定同意。

示範把同一套八個欄位完整寫兩次，讓後面的個人練習有可對照的格式。先開啟山徑咖啡品牌包第 11 節與山徑咖啡預約練習頁。

05

完成預約與加入 LINE 要沿用同一組欄位

個人練習要補完另外兩列，完成後四個互動才都有能交給設定者的規格。請只從品牌包第 11 節與練習頁取材；先操作頁面並查看最近五筆事件監看區，再填表。

  1. 為 booking_complete 與 line_join 各填一列：使用者操作、網站訊號與推送時機、觸發條件、讀取的變數、GA4 事件名稱與參數（含型別）、應出現的測試、不應出現的測試、要向網站或工程確認的事。
  2. 檢查事件名稱是否逐字一致，參數有沒有來源與固定型別，測試是否能分辨正例和相近反例。
  3. 確認事件與參數沒有姓名、Email、電話；自由輸入內容改以固定分類或非個人資料的值表達。

先用自己的操作紀錄完成兩列，再展開下方方向檢查判斷是否完整。

做完再展開：參考方向

完成預約要以網站確認必要欄位通過並送出為界線；加入 LINE 要以實際按鈕互動為界線。兩列都應寫出網站推送、GTM 收件與 GA4 命名的關係，並各用一個相近但不成立的操作驗證觸發範圍。

06

四列規格會直接變成下一節的預覽清單

這一節的完成物是四列追蹤規格，不是已安裝的追蹤。下一節會先建立自己的容器與 Google 代碼，讓練習頁在網站監看區與 Tag Assistant 顯示四個資料層事件；GA4 事件代碼則在後續設定。模組作業選出的三個代表旅程事件，也會沿用這八個欄位寫成工程需求與驗收清單。
