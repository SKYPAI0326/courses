單元 7-1

GTM 核心概念：四元素心智模型

GTM 的常見追蹤設定，會用到四個核心元素：容器、代碼、觸發條件、變數。理解它們的關係後，就能讀懂設定、找出缺少的資料，並在發布前驗證。

學習目標 OUTCOMES
能用自己的話解釋 GTM 四元素（容器/代碼/觸發條件/變數）及其相互關係
能說明 GTM 與直接在網站安裝追蹤代碼的差異，以及使用 GTM 的核心優勢
能說明如何用 GTM 預覽模式（Preview）檢查代碼是否在預期事件與同意狀態下觸發
FOUR ELEMENTS · 四元素

GTM 的積木系統

GTM 就像一個智慧型容器，放在你的網站上。這個容器裡裝著你設定的各種追蹤代碼，並根據你定義的條件，決定何時觸發哪個代碼。所有複雜的設定，都是這四個元素的組合。

📦
容器
Container
用來集中保存網站或 App 的 Tag、Trigger 與 Variable。網站必須先正確安裝容器；新增 dataLayer、同意管理或網站功能時，仍可能需要修改網站與工程支援。
例：你的官網 = 一個容器（GTM-XXXXXXX）
🏷️
代碼
Tag
在條件符合時執行或傳送資料的設定，例如 Google tag 或 GA4 Event。優先使用合適的內建或審核過的模板；未支援的 Custom HTML 仍涉及程式碼、權限、安全與效能風險。
例：Google tag、GA4 Event tag、Meta Pixel 基礎代碼
⚡
觸發條件
Trigger
監聽頁面或 App 的事件，並在條件符合時讓 Tag 觸發。可以是頁面瀏覽、點擊、表單事件或 dataLayer 自訂事件；條件必須依真實網站資料設定。
例：當實際 dataLayer event 等於「generate_lead」時
🔢
變數
Variable
供 Tag 或 Trigger 使用的值。可使用 Page URL 等內建變數，也可建立 dataLayer 變數；變數名稱與值必須能從網站或事件契約取得。
例：{{Click Text}} = 用戶點擊的按鈕文字
💡
四元素關係：容器保存設定；Trigger 判斷何時觸發；Tag 決定要執行或傳送什麼；Variable 提供判斷與傳送所需的值。這是閱讀常見追蹤設定的心智模型，不代表每個需求都能只靠這四項完成。

兩個容易混淆的觸發器：Consent Initialization 只用於設定或更新 consent 的 tag，而且會早於其他 trigger；Google tag 等需要提早載入的一般 tag 使用 Initialization。發布前再用 Preview／Tag Assistant 檢查哪些 tag 觸發、哪些沒有觸發。核對：Tag Manager consent mode support、Preview and debug containers。

GTM WORKFLOW · 使用流程

從設定到發布，七步驟標準流程

Step 1
建立 GTM 帳號與容器：到 tagmanager.google.com 建立帳號，選擇「網站」容器類型。
Step 2
安裝 GTM 程式碼到網站：把 GTM 提供的兩段程式碼分別貼入 <head> 和 <body>。WordPress 可用外掛。
Step 3
先建立同意預設：依組織核准的 CMP／Consent Mode 設定，在 Consent Initialization 建立 default 狀態。不得先讓量測代碼觸發，再補 consent。
Step 4
建立代碼與觸發條件：例如 Google tag 使用 Initialization - All Pages；事件 tag 再依按鈕、表單或 dataLayer 事件觸發。
Step 5
設定 consent update：使用者接受、拒絕或變更選擇時更新 consent 狀態，並讓後續 tag 遵守該狀態。
Step 6
預覽模式驗證（Preview）：使用 Tag Assistant 逐一測試接受、拒絕、部分接受，確認 default／update、tag firing 與參數順序。
Step 7
核准後發布（Submit）：留下 Preview 證據、版本名稱與變更摘要；任一 consent 情境失敗就停止，修正後重跑。
GTM vs 直接安裝

為什麼要多一個中間層？

直接把追蹤代碼貼進網站也能追蹤，為什麼還要用 GTM？答案在於：彈性、速度、版本控管。

⚡
GTM 的核心優勢：
1. 降低部分日常調整成本：容器與事件資料已備妥時，部分 Tag 可不改網站版型就更新；新 dataLayer、同意或網站功能仍需工程協作
2. 版本控管：每次發布都有版本紀錄，搞錯了可以一鍵回滾
3. 集中管理：所有追蹤代碼在一個地方，不用在網站各處找散落的代碼
4. 發布前可預覽：用 Tag Assistant 檢查事件、Tag 與資料，再依核准流程發布
AI 接口 · GTM 4 元素配對

需要追蹤的事件 → AI 給你「Tag/Trigger/Variable」配置

理解 GTM 4 元素後，最常卡的是「我要追蹤這個事件，該怎麼配 4 元素」。下面 prompt 讓 AI 幫你拆解。

把這段貼進任意生成式AI
請幫我設計 GTM 配置追蹤以下事件： 【要追蹤的行為】[列出 3-5 個常見事件，如：點擊「立即試課」按鈕、提交「諮詢表單」、捲動頁面 75%、播放影片 50%、點擊外連] 【目標平台】[GA4 / Meta Pixel / 兩者皆需] 【實際頁面與事件資料】[網址、事件名稱、可用的 dataLayer 欄位；若是點擊再貼元素資訊或選擇器] 【同意需求】[哪些狀態可觸發；不知道就寫「待確認」] 請為每個行為輸出： - 對應的 Tag 類型 - Trigger 設定（觸發條件 + 元素選擇器） - 需要的 Variable - 該在 GA4 / Meta 後台對應做什麼設定 - Preview 要操作的測試步驟、預期觸發與不得觸發的情境 只能使用我提供的網址、事件、欄位與元素資訊。缺少 DOM 或 dataLayer 證據時標「待查」，不可猜選擇器，也不可宣稱可直接發布。
可接受的參考輸出（配置草案）

先寫事件契約：逐一說明要觀察的行為、送往哪個平台，以及事件名稱和必要參數。若事件名稱、dataLayer 或元素資訊未提供，就清楚列為待查，不能用看似合理的 /trial 或 #cta-button 代填。

再配對設定：每個行為各自列出 Tag、Trigger 與 Variable，並解釋資料從哪裡來。GA4 中只有對業務重要、且已確認正確蒐集的事件，才由負責人決定是否標成關鍵事件。

最後寫 Preview 驗收：列出會觸發、不會觸發與不同同意狀態的測試步驟。Tag Assistant 的事件序列、Tag 狀態與參數都符合預期後，草案才可送審；Preview 失敗就回到對應的 Trigger、Variable 或 consent 設定修正。

AI 可以協助整理配置，不能看見你的實際 DOM、dataLayer、權限與同意狀態。任何未由頁面或事件證據支持的選擇器與欄位，都必須維持待查。
GTM 的起點是要回答的問題與事件契約。再配置 Tag、Trigger、Variable，最後用 Preview 檢查該觸發與不該觸發的情境；沒有證據就不發布。
PRACTICE · 從辨識到獨立判讀

同一份 trace，先一起拆、再自己驗

沒有 GTM 容器也能完成本節概念練習。先建立 measurement-decision.md，再開啟 GA4 × GTM 共用量測練習包 的 Part 2。若已完成 M6-1，就從 ga4-setup-check.md 帶入練習軌、GA4 可用條件與平台狀態；若直接從 M7 開始，使用練習包並把 GA4 readiness 標為 PENDING。真實環境軌仍須在下一節以 Tag Assistant 留下平台證據。

D
老師示範：用正常 trace 指出 Container、Tag、Trigger、Variable 與 Consent，各自對應哪一列，以及為何 Consent Initialization 必須最早；把配對與證據列寫進 measurement-decision.md。
T
一起做：兩人一組把「預約體驗」拆成 Tag／Trigger／Variable；互相檢查事件名稱與參數是否能從案例需求找到，再把無來源欄位標成待查，不准讓 AI 補欄位。
S
獨立驗收：不看前例，在同一份 measurement-decision.md 判讀故障 trace，寫出至少兩個失敗證據、風險與修復位置，再重排正確順序。答案必須包含「default 太晚」與「denied 時事件仍觸發」；缺一即回到正常 trace 對照修正。
離線通過只標記 CONFIG REVIEW PASS；看到 Tag Assistant 與 GA4 的真實證據後，才能標記 PLATFORM VERIFIED。
