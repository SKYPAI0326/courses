看懂一條 Make 流程：從資料進來到通知送出

用一份已驗證的四模組 Blueprint，追蹤資料如何從 Google Sheets 進入 Gemini，再交給 Google Docs 與 Email；完成一張可交接的 v1-sheets 地圖，並練習把來源換成 Gmail。

學習成果
完成物：v1-sheets（第一版）四模組工作流地圖，包含順序、模組、角色、輸入、輸出、映射備註（來源 → 去向 → 用途）、失敗影響七欄。

(01)

先看一件工作如何被自動完成

今天的任務
阿凱要把一筆客戶回饋整理成主管可讀的報告、保存一份文件，再寄出同一份結果。今天先看懂資料如何從一個工作站交給下一個工作站，之後才有能力自己設定 Make。
現在：看試算表 → 手動請 AI 整理 → 複製到文件 → 寄信通知
目標：試算表的一列 → Gemini 整理 → Google Docs 保存 → Email 通知

這裡說的資料流，就是同一筆資料從來源欄位出發，依序經過處理、保存與通知；每一站都會留下下一站能讀的結果。你現在要追的不是四個工具名稱，而是「這一筆資料在每一站變成了什麼」。

先把四個詞放到同一張圖上：Make 是把服務接成自動化流程的平台；情境流程（Scenario） 是一條完整的自動化路徑；模組 是路徑中的一個工作站，接收輸入後交出輸出；Blueprint 則是把已完成的情境流程設定記錄成文字檔的流程食譜。

Blueprint 通常用 JSON 格式保存；你可以把 JSON 先理解成「用欄位記錄流程設定的文字格式」，本節只讀其中的模組、輸入與輸出，不要求你從零寫 JSON。

第一個練習會先給你一份去敏版（已移除連線與個資）的流程食譜與測試資料，請你按照資料流把四個工作站重畫成 v1-sheets 地圖（第一版）；等你能說清楚每個工作站的輸入與輸出，再把同樣的邏輯搬到 Make 畫面。接著只替換資料來源，做一個 v2-gmail 註記（第二版）。登入平台與 Google 帳號授權是之後實際執行時才需要的設定，不是本節的第一步。

◎
本節先學什麼　你要先能說出「哪一列資料進入哪個模組、產生什麼結果、下一站為什麼需要它」。本節不處理分流、資料格式轉換或人工審核控制，後續單元才會用實際模組示範。
(02)

四個工作角色，兩個跨模組問題

先用角色理解每個模組的工作，再用「映射」與「失敗影響」把模組接起來。角色是幫助閱讀的分類，不是 Make 官方的固定分類名稱。

工作角色白話問題本案例模組
資料來源第一批資料從哪裡進來？Google Sheets / Watch Rows
處理哪個模組把資料變成新內容？Gemini / Create a Completion
內容交付AI 結果保存到哪裡？Google Docs / Create a Document
通知誰會收到結果？Google Email / Send an Email

把每個模組想成一個工作站後，再補兩個 Make 介面常見的詞。模組每執行一次，會交出一小包本次資料，Make 稱它為 Bundle；在本案例裡，就是「這一列客戶回饋目前帶著哪些值」。Gemini 要做的工作說明，稱為 Prompt；你可以先把它理解成「告訴 AI 要讀哪些值、要產出什麼的文字指令」。

資料映射是把上一個模組交出的值，指定給下一個模組的欄位。在本案例中，{{2.result}} 讀取第 2 號（Gemini）模組的 result 欄位，接著同時成為 Docs 的內容與 Email 的內文；它不是第五種角色。失敗影響則要說清楚現象、負責人、修正位置、重跑點與停止狀態。

在這個案例裡，資料不是「經過四個工具」就算完成，而是沿著一條有因果的路徑移動：Sheets 先交出一列資料，Gemini 才能把其中三個值放進 Prompt；Gemini 完成後交出 result，Docs 與 Email 才能各自使用同一份文字。為了讓接手者看得懂這條路徑，我們在地圖中增加「映射備註」欄。

映射備註不是另一個輸出欄位，而是一句把箭頭說完整的話，至少回答三件事：「這個值從哪裡來？要放到哪裡？下一步為什麼需要它？」例如：Sheets 的位置鍵 3 代表回饋，所以把它放進 Gemini Prompt 的回饋欄；Gemini 產生的 result 再提供給 Docs 內容與 Email 內文。這樣讀者看到備註，就能從前因追到後果，而不是只看到幾個箭頭。

正例：位置鍵是匯出檔裡暫時使用的欄位編號；把 Sheets Bundle 的位置鍵 1、2、3 對照成姓名、評分、回饋，再寫出三個值如何進入 Gemini Prompt。非例：只寫「Sheets → AI → Email」，看不到欄位，也無法定位空白文件的原因。

i
閱讀習慣　文件空白時，先查 Gemini 是否產生 result、Docs 是否映射 {{2.result}}；不要一開始就重建整條流程。

示範：把 4 模組 Blueprint 讀成地圖

以下使用課程資產中的去敏（已移除連線與個資）Blueprint 與測試資料。請先開啟 去敏 Blueprint、測試資料 CSV，需要查欄位時再開啟 匯入對照 與 預期結果。你可以把 Blueprint 想成一份「已組好的流程食譜」：先看檔案裡列出的模組，再看每個模組的輸入與輸出，不必先讀懂整份 JSON 語法。placeholder（暫代文字）只代表「匯入後要重新綁定」，不代表你要把任何真實帳號寫進地圖。

Blueprint 裡的編號是模組 ID（平台用來辨認每個工作站的編號），不一定連號。本案例的 ID 是 1、2、7、8，真正的執行順序仍以流程中的排列為準；地圖另外使用 1–4 表示學習時的順序，避免把「模組身分」和「執行先後」混在一起。

匯出的 Bundle 有時只把欄位叫作位置鍵 1、2、3，沒有直接寫出姓名、評分、回饋。這就是為什麼要先用測試資料對照，再在地圖中補上工作上的語意；位置鍵不是新的資料，而是同一列資料在匯出檔裡的暫時名稱。本例的時間戳記位於位置鍵 0；Docs 會用位置鍵 0（時間）與 1（姓名）組成文件名稱，而 Gemini 只讀位置鍵 1、2、3。

示範輸入

先追一筆資料再讀表格：林小姐的「物流延遲，客服回覆太慢」先存在 Sheets 這一列的第 3 個位置；因此它會被放進 Gemini 的回饋欄。Gemini 產生 result 後，Docs 用它建立文件，Email 再用同一份 result 發出通知。下表的「映射備註」就是把這段前因後果寫給下一位接手者。

(04)

跟著做：完成一張可交接的地圖

現在把示範的判斷展開成七欄。每一步都先留下可觀察結果，再進入下一個模組；你可以使用 Google Sheets、Google Docs 或 Markdown，不需要先登入 Make。填寫「映射備註」時不要只抄箭頭，請用「來源值 → 目的欄位 → 下一步用途」說明為什麼這樣接。

起始狀態
準備 CH1-1-reference-4module.sanitized.blueprint.json、CH1-1-test-data.csv、CH1-1-import-map.md。如果無法開啟檔案，直接使用上一節的示範表。

先不要急著填箭頭。每一列的「映射備註」都要接回上一列的輸出，並說明這個值交給下一個模組後要完成什麼；例如先寫「Sheets 交出位置鍵 3」，再寫「它進入 Gemini 的回饋欄」，最後補上「因此 Gemini 才能產生供 Docs 與 Email 使用的 result」。

本節把跟做分成四個 Stage（階段）：S1 先認出來源欄位，S2 追 Gemini 的中間結果，S3 接上文件與通知，S4 只替換資料來源。步驟標籤的意思是：Demo 教師先示範、Together 全班同步跟做、Solo 你獨立完成、Check 停下來核對；它們是課堂節奏，不是 Make 的功能名稱。每個 Checkpoint（檢查點） 都是完成一段後的停站，確認前一段真的成立，才繼續往下接。

1
Together · 建立 v1-sheets 欄位（S1）
學員操作：建立「順序、模組、角色、輸入、輸出、映射備註（來源 → 去向 → 用途）、失敗影響」七欄，填入 1–4 與 Sheets、Gemini、Docs、Email。
預期結果：表格有四列，順序與示範一致，標題為 v1-sheets。
快速檢查：只看角色欄，能說出取得、處理、保存、通知的差異。
卡住時：欄位不足就回到 Stage S1 補齊，再從本步重做；不能建立表格時，複製示範表並標記「待轉入表格」。
2
Together · 對照來源 Bundle（S1）
學員操作：在 Sheets 列填入「輸入：試算表新增的一列」；輸出填「位置鍵 1、2、3」；映射備註改寫成完整句：「Sheets 先交出一列，位置鍵 1、2、3 分別代表姓名、評分、回饋，所以三個值會進入 Gemini Prompt。」。
預期結果：讀者知道這份匯出先用位置鍵，再由地圖賦予語意。
快速檢查：指出回饋的來源是 Sheets 位置鍵 3，不是 Gemini。
卡住時：若只寫「Google Sheets」，回到 Stage S1 改成實際值或位置鍵；修正後重做本步，不需清除其他列。
Checkpoint 1：來源欄位可追蹤

現在應該看到：Sheets 列有一列資料、位置鍵 1/2/3 與姓名／評分／回饋的對照。若沒看到：回到步驟 2。通過後才能繼續：把這三個值交給 Gemini。

3
Demo → Together · 對照 Prompt 與 result（S2）
學員操作：在 Gemini 列填入輸入 {{1.`1`}}、{{1.`2`}}、{{1.`3`}}；輸出只填 result；映射備註寫成因果句：「Sheets 的位置鍵 1、2、3 已進入 Gemini Prompt，因此 Gemini 產生 result，後續 Docs 內容與 Email 內文都讀 {{2.result}}。」。
預期結果：能完整讀出「Sheets 的第 3 個資料值進入回饋欄位，Gemini 產生一個 result，後面兩個模組都讀它」。
快速檢查：地圖沒有自行新增的 summary、reply_draft、needs_review。
卡住時：回到 Stage S2 對照 import-map；若 result 空白，保留來源列，修正映射後從 Gemini 重跑。
4
Together · 寫出 Gemini 失敗影響（S2）
學員操作：在 Gemini 列寫「result 空白或格式不符 → 流程負責人回到 Prompt／欄位映射修正 → 從 Gemini 重跑；保留原始輸入」。
預期結果：失敗欄位同時包含現象、負責人、修正位置、重跑點與資料保留方式。
快速檢查：另一個人看到這格，不需要猜要不要重新讀 Sheets。
卡住時：若只寫「Gemini 失敗」，回到 Stage S2 補完整句；仍無輸出就停在「待修正」，不要送空白到 Docs。
Checkpoint 2：result 是唯一中間輸出

現在應該看到：Gemini 只有 result，Docs 與 Email 都從它取值。若沒看到：回到步驟 3。通過後才能繼續：填寫兩個後續模組。

5
Together · 對照 Docs 與 Email（S3）
學員操作：Docs 列填入文件名稱 客服回饋：{{1.`0`}}-{{1.`1`}}、內容 {{2.result}}，輸出「文件名稱與 URL／ID」；映射備註寫「Sheets 的位置鍵 0（時間）與 1（姓名）組成文件名稱，Gemini 交出的 result 寫入文件內容，形成可保存的交付物」。Email 列填主旨 {{7.name}}、內文 {{2.result}}、課堂提供收件人，輸出「寄信狀態或 message ID」；先注意 7 是 Docs 的模組 ID，name 是文件名稱，所以它被用來組成 Email 主旨；再把映射備註寫成「Docs 保存同一份 result 後，Email 沿用它作為內文，讓通知與文件一致」。
預期結果：看得出兩個模組共用同一個 result，但各自交出不同狀態；文件 URL 不會自動變成 Email 內文。
快速檢查：若 Docs 沒有 URL，能說明要停在 Docs；若 Email 失敗，能從 Email 單獨重跑。
卡住時：回到 Stage S3 對照 import-map；若把 {{7.name}} 當成內文，改回主旨欄。修正後只重跑被修正的模組；不要清除已建立文件。
6
Check · 完成四列失敗影響（S3）
學員操作：逐列補上「現象 → 負責人 → 修正位置 → 重跑點 → 是否保留資料 → 無法修復時的停止狀態」。
預期結果：四列都能讓接手者判斷先查哪個欄位，以及何時停止。
快速檢查：遮住模組名稱，只看失敗影響，仍能區分來源、Gemini、Docs、Email。
卡住時：回到 Stage S3 的示範表逐列比對；缺少停止狀態就補「待修正，不送出下游」。
Checkpoint 3：v1-sheets 可以交接

現在應該看到：四列都有輸入、輸出、映射與失敗影響，result 從 Gemini 流到 Docs 與 Email。若沒看到：回到缺欄位的步驟。通過後才能繼續：複製地圖做來源轉移。

7
Solo · 建立 v2-gmail 轉移註記（S4）
學員操作：複製 v1-sheets 成 v2-gmail；只把來源改成 Gmail／Watch New Emails，輸入欄位改成 sender、subject、body。在 Gemini 映射備註寫「來源改成 Gmail，所以 sender、subject、body 取代 Sheets 的位置鍵並進入 Prompt；Gemini 仍產生 result，因此 Docs 與 Email 的 result 映射保持不變」。
預期結果：清楚列出「改變」是來源與 Gemini 輸入；「保持」是 result、Docs 內容與 Email 內文。
快速檢查：圈出兩個保持不變的映射，並標記 customer_name、rating、feedback 在 Gmail 版本中「不再使用」。
卡住時：若把 subject 寫成 result，回到 Stage S4 只修 Gemini 輸入列；保留 v1-sheets，無法判斷就標記「待確認」。
8
Check · 寫出轉移說明（S4）
學員操作：在 v2-gmail 下方寫三句話：哪些模組與輸出保持不變？sender、subject、body 如何進入 Gemini？如果 result 空白，先回哪個 Stage？
預期結果：同學只讀這三句，就能知道要重做的欄位與不必重做的模組。
快速檢查：v1-sheets 原版仍保留，v2-gmail 只改一個主要教學變因。
卡住時：回到 import-map；仍無法判斷就保留兩版並標記「待教師確認」，不要覆寫正式地圖。
(05)

完成驗證：用欄位交接，不用一句「我懂了」

逐項核對下列證據。完成不是把四個工具名稱排成一行，而是另一個人能依地圖判斷資料去向、失敗位置與來源替換範圍。

  • v1-sheets 有 4 個模組與七個欄位，順序為 Sheets、Gemini、Docs、Email。
  • Sheets 位置鍵 1/2/3 與姓名、評分、回饋的語意對照清楚。
  • Gemini 只交出 result；Docs 與 Email 都從 {{2.result}} 取值。
  • 四列失敗影響都包含現象、負責人、修正位置、重跑點與停止狀態。
  • v2-gmail 只改來源與 Gemini 輸入，保留後續三個模組的 result 映射。
  • 沒有把本 Blueprint 尚未提供的分流、資料格式轉換或人工審核控制，誤當成既有模組或欄位。

(07)

常見錯誤：先查欄位規則，再查工具

這三個錯誤都會讓流程「看起來有跑」，但交付物不可靠。每個修正都回到明確 Stage，不用整條流程重做。

把位置鍵當命名欄位

現象：地圖直接寫 Sheets 輸出 customer_name。

原因：沒有查看實際 Bundle。

修正：回 Stage S1，用 import-map.md 對照位置鍵 1/2/3，再寫入語意。

把 result 拆成不存在的欄位

現象：地圖出現 summary、reply_draft 或 needs_review。

原因：把別的案例欄位規則套進這份 4 模組 Blueprint。

修正：回 Stage S2，確認 Gemini 只有 result，Docs 與 Email 都讀它。

下游失敗卻整條重跑

現象：Email 失敗後又建立一份重複文件。

原因：沒有記錄各模組的失敗影響。

修正：回 Stage S3，只修正 Email 並從 Email 重跑；保留已成功建立的 Docs，收件狀態不明時停下人工確認。
