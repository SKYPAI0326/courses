(04) · CH1-4

讓 LLM 協同設計：從需求到模組規格

把需求、資料契約與限制交給 LLM，產出一份人可以逐項驗收的工作流設計規格。

學習成果
完成 workflow-spec-v1：模組清單、映射、限制與測試案例。
完成 prompt-log-v1 與 review-checklist-v1，留下人的決策證據。
能逐項判斷 LLM 建議是否符合契約，並只修改一個受控變因。
(01)

LLM 不是自動化按鈕，而是設計助理

為什麼這很重要
CH1-3 已把 Make 的 scenario-v1 與離線的 scenario-v1-offline-map 分開；無論哪條路徑，換來源、增加欄位或加入審核條件，都要重新整理模組清單與測試案例。LLM 能協助整理，卻不會自動知道你的資料契約，也不替你承擔錯誤映射的責任。

本節的任務不是「請 AI 幫我做自動化」，而是把需求、資料契約與限制條件交給 LLM，要求它產出可檢查的工作流設計規格。阿凱用同一個客戶回饋案例，請 LLM 提出模組清單、欄位映射、分流條件與測試案例，再用 CH1-2 的契約逐列驗收。

本節完成物　workflow-spec-v1、prompt-log-v1、review-checklist-v1。起始狀態可接 CH1-3 的 Make scenario-v1，或離線 scenario-v1-offline-map 與 run-log-v1-simulated；兩條路徑都不需要 Make token 或真實帳號，離線結果標示 SIMULATED。
先開本節材料　請先開啟 去敏需求描述、完整提示詞模板、工作流規格模板、提示紀錄模板、人工審核清單 與 LLM 固定輸出。有免費 LLM 介面時使用提示詞；沒有帳號或額度時，使用固定輸出完成同樣的逐列審核。
(02)

提示詞要把五件事說清楚

LLM 適合把自然語言需求拆成模組責任、把契約欄位整理成映射表、依限制提出測試案例。它不適合猜測未提供的連線設定、創造不存在的欄位，或替你按下上線按鈕。

提示區塊白話問題本節提供的內容
任務要設計什麼？客戶回饋整理與人工審核流程
已知資料LLM 可以使用哪些欄位？contract-input-v1、contract-output-v1
限制哪些事不能猜？不含 credential；不得新增未定義欄位
輸出格式要交付什麼？模組表、映射表、測試表、疑點清單
驗證要求如何知道答案合格？每列對應契約欄位與成功／失敗出口

正例：要求 LLM 以表格列出模組角色、輸入、輸出、限制與測試案例，並標出不確定處。錯例：只輸入「幫我做一個自動回覆流程」，讓 LLM 自己猜工具、欄位與收件人。若它建議契約沒有的 customer_phone，應標成「未提供、不得直接採用」。

設計規格不是藍圖　workflow-spec-v1 是給人審查與後續建置使用的設計文件，不是可直接匯入 Make 的 JSON；它必須留下決策理由、未解疑點與測試案例。
(03)

完整示範：把需求交給 LLM，再拆回契約

先看完整輸入，再看中間判斷與完成品。這裡唯一的事實來源是已定義的契約；LLM 沒有被授權補欄位或執行流程。

原始需求

工作室收到客戶回饋後，先產生摘要與回覆草稿；需要人工確認的內容不得直接進入文件或通知；一般內容建立 Google Docs，之後再由團隊決定是否加上通知。

提示詞完整版本

你是流程設計助理，不是流程執行者。 請依下列資料設計一份可檢查的 Make 流程規格。 任務：整理客戶回饋，產生摘要與回覆草稿，需人工確認時停止後續動作。 輸入契約：customer_identity（必填文字）、message_text（必填文字）、 urgency_signal（選填數字或空值）、owner_email（固定 Email 設定）。 輸出契約：summary（必填文字）、reply_draft（必填文字）、 needs_review（必填布林值）。 限制：不得使用 credential、token 或個資；不得新增契約未定義的欄位； Email 不是本次主軸，只列為可替換的後續動作。 請輸出四張表：1. 模組清單 2. 欄位映射 3. 控制與失敗出口 4. 測試案例。 每列都要標明輸入、輸出、驗證方式與不確定處；若資料不足，請寫「需人工確認」。

(04)

跟著做：先固定需求與輸出格式

先完成一條最短可跑路徑：用完整提示詞取得四張表，再逐列比對契約；不要一開始就要求 LLM 產生 JSON。

1
Together · 整理需求與邊界
學員操作：複製原始需求，另列出「本次要做」「本次不做」；不做項目包含 credential、實際寄信與未定義客戶欄位。
講師提示：限制不是附註，而是避免 LLM 自行補齊的護欄。
預期結果：prompt-log-v1 有一段可直接送出的需求與限制。
快速檢查：遮住工具名稱，仍能說明任務要交付什麼結果。
卡住時：回到 CH1-3 的完成物，先寫成功與停止狀態，再補工具。
2
Together · 貼入契約摘要
學員操作：把輸入／輸出契約的欄位、必填狀態、型別與缺值處理貼入提示詞；移除所有真實帳號與連線資訊。
講師提示：只貼必要資料，讓 LLM 能設計映射但看不到秘密。
預期結果：提示詞明確包含四個輸入欄位與三個輸出欄位。
快速檢查：逐欄圈出 message_text、reply_draft、needs_review。
卡住時：使用 CH1-2 的表格，不要從 Make 畫面臨時抄欄位。
3
Demo → Together · 要求固定輸出格式
學員操作：要求 LLM 輸出模組清單、欄位映射、控制／失敗出口、測試案例四張表，並要求每列提供驗證方式與疑點。
講師提示：表格是審核介面；沒有固定欄位就無法比較 LLM 兩次回答。
預期結果：得到 workflow-spec-v1 的四張表，而不是一段無法定位的長文。
快速檢查：每張表都有輸入、輸出或驗證欄位。
卡住時：補上「若資料不足寫需人工確認」，不要讓 LLM 自行猜答案。
Checkpoint：LLM 回答是否可審核

現在應該看到：四張表、契約欄位、控制條件、成功／失敗案例都出現；未提供的資訊被標記疑點。

若沒看到：回到步驟 2 或 3，補契約與輸出格式，不要直接採用整段敘述。

通過後才能繼續：你能在回答中找到每個模組的輸入、輸出、限制與驗證方式。

(05)

跟著做：逐列比對模組、映射與測試

LLM 的四張表不是自動通過。你要把建議拆回 CH1-2 契約，留下「保留／修正／拒絕」與事實理由。

4
Together · 比對模組清單
學員操作：逐列對照 scenario-v1 與 workflow-spec-v1，將模組標記「保留／修正／拒絕」，並寫理由。
講師提示：工具名相同不代表責任相同；要看角色與下游用途。
預期結果：模組清單每列都有人的審核狀態。
快速檢查：指出一列 LLM 建議與契約不符的內容，或確認它為何保留。
卡住時：回到四種模組角色與輸出契約，先判責任再判工具。
5
Together · 比對欄位映射與限制
學員操作：檢查 customer_identity、message_text、owner_email、needs_review 的來源、型別與去向；任何未定義欄位標記拒絕。
講師提示：映射錯誤比工具錯誤更難被察覺，因為答案看起來仍然完整。
預期結果：review-checklist-v1 有欄位級判斷與修正理由。
快速檢查：確認 sender 未被當成 owner_email，needs_review 未被寫成文字條件。
卡住時：使用「原始欄位 → 契約欄位 → 下游」三段式追蹤。
6
Together · 驗證測試案例
學員操作：檢查 LLM 是否提出一般、需人工、型別錯誤三種案例；若缺少一種，要求它只補該案例，不重新生成整份規格。
講師提示：測試案例要改一個主要變因，才能知道哪條規則被觸發。
預期結果：workflow-spec-v1 有三種案例與可觀察預期結果。
快速檢查：每個案例都有輸入變更、預期狀態與驗證證據。
卡住時：回看 CH1-3 的 test-cases-v1，沿用已有測試，不接受抽象的「測試成功」。
Checkpoint：規格能否交給建置者

現在應該看到：每個模組、欄位、限制與測試都有審核狀態；未實作的人工出口被保留為疑點。

若沒看到：回到步驟 4～6，補上保留／修正／拒絕與理由。

通過後才能繼續：另一位建置者只看 workflow-spec-v1，能開始配置模組而不需要猜欄位。

(06)

跟著做：受控追問與決策紀錄

最後一次只改一個條件，觀察 LLM 是否能清楚指出受影響範圍；保存決策，讓下次能重跑而不是重新猜。

7
Solo · 提出一次受控追問
學員操作：只改一個條件，要求 LLM 將來源從 Sheets 改為 Gmail；保留輸出契約、Filter 與 Docs，並要求列出受影響欄位。
講師提示：追問要限定變因，才能比較前後差異。
預期結果：LLM 只修改來源與輸入映射，明確寫出 sender、subject + body 與 owner_email 的用途。
快速檢查：沒有新增 customer_phone 或付費連線要求。
卡住時：把完整規格重新貼回去，並要求「只輸出變更表」。
8
Check · 保存提示與決策紀錄
學員操作：在 prompt-log-v1 保存原始提示、LLM 回答摘要、人的修正與拒絕項目；在 review-checklist-v1 寫通過條件。
講師提示：紀錄「為什麼採用」比紀錄「AI 說了什麼」更能交接。
預期結果：三份完成物可回溯，未來可比較 LLM 版本或重新產生答案。
快速檢查：另一個人能看懂哪些內容由 LLM 提出、哪些由人決定。
卡住時：使用四欄句型：原建議／事實依據／人的決定／後續影響。
變化練習　只把需求改為「每週彙整多筆回饋，先依 needs_review 分成待人工與可建立文件兩群」，要求 LLM 只補上批次處理的模組責任與兩個測試案例；不得直接加入 Iterator 或新欄位，除非它說明契約為何需要改變。

完成驗證

  • workflow-spec-v1 有模組清單、欄位映射、限制／失敗出口與測試案例四張表。
  • 每一列都能對照 CH1-2 契約，未定義欄位被標記拒絕或需人工確認。
  • prompt-log-v1 保存完整提示、契約摘要、限制與修正理由，不含 credential、token 或個資。
  • review-checklist-v1 逐項標記保留／修正／拒絕，並有事實依據。
  • 測試案例包含一般、需人工、型別錯誤三種路徑，且每次只改一個主要變因。
  • 來源改成 Gmail 時，只修改輸入映射與受影響欄位，不破壞輸出契約與 Filter。
(07)

常見錯誤：先查契約，再查工具

三個錯誤都會讓答案看起來完整，卻無法安全建置或測試。

提示詞只有目標沒有契約

現象：LLM 自行補欄位與工具。

修正：貼入必填／選填／型別、輸出格式與缺值處理。

把 LLM 回答當成 Make 藍圖

現象：直接照著配置而不比對測試。

修正：先產出 workflow-spec-v1，逐列標記保留／修正／拒絕。

一次要求太多變更

現象：來源、條件、通知同時改，無法定位結果差異。

修正：一次只改一個變因，保存前後版本與理由。

(08)

檢核題：用契約說明你的判斷

用欄位、型別與安全出口說明判斷，不只看答案是否流暢。

Q1：為什麼提示詞要寫「不得新增契約未定義的欄位」？
顯示答案與理由
正確答案：B。限制讓 LLM 的建議留在已知事實範圍內。
Q2：LLM 建議新增 customer_phone，但契約沒有這個欄位。你應該怎麼做？
顯示答案與理由
正確答案：B。先保護契約邊界，再決定是否真的需要變更上游規格。
(09)

試跑包：沒有連線也能完成本節

使用去敏需求描述、固定輸出或免費可用的 LLM 介面，即可完成三份文件；不得提供 credential、token、固定帳號或個資。

上游資料

使用 CH1-2 三份契約、CH1-3 的 Make scenario-v1 或離線 scenario-v1-offline-map／run-log-v1-simulated，以及 test-cases-v1；本節另提供 去敏需求描述 供無上游檔案時對照。

提示素材

完整提示詞模板可直接複製；沒有 LLM 帳號時改用固定輸出，不把登入設為完成條件。

完成模板

workflow-spec-v1 四張表、prompt-log-v1、review-checklist-v1；逐項留下保留／修正／拒絕。

交付限制

保存人的決策理由；未實作的人工出口、疑點與測試證據不可省略。不得提供 credential、token、固定帳號或個資。
