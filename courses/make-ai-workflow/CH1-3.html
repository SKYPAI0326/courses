(03) · CH1-3

建立一條可執行的範例流程

使用 CH1-2 的輸入與輸出契約，建立並測試一條 Make＋Gemini 範例流程，能說明每個模組的映射、控制條件、測試結果與失敗出口。

學習成果
Make：完成 scenario-v1；離線：完成 scenario-v1-offline-map，兩者皆保留四個核心模組的映射。
Make：完成實際 run-log-v1；離線：完成標示 SIMULATED 的 run-log-v1-simulated。
完成 test-cases-v1：依模式保存實際或模擬證據，可交給 CH1-4 延伸。
(01)

先讓一筆資料安全走完最短路徑

為什麼這很重要
CH1-1 讓你看懂模組如何排列，CH1-2 讓你把欄位與型別寫成契約。現在把這兩份文件接到 Make，先跑出一條真的能測試的最小流程，再決定要不要加入通知。

阿凱在弄一下行銷工作室收到一筆客戶回饋。今天先用 Google Sheets 作為示範來源，讓 Gemini 依照 contract-input-v1 產生固定格式的摘要、回覆草稿與 needs_review，再用 Filter 決定是否建立 Google Docs。Sheets 是案例入口，不是唯一正解；同一份契約之後可換成 Gmail。

本節完成物　Make 路徑完成 scenario-v1、實際 run-log-v1、test-cases-v1；離線路徑完成 scenario-v1-offline-map、run-log-v1-simulated、test-cases-v1，所有結果標示 SIMULATED，不可填寫虛構 URL。
先開本節材料　請先開啟 四張模組卡、兩筆測試資料、Gemini 固定輸出、執行紀錄模板 與 測試案例模板 與 離線模擬執行包。沒有 Make 連線時，依離線包完成映射與模擬測試，不能把結果寫成平台執行。
(02)

最短可跑路徑：來源、處理、控制、後續動作

最短可跑路徑只保留能驗證核心學習的模組：來源、處理、控制、第一個後續動作。先確認資料有進 Gemini、輸出符合契約、Filter 會分流，再補通知或其他延伸；一次接完所有模組，錯誤會同時出現在多個位置。

Google Sheets / Watch Rows → Gemini / Generate → Filter：needs_review = false → Google Docs / Create a Document

當 needs_review=true 時，資料不進 Docs，而是停在「待人工確認」的未實作出口。這個出口也要寫進執行紀錄，否則測試只涵蓋成功路徑。

設定面向要回答的問題本節證據
輸入映射這個模組拿到哪個契約欄位？Sheets 的 feedback → message_text
處理設定模組如何產生下一個結果？Gemini 依固定輸出格式生成三欄
控制條件什麼資料可以繼續？needs_review = false 才進 Docs
執行證據如何知道真的成功或失敗？Run log 記錄 bundle、輸出、狀態與出口

正例：先用一筆已知的 Sheets 資料執行，確認 Gemini 回傳 summary、reply_draft、needs_review，再建立 Docs。錯例：直接把整封資料塞進 Docs，看到文件出現就認為流程成功，卻沒有檢查 AI 輸出欄位與 Filter 分流。

你要判斷　如果 Docs 有建立但內容是空白，先回到 Gemini 的輸出契約與 Docs 映射，不先重建來源模組。

(04)

跟著做：依模式建立最小流程

示範已把模組責任、契約映射與兩條出口走過一次。現在依最短路徑操作；每一步都留下可觀察結果，不把整條流程當成一個黑盒。

1
Together · 建立最小流程（Make／離線）
Make 路徑：建立 Scenario scenario-v1，依序放入 Google Sheets / Watch Rows、Gemini / Generate、Filter、Google Docs / Create a Document；先不要加入 Email 或其他通知。
離線路徑：不建立 Scenario，改用 scenario-v1-offline-map 與模組卡寫出同樣順序、輸入、輸出與停止出口。
講師提示：模組順序是資料流的最短路徑，不是完整產品版；先讓每個中間結果可觀察。
預期結果：Make 畫面或離線地圖都有四個模組且順序一致；離線不命名成可執行 Scenario。
快速檢查：兩條路徑都能說出每個模組的角色與下一個模組需要什麼。
卡住時：若找不到模組，改用教師提供的模組卡記錄設定，不把登入問題當成本節阻塞。
2
Together · 映射來源欄位
Make 路徑：在 Sheets 模組指定測試試算表與工作表；確認輸出欄位對應 customer_identity、message_text、urgency_signal 的來源值。
離線路徑：依離線模擬執行包抄入固定輸入並完成同樣映射，不填連線或執行 ID。
講師提示：Watch Rows 的輸出仍是來源欄位，正規化欄位要在交給 Gemini 前說明映射。
預期結果：Make 測試 bundle 或離線輸入表都有林小姐、回饋文字與 rating=2。
快速檢查：遮住試算表名稱，只看欄位值仍能判斷這是一筆客戶回饋；離線不可寫成 Make bundle。
卡住時：回看 CH1-2 的 mapping-v1；不要把 owner_email 從客戶列猜出來，使用課程提供的固定設定。
3
Demo → Together · 設定 Gemini 輸入與輸出
Make 路徑：將 customer_name／feedback／rating 映射到契約欄位，貼上示範的輸出要求，指定只回傳 summary、reply_draft、needs_review 三欄。
離線路徑：使用固定 Gemini 輸出填入三個欄位與型別，不宣稱已呼叫 Gemini。
講師提示：輸出格式是下游的契約，不是美化文字；先驗證欄位與型別，再談提示詞風格。
預期結果：Make 測試輸出或離線固定輸出含兩個文字欄位與一個布林欄位；離線標示 SIMULATED。
快速檢查：逐欄圈出三個輸出，並寫下各自的下游用途。
卡住時：若輸出混入說明文字，先把「只回傳 JSON 欄位」寫進提示詞，並在記錄中標為輸出格式錯誤。
Checkpoint：Gemini 輸出是否符合契約

現在應該看到：Make 輸出可追溯到 CH1-2；離線固定輸出與映射已標示 SIMULATED，兩者都尚未執行 Docs。

若沒看到：回到步驟 2 或 3，先修正映射或輸出格式，不要繼續設定 Filter。

通過後才能繼續：兩條路徑都能指出哪一欄控制分流、哪兩欄會進入文件；Make 才繼續設定平台 Filter。

(05)

跟著做：設定分流、文件與執行證據

成功建立模組不等於流程驗證完成。先讓 true 安全停下，再重跑 false 成功路徑，最後把兩筆結果寫進可交接的紀錄。

4
Together · 設定 Filter 分流
Make 路徑：在 Filter 建立條件 needs_review = false，通過路徑連到 Docs；在執行紀錄說明 true 會進待人工確認出口。
離線路徑：在地圖標出 false → Docs、true → 待人工確認，不宣稱平台真的攔截資料。
講師提示：Filter 不修改資料，只決定是否繼續；不要把它當成內容審核器。
預期結果：Make 的 false 可通過、true 不建立 Docs；離線兩條路由標示 SIMULATED。
快速檢查：Make 用 true 確認沒有新文件；離線比對固定輸出與預期路由。
卡住時：檢查布林值是否被當成文字；若型別不明，回到 Gemini 輸出契約。
5
Together · 映射 Google Docs
Make 路徑：將 summary 與 reply_draft 放入文件標題／內容欄位，設定文件名稱包含測試識別，例如 feedback-test-B；保存實際文件 URL。
離線路徑：填入 {{simulated_document_url}} 與預期文件內容，不產生虛構 URL。
講師提示：Make 文件建立成功的證據是 URL 與內容；離線只比對固定輸出與預期內容，不把 placeholder 當 URL。
預期結果：Make 的 needs_review=false 建立含摘要與草稿的文件；離線完成預期文件內容比對並標示 SIMULATED。
快速檢查：Make 打開文件確認內容與 Gemini 回傳一致；離線逐欄比對固定輸出，不填真實 URL。
卡住時：Make 查 Docs 權限與欄位映射；離線回看固定輸出與地圖，不把缺少連線寫成錯誤。
6
Together · 記錄一筆成功執行
Make 路徑：在 run-log-v1 記錄測試資料、執行時間、Gemini 三欄輸出、Filter 結果、Docs URL 與狀態「已完成」。
離線路徑：在 run-log-v1-simulated 記錄固定輸入／輸出、預期路由、{{simulated_document_url}} 與 SIMULATED／未在 Make 驗證。
講師提示：執行紀錄是交接與除錯證據，不是流水帳；至少保留能重現判斷的欄位。
預期結果：Make 成功案例可由另一位同事依實際 log 重現；離線可依模擬包重建預期判斷，但不宣稱平台重跑。
快速檢查：Make 遮住畫面只看 log 能重述資料走過哪些模組；離線只檢查欄位與路由是否完整。
卡住時：依 test-cases-v1 的欄位順序補寫：輸入、輸出、條件、結果、證據。
Checkpoint：成功路徑是否可重現

Make 現在應該看到：一筆 false 測試有真實 Docs URL，一筆 true 測試沒有建立文件；兩筆都有實際執行紀錄。
離線現在應該看到：兩筆路由均有固定輸入、預期輸出與 SIMULATED 紀錄；沒有真實 URL 或執行 ID。

若沒看到：Make 回到 Filter 確認條件與測試值；離線回到模擬包對應案例，不補造平台證據。

通過後才能繼續：接手者只看對應模式的 log，就能說出成功、待人工確認與錯誤各自的出口。

(06)

跟著做：故意失敗，再提交測試包

失敗測試不是把流程弄壞，而是確認安全出口真的存在。只改一個主要變因，讓你能定位停止模組與修復責任。

7
Solo · 故意製造一個失敗
Make 路徑：複製測試資料成 B，將 message_text 清空或把 needs_review 改成文字；只改一個主要變因，執行後記錄停止模組、錯誤原因、負責人與重試方式。
離線路徑：依離線模擬包只改一個主要變因，記錄預期停止位置、原因、負責人與重試方式，標示 SIMULATED。
預期結果：Make 流程在來源、Gemini 或 Filter 的對應位置停止，不建立空白 Docs；離線紀錄呈現相同預期出口，但不宣稱實際停止。
快速檢查：log 中能指出哪個契約條件不合格，以及下游為何暫停。
卡住時：回看 CH1-2 的失敗處理表；不要把所有錯誤都寫成「重跑全部」。
8
Check · 提交最小流程與測試包
Make 路徑：保存 scenario-v1 藍圖、實際 run-log-v1、test-cases-v1；在交接說明中寫出若來源改成 Gmail，哪些模組保持不變、哪些欄位需重新映射。
離線路徑：保存 scenario-v1-offline-map、run-log-v1-simulated、test-cases-v1，並標示尚未在 Make 驗證。
預期結果：Make 的三份文件與藍圖可交給 CH1-4 使用；離線地圖、模擬 log 與測試包可供規格審查，但不能當成已執行藍圖。
快速檢查：接手者依對應模式的測試包，能重建一筆成功與一筆失敗的判斷；離線包明確標示需要後續平台驗證。
卡住時：逐項檢查完成物、輸入契約、輸出契約、兩條 Filter 路徑與對應模式的證據；離線不要補寫實際 URL。
變化練習　複製 scenario-v1 成 scenario-gmail-variant，只替換來源為 Gmail / Watch Emails；保留 Gemini、Filter、Docs 的契約與控制條件。映射 sender → customer_identity、subject + body → message_text，並在測試包標記 Gmail 沒有 urgency_signal。

完成驗證

  • Make 的 scenario-v1 有 Sheets、Gemini、Filter、Docs 四個核心模組；離線使用 scenario-v1-offline-map，不可命名成可執行 Scenario。
  • Make 至少一筆 needs_review=false 建立真實 Docs，一筆 true 停在待人工確認；離線兩筆均標示 SIMULATED，不可填虛構 URL。
  • Gemini 輸出只包含 summary、reply_draft、needs_review，型別符合 contract-output-v1。
  • Make 的 run-log-v1 記錄實際輸入、輸出、Filter 結果、文件 URL／停止狀態；離線的 run-log-v1-simulated 記錄預期輸出、placeholder 與停止位置。
  • test-cases-v1 有成功與失敗案例，且失敗只改一個主要變因。
  • 來源替換為 Gmail 時，sender、subject + body 與 owner_email 的用途沒有混用。
(07)

常見錯誤：先看中間結果，再看綠燈

下面三個錯誤都會讓畫面看似完成，卻沒有可交接的證據。

一次接太多模組

現象：流程很短就加入 Email 與額外格式化。

修正：回到 Sheets → Gemini → Filter → Docs 的最短路徑，先驗證一條成功與一條停止。

只看綠色成功狀態

現象：Docs 有建立就認為流程成功。

修正：同時檢查三個 Gemini 輸出、Filter 值與文件內容。

失敗時全部重跑

現象：空值或型別錯誤直接重跑整條流程。

修正：先定位停止模組與契約缺口，再由指定負責人重試單一模組。

(08)

檢核題：用出口與證據說明成果

前面的操作要求你做出最小流程與兩筆紀錄，這兩題確認你能從控制條件與執行證據判斷流程是否可交接。
