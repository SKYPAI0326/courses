先取得完整 Prompt　第一次請 LLM 修改 JSON 時，直接複製 CH1-5 最小 diff Prompt，再把去敏 JSON 貼到指定位置。沒有 LLM 帳號時，使用同頁的固定 diff；兩者都不能取代 Make 實際執行證據。
兩條測試路徑　`MAKE` 模式才執行修改後流程，並在 三筆測試案例填執行 ID、Docs URL、停止位置與實際輸出；`SIMULATED` 模式只用去敏 JSON、固定 diff與同一份測試表做欄位／路由靜態比對，填 {{simulated_document_url}} 並標示「尚未在平台驗證」。離線審查通過不等於平台接受，必須保留這個證據層級。
閱讀示範表的方法　頁面中的「取得文件 URL／未建立 Docs」是 Make 路徑的示範結果；離線學員請把它視為預期判斷，改填固定輸出與 placeholder，並在 diff-log-v1 註明尚未在平台執行。
五至七步的證據對照　步驟 5：Make 執行 false 並記執行 ID／Docs URL；離線以固定 diff 比對欄位與預期文件，填 {{simulated_document_url}}。步驟 6：Make 執行 true 與文字型別錯誤並記停止訊息；離線比對 manual_review／type_error 預期路由並標示 SIMULATED。步驟 7：Make 依實際結果接受或退回；離線只能標為「離線審查通過／待 Make 驗證」或退回。

(05) · CH1-5

讓 LLM 修改與除錯 JSON

先去敏，再要求最小 diff；Make 以實際執行結果決定接受、退回或還原，離線以模擬審查標示待驗證，不讓 LLM 順手重寫整份 Make 藍圖。

學習成果
完成 blueprint-safe-v1.json：移除 credential、token、固定帳號、資料夾 ID 與個資的安全藍圖。
完成 change-request-v1：只改一個主要變因，並寫清楚不變條件與驗收。
完成 diff-log-v1：保留差異、理由、測試結果、決策與還原步驟。
(01)

先把「只改一欄」變成可審查的變更

為什麼這很重要
CH1-4 教你讓 LLM 產出設計規格；本節處理更容易出事的情境：已有一份 Make JSON，但只想修一個欄位映射或一條 Filter 條件。完整藍圖貼給 LLM 可能洩漏連線設定，也可能順手重寫不相關模組。

阿凱要讓 scenario-v1 的 Filter 讀取 Gemini 輸出的 needs_review，並修正 Filter 將文字「false」誤當布林值的問題。他會提供去敏 JSON、變更目標與不變條件，要求 LLM 輸出最小 diff、理由、測試與還原。沒有 Make 工作區時，改用同一份去敏 JSON 審查差異與預期路由，不把模擬結果寫成平台執行證據。

起始狀態　Make 路徑使用教師提供的去敏 JSON、CH1-2 契約與 CH1-3 scenario-v1；離線路徑使用去敏 JSON、固定 diff 與測試表完成靜態審查。離線不產生真實 Docs URL、Filter 執行紀錄或平台錯誤訊息。
先開本節材料　請先開啟 去敏藍圖 fixture、去敏檢查表、變更需求單、固定測試案例、差異紀錄模板 與 固定 diff 範例 與 完整最小 diff Prompt。固定 diff 是無 LLM 帳號備援，不代表實際執行成功。
(02)

兩個邊界：最小修改與安全 JSON

最小修改是只改變達成需求所需的欄位、條件或模組參數，保留其他節點、順序與連線；目的不是追求「改得越少越好」，而是讓測試與還原範圍可控。安全 JSON則保留教學需要的結構與欄位，移除可以登入、識別個人或定位雲端資源的值。

修改類型允許範圍不應順手改動
Filter 欄位映射feedback_text → needs_review來源模組、Docs 版型
條件型別「false」→ falseGemini prompt 全文、通知模組
輸出欄位保留 needs_review重新命名所有輸出
要保留要移除或替換
模組類型、順序、欄位名稱、條件、範例輸出OAuth token、API key、credential ID、資料夾 ID、真實 Email、個資

正例：只修改 Filter 的比較值與型別，並提供 false、true 與文字型別錯誤三個測試。錯例：LLM 回傳完全重排的 JSON，雖然看似乾淨，卻無法知道哪些變更造成新的失敗。若需求只說「修正欄位映射」，LLM 卻新增 Email 模組，就應退回。

(03)

示範：用去敏 JSON 提出一個可還原的最小 diff

先保留結構，再把敏感值換成 placeholder。這段可直接交給 LLM 看；它足以理解欄位與條件，但不能登入或識別真人。

{ "module": "Gemini / Generate",
  "input": { "message_text": "{{sample_text}}" },
  "output": { "summary": "{{summary}}", "reply_draft": "{{draft}}", "needs_review": "{{flag}}" },
  "connection": "{{removed_credential}}" }

變更需求：只修改 Filter 的條件型別與 Gemini → Filter 的欄位映射；needs_review 必須是布林值，false 才能通往 Google Docs，true 必須停在待人工確認。不新增模組、不改來源、不改 Docs 欄位、不改提示詞文字。請輸出修改前後差異、每個差異的理由、三個測試案例與還原方式。

路徑修改前修改後理由驗證
Filter.condition.value「false」false讓條件使用布林值false 通過、true 停止
Filter.inputfeedback_textneeds_review控制欄位來自 Gemini 輸出檢查映射與輸出契約

LLM 另列出「未修改」清單：來源模組、Gemini prompt、Docs、連線設定 placeholder 均維持不變。這張清單讓人快速發現是否偷改範圍。

測試輸入預期實際判斷
A：可繼續needs_review=false進 Docs通過，取得文件 URL
B：需人工needs_review=true停在人工出口通過，未建立 Docs
C：型別錯誤needs_review="false"標記型別錯誤、不通過、不下游標記型別錯誤，未採用且未執行下游
接受門檻　A、B 通過，且 C 沒有被誤放行，才可接受 diff。任一測試失敗，就保留 blueprint-safe-v1.json，還原到修改前版本，不能在未記錄狀態繼續疊改。

同一份 scenario-v1 去敏 fixture 的前後狀態如下；Filter 在第 2 個模組，表格路徑可直接由這份素材重現：

{
  "scenario": "scenario-v1",
  "modules": {
    "before": [
      { "position": 1, "module": "Gemini / Generate",
        "output": { "needs_review": "{{needs_review_boolean}}" },
        "connection": "{{removed_credential}}" },
      { "position": 2, "module": "Filter",
        "input": "feedback_text",
        "condition": { "operator": "equal", "value": "false" },
        "routes": { "false": "Google Docs", "true": "manual_review" } }
    ],
    "after": [
      { "position": 1, "module": "Gemini / Generate",
        "output": { "needs_review": "{{needs_review_boolean}}" },
        "connection": "{{removed_credential}}" },
      { "position": 2, "module": "Filter",
        "input": "needs_review",
        "condition": { "operator": "equal", "value": false },
        "routes": { "false": "Google Docs", "true": "manual_review" } }
    ]
  },
  "test_inputs": [
    { "needs_review": false, "expected_route": "Google Docs" },
    { "needs_review": true, "expected_route": "manual_review" },
    { "needs_review": "false", "expected_route": "type_error", "expected_downstream": false }
  ]
}
(04)

跟著做：先建立安全副本與變更邊界

以下 1～3 步先把可交付的最小路徑建立起來；每一步都留下可觀察結果，才把問題交給 LLM。

1
Together · 複製並去敏藍圖
學員操作：將教師 JSON 複製為 blueprint-safe-v1.json，搜尋 token、secret、password、credential、真實 Email、資料夾 ID 與個資；以 placeholder 替換並保留模組結構。
講師提示：去敏不是刪掉欄位名；要讓 LLM 看懂結構，但無法登入或識別真人。
預期結果：JSON 可解析，保留模組、輸入、輸出、條件與連線 placeholder。
快速檢查：檔案中沒有真實 token、credential 值、固定帳號或個資。
卡住時：使用試跑包的關鍵字清單逐項搜尋；不確定的值先替換，不要猜安全與否。
2
Together · 寫變更需求與不變條件
學員操作：建立 change-request-v1，寫明唯一主要變因「修正 needs_review 型別與 Filter 映射」，並列出不改來源、提示詞、Docs 與模組數量。
講師提示：不變條件是 diff 的邊界，也是後續審核依據。
預期結果：需求能被另一個人判斷是否超出範圍。
快速檢查：同學能用一句話說出允許與禁止的修改。
卡住時：回到示範的兩個修改路徑；不要把「順便優化」寫進需求。
3
Demo → Together · 要求 LLM 只輸出 diff
學員操作：把去敏 JSON、變更需求、契約摘要與輸出格式貼給 LLM；要求輸出修改前／後、理由、未修改清單、測試與還原。
講師提示：完整 JSON 可以作為參考，但第一個交付物應是可讀 diff，不是整份重寫。
預期結果：LLM 回答包含明確路徑與三個測試案例：false、true 與文字型別錯誤。
快速檢查：每個 diff 都能指出路徑、舊值、新值與理由。
卡住時：補上「不得新增模組、不得改動未列路徑、資料不足寫需人工確認」。
Checkpoint：修改範圍是否受控

現在應該看到：只有 Filter 型別與輸入映射變更；來源、Gemini prompt、Docs 與連線 placeholder 被列在未修改清單。

若沒看到：退回 LLM 回答，要求「只輸出變更表」，不要直接複製整份新 JSON。

通過後才能繼續：你能逐項說明每個變更如何對應 contract-output-v1。

(05)

人工審查，再用三條路徑驗證

LLM 提供建議，人負責決定是否符合事實與範圍。先審 diff，再依序跑成功、停止與型別錯誤；不要以靜態文字代替執行證據。

4
Together · 人工審查 diff
學員操作：將每個差異標記「接受／退回／需確認」；檢查 needs_review 的來源、型別、Filter 去向與未修改清單。
講師提示：不能只靠文字判斷的內容，標記需測試。
預期結果：diff-log-v1 有每個修改的採用狀態與理由。
快速檢查：指出一個需要實際執行才能證明的項目。
卡住時：回看 CH1-3 的成功／停止測試，將未知事項列為需確認。
5
Together · 先跑成功案例
Make 路徑：用 needs_review=false 的輸入執行修改後流程，記錄執行 ID、Docs URL、執行狀態與實際輸出。
離線路徑：用固定 diff 比對欄位與預期文件，填 {{simulated_document_url}} 並標示 SIMULATED，不得填真實 URL。
講師提示：成功案例只證明通過路徑，還不能證明安全分流。
預期結果：Make 建立 Docs 且內容符合 summary 與 reply_draft 契約；離線只完成欄位與路由的模擬判斷。
快速檢查：Make 的文件內容、URL 與執行 ID 都存在；離線固定輸出與契約一致並保留 SIMULATED 標記。
卡住時：比較修改前後 diff；Make 再查 Filter 與 Docs，離線則列出尚待平台驗證，不把缺少連線當成測試失敗。
6
Together · 再跑停止與型別錯誤
Make 路徑：用 needs_review=true 執行，確認資料停在人工出口；再用 needs_review="false" 測試型別錯誤，記錄停止位置、執行 ID 與結果。
離線路徑：比對 manual_review／type_error 預期路由，記錄停止位置與原因並標示 SIMULATED。
講師提示：安全測試要包含「看似相同但型別不符」的案例。
預期結果：Make 的 true 不建立 Docs、文字型別不被自動轉換；離線記錄相同預期但標示 SIMULATED。
快速檢查：Make log 有停止位置、執行 ID、原因、負責人與重試方式；離線 log 有預期停止位置、原因與尚待平台驗證欄。
卡住時：先停用後續通知，回到輸出契約檢查布林值；離線不要把固定輸出改寫成實際錯誤訊息。
Checkpoint：測試是否證明最小修改

Make 現在應該看到：false 成功、true 停止、文字型別錯誤被攔截，且每案有執行 ID、Docs URL 或停止訊息；所有結果都能回到 diff-log-v1。
離線現在應該看到：三案預期路由與固定輸出逐列相符，紀錄標示 SIMULATED 並列出真實執行尚待驗證。

若沒看到：還原 JSON，逐一重跑；不要在多個修改同時存在時猜原因。

通過後才能繼續：Make 依實際執行結果決定接受或退回；離線依模擬審查結果決定是否送交後續平台驗證。

(06)

把決策與還原寫進交接紀錄

測試完成後才做決策；還原不是失敗，而是控制變更範圍的正式步驟。最後讓下一位設計者在不接觸 credential 的情況下理解與重做修改。

7
Solo · 接受、退回或還原
學員操作：若三個測試符合預期，將狀態標為接受；若任一失敗，標為退回並使用 blueprint-safe-v1.json 還原，再記錄下一個修正需求。
講師提示：保留原始安全檔；若找不到還原來源，停止，不要覆寫現有 JSON。
預期結果：diff-log-v1 有明確決策與版本位置，沒有未標記的半成品。
快速檢查：另一個人能知道目前採用哪個版本、如何回到上一版。
卡住時：回到修改前安全副本，先補版本位置再做下一次變更。
8
Check · 保存交接紀錄
學員操作：在 diff log 最下方寫變更目的、影響模組、測試結果、還原步驟與下一位負責人；移除所有秘密值後才分享。
講師提示：交接文件描述決策與證據，不只附上 LLM 回答。
預期結果：下一位設計者可在不接觸 credential 的情況下理解與重做修改。
快速檢查：只看 diff log 就能說出改了什麼、為何改、如何驗證與如何還原。
卡住時：依序補「變更／理由／測試／狀態／還原」五欄。
變化練習　只把變更改成「Docs 標題加入測試日期」，要求 LLM 不修改來源、Gemini 輸出、Filter 與通知；產出另一份 diff，並說明哪些測試仍需重跑、哪些可沿用。

完成驗證

  • blueprint-safe-v1.json 可解析，沒有 credential、token、固定帳號、資料夾 ID 與個資。
  • change-request-v1 只改一個主要變因，並列出不變條件。
  • LLM diff 有路徑、舊值、新值、理由、未修改清單、測試與還原。
  • 測試涵蓋 false 成功、true 停止、文字型別錯誤三條路徑。
  • diff-log-v1 能指出接受／退回／需確認的決策與負責人。
  • 任一測試失敗時，能回到安全 JSON，而不是覆寫未驗證版本。
(07)

常見錯誤：看似快，實際無法追責

把完整藍圖原封不動貼給 LLM

現象：可能洩漏秘密，也讓模型看見不必要的連線細節。

修正：先做去敏副本並搜尋敏感關鍵字，未知值一律換 placeholder。

接受整份重寫 JSON

現象：無法知道改動範圍，失敗時也無法定位原因。

修正：要求最小 diff、未修改清單與版本還原。

只測試成功案例

現象：看不到 Filter 失效或型別錯誤。

修正：固定測試 false、true 與文字型別三條路徑。

(09)

試跑包：在無真實連線時仍能完成驗證

本節需要的素材都可去敏。使用固定輸出或教師提供的測試資料，即可練習差異審查、三條測試路徑與還原。

去敏參考 JSON

開啟去敏藍圖 fixture；保留模組結構，不含連線或個資。

去敏檢查

開啟去敏檢查表；逐項確認 token、ID 與個資已替換。

變更需求

複製變更需求單，先寫允許與禁止的路徑。

固定測試

開啟三筆固定測試，填寫實際結果與決策，不把預期當證據。

差異紀錄

複製 diff log，保存版本、理由、測試與還原。

離線備援

閱讀固定 diff 範例；沒有 LLM 帳號時仍能做逐列審查。
