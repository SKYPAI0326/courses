6.3

GitHub + Railway：外部部署評估與驗收

評估 AI Studio、GitHub 與 Railway 的部署取捨，先核對金鑰、費用、網路條件和撤回方式。

選修成果
判斷是否需要本機以外的部署方式
依平台現況確認環境、金鑰位置與成本

先確認為什麼要外部部署

Railway 是 AI Studio Build 之外的主機選項，不是必修路徑，也不會免除 Gemini API 用量費用。若只需要快速分享測試，先比較 AI Studio 的 Share、Cloud Run 部署和 GitHub 同步；只有版本管理、主機流程或團隊操作方式確實需要時，再評估外部部署。參考 Build 功能說明、Cloud Run 部署說明 和 Railway Trial 條件。

開始前準備可重新開啟的 AI Studio 專案、允許同步的 GitHub 帳號、可安全設定伺服器端環境變數的 Railway 專案，以及一份不含機密的測試資料。交付物是「可重新部署的版本＋測試和回復紀錄」，不是只拿到公開網址。

把程式碼同步到 GitHub，先檢查再提交

  1. 在 AI Studio Build 專案的 GitHub 整合中連結或建立 repo；目前功能支援同步程式碼，實際按鈕和權限提示依帳號畫面為準。
  2. 確認 repository 所有人、可見性與存取權。檢查將提交的檔案，不要假設 secret 一定會被排除；任何 API key、個資或內部樣本都不可提交。
  3. 提交後打開 GitHub 檢查檔案清單和最近一次變更。若發現 key 已寫入或提交，先撤回暴露版本、撤銷／輪替 key，再重新部署；刪掉檔案不會讓已暴露的 key 自動失效。
  4. 記下 commit 或同步版本，作為稍後部署失敗時的回復點。

連接 Railway，將 secret 留在伺服器端

  1. 從 Railway 建立測試專案，授權讀取指定 repo，選擇正確分支。先查看目前 Trial 類型、外連網路限制、記憶體／CPU 上限和資料保存條件。
  2. 由 Railway 依專案設定建置並啟動服務。若失敗，先看 build/deploy logs，核對啟動命令、port 和依賴；不要把 API key 貼進錯誤回報或前端。
  3. 在主機的環境變數／secret 管理介面新增 GEMINI_API_KEY，只放伺服器端。變數名稱和重新部署方式以 Railway 當前文件為準；不可把金鑰寫入 HTML、JavaScript、GitHub 或教學截圖。
  4. 重新部署後先用假資料測正常輸入、空值、網路／額度失敗和重試。確認公開網址沒有在瀏覽器程式碼中暴露 key，並記錄伺服器 log 位置。

Railway 目前列有一次性 US$5 Trial credit，最長 30 天或額度耗盡；Limited Trial 會有外連網路限制，驗證狀態和資源條件以官方當下說明為準。Trial、主機資源和 Gemini API 分別計費；使用前查看 Free Trial 與 方案／用量，不要把試用額度當成長期免費。

驗收部署與準備撤回

用測試網址分別檢查：頁面可開啟、模型請求成功、錯誤時不洩漏 key、刷新後狀態符合預期、費用與用量能追蹤。若服務無法啟動或帳號限制未解決，停止發布並保留 AI Studio 專案和 GitHub commit。

正式使用前寫下：目前網址、repo／commit、secret 名稱（不可記錄 secret 值）、部署時間、測試資料、費用查看位置、停止／刪除服務步驟及 key 輪替方法。GitHub Pages 只能託管靜態內容，不能替代含 Gemini API 的伺服器端執行環境；查看 GitHub Pages 說明。

✓
本單元驗收：能說明為何需要外部主機，並證明 repo 沒有 secret、API key 位於伺服器端、測試網址可運作、費用可追蹤且有撤回方案。不符合其中一項，就維持未部署狀態。
