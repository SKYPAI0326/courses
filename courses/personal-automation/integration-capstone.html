INTEGRATION CAPSTONE · MAKE → N8N

把 Make 契約帶進 n8n

你已完成雲端流程與平台地圖。這次把同一份資料契約放進本機 n8n，建立可重跑的輸入檢查、分流與交接證據，讓雲端與地端各自負責清楚。

前置條件
Make 交接包、Bridge-1 的 platform-map-v1、n8n 環境檢查
本節完成物
n8n-contract-flow-v1＋兩條證據路徑＋交接包
核心判斷
同一份契約是否在本機仍維持欄位、型別與終態
先說清楚：候選工作流檔案仍標為 DRAFT_IMPORT_CANDIDATE。只有你在自己的 n8n 執行並留下紀錄，才可標為 N8N；固定輸出與離線演練使用 SIMULATED，未執行使用 NOT_RUN。
(01)　Brief｜先理解整合任務

阿凱為什麼把部分工作移到本機

工作情境
阿凱在弄一下行銷工作室負責客戶回饋。Make 已能讀取雲端資料、交給 AI 整理並分出待人工項目；團隊接下來要批次處理本機檔案，因此需要在 n8n 重建一段相同責任的流程。

本專題的成功條件是「資料契約仍成立」。你要能指出輸入欄位、型別、AI 輸出、分支條件與終態；平台名稱、按鈕位置與認證方式則分開記錄。這樣日後替換來源或下游時，改動範圍仍可追蹤。

雲端 Make：取得回饋與整理契約 ↓ 交接 platform-map-v1 本機 n8n：檢查輸入 → 判斷 needs_review ├─ true → manual_review（停止，不建立交付物） └─ false → ready_for_delivery（交給下一節）
(02)　Upstream Artifacts｜接住上游成果

先確認你手上的檔案就是同一個版本

整合會沿用 Make 與 Bridge-1 的材料。若檔案缺少或版本不一致，先停下來記錄缺口；不要用 LLM 另生一份看似相同的契約。

上游材料本節用途取得方式／限制
CH1-2-contract-input-template.md、contract-output固定輸入與輸出欄位。缺檔時使用下方契約表，標註未直接讀取原檔。
platform-map-v1.md記錄 Make／n8n 責任差異。沿用 Bridge-1 的完成副本。
integration-capstone-contract-v1.md核對整合輸入、終態與交接欄位。這是專題契約；不要改寫原始版本。
m4-bridge-contract-fixture.json選配的匯入比較材料。DRAFT_IMPORT_CANDIDATE；不能直接宣稱可執行。

共同資料契約

欄位範例值型別與限制下游用途
customer_identity林小姐文字，不可空白辨識回饋提出者
message_text物流延遲，客服回覆太慢文字，不可空白交給 AI 閱讀
urgency_signal2數字；本案例的代理訊號協助練習分流

(03)　Intermediate Deliverables｜先畫出中間結果

建立節點前，先固定資料形狀與終態

n8n 的 Item 是節點交出的單筆資料項目。這次先用一筆固定資料建立可觀察路徑，再把同一份契約套到三個案例；你會比較容易找出是輸入、型別還是分支出了問題。

輸入 Item

{
  "customer_identity": "林小姐",
  "message_text": "物流延遲，客服回覆太慢",
  "urgency_signal": 2
}

固定處理輸出

{
  "summary": "物流延遲且客服回覆時間過長",
  "reply_draft": "感謝你的回饋，我們會檢查物流通知流程並改善客服回覆時間。",
  "needs_review": true
}

ready_for_delivery

契約檢查通過，且 needs_review=false。可以交給下一個文件或檔案節點。

manual_review

needs_review=true。停止在人工出口，不建立未審核交付物。

contract_error_stop

必要欄位缺少或型別錯誤。停止且不猜測、不執行下游。

(04)　Build｜建立並重跑最小流程

六步完成 n8n-contract-flow-v1

請在 n8n 工作區逐步建立。每一步都先執行目前節點、查看 Output，再進入下一步；候選 JSON 可用來比較結構，不能跳過理解與驗收。

Step 1｜建立可重跑的起點

建立新 workflow，加入 Manual Trigger，命名 n8n-contract-flow-v1。先按 Execute 確認流程能啟動。

預期
Execution 有啟動紀錄，即使尚未有輸入也可以。
檢查
畫面只有起點；尚未加入 Webhook、Gemini 或 Google 節點。
卡住
回到 n8n 環境檢查，確認 Docker 與工作區。

Step 2｜放入共同輸入

在 Manual Trigger 後加入 Edit Fields（Set），建立三個欄位：customer_identity=林小姐、message_text=物流延遲，客服回覆太慢、urgency_signal=2。最後一欄保持數字型別。

預期
Output 是一個 Item，含三個共同欄位。
檢查
JSON 中的 2 沒有引號。
卡住
回 Output 檢查欄位是否誤用 customer_name 或 feedback。
Checkpoint 1｜共同輸入已固定
三個欄位都有值、型別正確，且與 Bridge-1 的地圖一致。少一欄就回 Step 2。

Step 3｜建立契約檢查

加入 If，命名 Contract fields present。用 AND 連接三個條件：customer_identity 不為空、message_text 不為空、urgency_signal 是數字。

預期
林小姐資料走 True；缺值或型別錯誤走 False。
檢查
True 只代表契約通過，還不能宣稱已建立文件。
卡住
先看上一節點的實際 JSON，再修 Expression 路徑。

Step 4｜寫出安全錯誤出口

在 False 出口接 Edit Fields，命名 contract_error_stop，輸出 route=contract_error_stop、reason=必要欄位缺少或型別錯誤、downstream_executed=false。

預期
錯誤資料有明確終態，不流向文件或通知。
檢查
未補造缺失資料，也未將文字轉成布林。
卡住
記下第一個 False 條件，再從該步重跑。

Step 5｜加入 needs_review 分流

在 True 出口後加入第二個 If，命名 Needs review?。先用 Edit Fields 放入固定輸出，再判斷布林 needs_review=true 是否成立。

預期
True 進 manual_review；False 進 ready_for_delivery。
檢查
案例 A 停止且不產生 Docs、Email 或本機檔案。
卡住
確認值是布林 true；文字 true 不算同一型別。

Step 6｜建立兩個安全終態

True 出口接 Edit Fields 輸出 route=manual_review、artifact_status=stopped_before_delivery、rerun_from=Needs review?；False 出口輸出 route=ready_for_delivery、artifact_status=ready_for_next_step。

預期
每條路徑都能說明資料在哪裡、由誰接手、從哪裡重跑。
檢查
A 的 artifact_status 是 stopped_before_delivery。
卡住
回 Step 5 確認分支，不要刪除人工出口。
Checkpoint 2｜最小契約流程完成
你可以按 Execute 重跑「輸入 → 契約檢查 → needs_review → 終態」。這條路徑穩定後，才適合接 Webhook、本機資料夾或 PDF。
(05)　Verify｜三案例與證據

用 A／B／C 確認成功與安全停止

每次只改一個主要條件。請保存執行時間、停止節點、輸出 JSON 與 evidence mode；沒有平台紀錄就保留 SIMULATED 或 NOT_RUN。

案例測試值預期終態驗收證據
A｜需要人工needs_review=truemanual_review；停止、不交付停止節點、人工負責人、N8N 或 SIMULATED
B｜通過needs_review=falseready_for_delivery輸出欄位、下游尚未接入的限制、證據狀態
C｜型別錯誤needs_review="false" 或必要欄位空白contract_error_stop錯誤欄位、未執行下游、修正後重跑方式
放行條件
A、B、C 都能在你的紀錄中找到「輸入 → 分支 → 終態 → 證據」。缺少任一段，整合流程維持未放行。
(06)　Handoff｜交接與重跑

把成果交給下一位接手者

交接包要讓沒有參與設定的人也能重建判斷。請把 n8n-contract-flow-v1、更新後的 platform-map-v1、A／B／C 測試紀錄、環境限制與還原方式放在同一資料夾。

  • 寫出 Make 版本與 n8n 版本，兩邊的執行證據分開保存。
  • 列出三個共同輸入欄位、型別與一筆具體測試值。
  • 說明 manual_review、ready_for_delivery、contract_error_stop 的責任人與重跑位置。
  • 標記候選 JSON、模擬輸出與尚未執行項目，不填虛構 URL、credential 或 execution ID。
  • 記下本機資料夾、Docker、API、備份與資料離開本機的限制。

交接完成後，下一節才接本機檔案、PDF 批次或雲端通知。若要替換輸入入口，沿用相同契約與三案例，再重新驗證欄位路徑、認證、缺值行為與批次邊界。

(07)　Revision｜遇到問題怎麼回來

用最短路徑修復並留下證據

看不到欄位

回上一節點 Output，確認實際 JSON 與型別，再修 Expression。不要用預設字串補掉缺值。

分支走錯

檢查 needs_review 是否為布林，以及 If 的比較方式；重跑 A／B／C。

匯入失敗

先把候選檔標為 DRAFT_IMPORT_CANDIDATE，回到手動六步，記下版本與錯誤位置。

完成本頁後，你應能說明雲端 Make 留下什麼、本機 n8n 接手什麼、哪裡可能需要人工，以及哪些結果仍等待驗證。這份說明與測試證據會成為後續檔案處理與 LLM 協同修改的邊界。
