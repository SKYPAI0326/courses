FINAL PROJECT · 4.3

AI 計劃生成器：課程壓軸實戰

整合前面 Module 的技能——Webhook 接收需求，Gemini 生成結構化行動計劃，n8n 存成可閱讀的本機 Markdown，Make 再選擇是否發送通知。流程自動化的是草稿產出，內容仍要人工檢查。

⏩ 時間調配提示：本節先完成 Manual Trigger → Edit Fields → AI 回應 → Markdown 檔案的基準流程。時間不足時，保留固定 AI 回覆檔案與執行記錄，外部 Webhook／Gmail 放到課後延伸；每位學員仍要完成一次本機輸出。
🧭 先選你的進入方式：已完成 4.1／4.2 的學員，可沿用 Google Forms → Make → n8n；尚未完成外部串接時，先用 Manual Trigger → Edit Fields（Set） 建立同樣的 body.project_name、body.objective、body.deliverables、body.owner 欄位，直接驗證「輸入 → AI JSON → 本機 Markdown」核心。若沒有 API key，可下載固定 AI 回覆，在 Step 3 的 Edit Fields 節點重現同一個輸出結構。可先填入：
project_name：2026 校慶科技展　｜　objective：吸引 500 人參與並展示 AI 應用　｜　deliverables：活動企劃書、分工表、時程表　｜　owner：活動組
最終成果 · 基準流程 + 延伸入口
①基準入口：在 n8n 用 Manual Trigger + Edit Fields（Set）填入一筆需求；已完成 4.1／4.2 者，也可用 Google Form → Make → Webhook 送入同樣欄位
②n8n 呼叫 Gemini API，依需求生成結構化行動計劃（JSON 格式）
③解析 AI 回傳，整理成可閱讀的 Markdown 任務清單
④Write File 儲存到本機 shared/AI計劃/，保留一份可檢查的成果
⑤延伸：若已接上 Webhook，可把結果回傳 Make，再由 Gmail 發送通知；未接外部服務不影響基準成果
STEP BY STEP · 操作步驟
1
準備輸入資料：先跑基準，再選外部入口
先在主機的 n8n-starter-kit/shared/ 建立 AI計劃/ 輸出資料夾。為了讓每位學員都能先完成核心流程，新增 Manual Trigger 後接 Edit Fields（Set），建立 body.project_name、body.objective、body.deliverables、body.owner 四個欄位。已完成 4.1／4.2 的學員，才把這個入口替換成 Google Forms → Make → n8n Webhook；欄位名稱保持相同，後續節點不用改。
// Edit Fields（Set）可先填入這筆測試資料 body.project_name: 2026 校慶科技展 body.objective: 吸引 500 人參與並展示 AI 應用 body.deliverables: 活動企劃書、分工表、時程表 body.owner: 活動組
判斷方式：只看到 Manual Trigger 就走基準入口；若你已經有 4.1／4.2 的 Webhook 與 Make，才使用外部入口。兩條路徑最後都要交給同一個 HTTP Request 節點。
Checkpoint 1：Edit Fields Output 看得到四個 body. 欄位，且專案名稱、目標與交付物都來自同一筆測試資料。沒有這四欄時，先不要建立 AI 節點。
2
設計能穩定輸出 JSON 的 Prompt
Prompt Engineering 是本步驟的核心。要讓 Gemini 穩定回傳可解析的 JSON，必須在 Prompt 中明確指定格式、禁止 markdown，並提供欄位範例。
Prompt 範本
你是管過 5+ 個跨部門專案的 PM，熟悉週報同步與里程碑拆解。請針對以下專案需求，生成一個詳細的行動計劃，並以純 JSON 格式回傳（不要包含 markdown 標記或額外說明文字）。 專案名稱：[專案名稱] 目標：[目標] 期望交付物：[期望交付物] JSON 格式如下： {"project": "...", "objective": "...", "tasks": [{"task": "任務名稱", "owner": "建議負責人角色", "start": "YYYY-MM-DD", "end": "YYYY-MM-DD", "status": "未開始", "deliverable": "產出"}]}
提示：明確寫「不要包含 markdown 標記」是關鍵。若 Gemini 仍然輸出 ```json ... ```，在 Code 節點加入清除 markdown 的邏輯。
Checkpoint 2：Prompt 已包含專案名稱、目標、交付物與 JSON 範例；你能說出每個欄位會從哪個輸入值帶入。
3
HTTP Request 節點：呼叫 Gemini API 生成計劃
有可用 API key 時，在 Manual Trigger → Edit Fields（Set）之後，或在外部 Webhook 之後，接上「HTTP Request」節點，呼叫 Gemini API。先到 Google AI Studio API Keys 建立測試 key，再在 n8n 的 Credentials 建立 Header Auth：Name 填 x-goog-api-key，Value 貼上 key；HTTP Request 的 Header Auth 選用這個 credential，頁面上的 URL 不要直接放 key。沒有 API key 或不想啟用外部服務時，改在同一位置新增 Edit Fields，建立 JSON 類型的 candidates 欄位，貼入固定 AI 回覆，並將本次模式記為 SIMULATED，直接進入 Step 4。
// HTTP Request 設定（有 API key 時） Method: POST URL: https://generativelanguage.googleapis.com/v1beta/models/gemini-2.0-flash:generateContent Header Auth: x-goog-api-key = YOUR_KEY // Body（JSON） { "contents": [{ "parts": [{ "text": "你是管過 5+ 個跨部門專案的 PM，熟悉週報同步與里程碑拆解。請針對專案「{{ $json.body.project_name }}」，目標「{{ $json.body.objective }}」，期望交付物「{{ $json.body.deliverables }}」，生成詳細行動計劃。以純 JSON 格式回傳，不要包含 markdown：{\"project\":\"...\",\"tasks\":[{\"task\":\"...\",\"owner\":\"...\",\"start\":\"YYYY-MM-DD\",\"end\":\"YYYY-MM-DD\",\"status\":\"未開始\",\"deliverable\":\"...\"}]}" }] }] }
服務界線：模型可用性、速度與 API 額度依帳號、模型與官方方案而異。若計劃不夠詳細，先在 Prompt 中加入「請生成至少 6 個具體任務，每項任務需說明負責人角色與具體產出」，再以執行記錄確認結果。
Checkpoint 3：API 路徑的 Output 出現 candidates；固定回覆路徑的 Edit Fields Output 也出現同名欄位。兩條路徑都能交給 Step 4 的 Code。
4
Code 節點：解析 AI 回傳並格式化成 Markdown
用 Code 節點解析 Gemini 回傳的 JSON，然後把結構化任務清單轉換為易讀的 Markdown 格式——包含標題、目標說明、任務表格，以及任務狀態清單。
// Code 節點 const raw = $input.item.json.candidates?.[0]?.content?.parts?.[0]?.text || ''; const clean = raw.replace(/^```(?:json)?\s*/i, '').replace(/\s*```$/, '').trim(); let plan; try { plan = JSON.parse(clean); } catch (error) { throw new Error('AI JSON 無法解析，請回到 HTTP Request Output 檢查原始回應'); } let md = `# 行動計劃：${plan.project}\n\n`; md += `**目標：** ${plan.objective ?? '未指定'}\n\n`; md += `## 任務清單\n\n`; const tasks = Array.isArray(plan.tasks) ? plan.tasks : []; if (!plan.project || tasks.length === 0) { throw new Error('AI JSON 缺少 project 或 tasks[]；請回到 Prompt 與 HTTP Request Output 檢查'); } tasks.forEach(t => { const done = t.status === '已完成' ? 'x' : ' '; md += `- [${done}] **${t.task}**\n`; md += ` - 負責人：${t.owner}　期間：${t.start} ~ ${t.end}\n`; md += ` - 產出：${t.deliverable}\n\n`; }); const ts = new Date().toISOString().slice(0,10).replace(/-/g,''); const fileName = `${ts}_${plan.project.replace(/\s/g,'_')}.md`; return [{ json: { md, fileName, project: plan.project } }];
提示：?.（Optional Chaining） 在這裡很有用——如果 AI 漏掉某個欄位，不會導致整個流程崩潰（例如 t.owner ?? '待指派'）。
Checkpoint 4：Code Output 有 md、fileName 與 project，且 tasks[] 至少有兩筆可閱讀任務。若出現 parse error，回看 Step 3 的原始回應。
5
Write File 儲存計劃文件
用「Convert to File」節點把 Markdown 字串轉為二進位，再用「Read/Write Files from Disk」的「Write File to Disk」操作儲存到本機的計劃資料夾。檔名包含日期和專案名，格式如 20260402_校慶科技展.md。
// Write File to Disk 設定 File Name: /files/shared/AI計劃/{{ $json.fileName }} Data: data（Convert to File 的輸出）
提示：Markdown 文件可以直接在 VS Code、Typora 或 GitHub 開啟並渲染，比純 txt 更專業。
Checkpoint 5：shared/AI計劃/ 出現以日期與專案命名的 Markdown 檔；開啟後能看到目標、任務、負責人、期間與產出。
6
延伸：回傳 Make → 發送 Gmail 完成通知
只有在你採用外部 Webhook 入口時，才需要接這一步：在 Write File to Disk 後新增「Respond to Webhook」，以 JSON 回傳計劃檔名和專案名給 Make（方法與 4.2 相同），Make 再發送 Gmail 通知。若你走 Manual Trigger 基準入口，看到本機 Markdown 檔案就已完成本節，不必為了驗收另開 Gmail 或 Make。
// ① n8n 新增 Respond to Webhook 節點 Respond With: JSON // ② Response Body：回傳給 Make 的資料 { "status": "success", "request_id": "{{ $json.request_id ?? 'm4-3-local' }}", "project": "{{ $json.project }}", "fileName": "{{ $json.fileName }}" }
提示：外部串接完成後，可以用手機填表測試；尚未完成外部串接時，請以本機 Markdown 成果與 Executions 記錄作為驗收依據。
完成驗證 · VERIFY
完成輸入後：（1）starter kit 主機的 shared/AI計劃/ 資料夾出現 Markdown 文件，（2）打開文件確認至少有專案名稱、目標與任務清單（每筆包含任務、負責人、日期與產出）。若已接上 Make／Gmail，再確認（3）收到檔名與狀態通知；尚未接外部服務時，記錄為延伸待驗證，不影響本節本機核心成果。n8n 節點的輸出路徑是 /files/shared/AI計劃/。
完成本節基準流程
你已整合了 Module 1 的環境建置、Module 2 的數據引用與邏輯判斷、Module 3 的批次文件處理，以及 Module 4 的雲地協作與 AI 生成——完成一套屬於自己的可重跑 AI 工作流程。
後續可依資料政策與外部服務設定，決定哪些步驟可自動化、哪些必須人工檢查。
常見問題 · TROUBLESHOOT
Gemini 回傳的 JSON 格式不穩定，有時包含 markdown 有時不包含？
在 Code 節點加入標準化清除邏輯：const clean = raw.replace(/```[\w]*\n?|\n?```/g, '').trim()，無論有沒有 markdown 包裝都能安全解析。同時把 JSON.parse 包在 try-catch 中，失敗時記錄原始 raw 方便 debug。
AI 生成的任務清單只有 2-3 項，感覺不夠詳細？
在 Prompt 中加入數量要求，如「請生成至少 6 個具體任務」。另外在「目標」欄位填入更多細節，AI 會根據輸入的豐富程度調整輸出深度。
整個流程跑到一半停了，不知道哪個節點出錯？
在 n8n 的「Executions」頁籤查看最近的執行記錄，點擊失敗的執行可以看到每個節點的輸入/輸出，找到第一個紅色錯誤節點逐一排查。
✅ 完成檢查 · 跑完本節你應該看到
  1. 固定資料模式（SIMULATED）：Manual Trigger + Edit Fields（Set）或 Webhook（擇一入口）、Edit Fields（固定 candidates）、Code（清 markdown 包裝 + JSON.parse）、Convert to File 與 Write File to Disk 全部亮綠；HTTP Request 不列入本模式驗收。
  2. API 模式（MAKE／API）：若已建立 Header Auth 並取得 API 回應，HTTP Request、Code、Convert to File 與 Write File to Disk 全部亮綠；API key 或額度不足時改走固定資料模式並標記 SIMULATED。
  3. Gemini 回應：Output 面板可看到 JSON 文字，解析後至少包含 project、objective、tasks[]；每筆任務含 task、owner、start、end 與 deliverable。
  4. 本機資料夾：shared/AI計劃/ 出現以日期與專案命名的 Markdown 檔，內容可以在文字編輯器中閱讀。
  5. 外部服務（選做）：若走 Webhook 入口，Make 收到 n8n 回傳的 status、request_id、project 與 fileName，Gmail 發出完成通知；若走 Manual Trigger，這一項標記為「未接外部服務」，不影響本節驗收。Google Docs／LINE 仍是後續延伸。
  6. Executions 頁：本次執行為綠色 Success，沒有 429 / timeout / parse error。
任一項對不上 → 對照上方「常見問題」；429 請放慢 Loop + Wait；JSON.parse 失敗請看 Code 節點的清理邏輯。
💼 實戰案例
情境｜某行銷公司客戶每週要 5 份活動企劃初稿——以前實習生寫 3 天，現在 AI 10 分鐘產完 + 人工 1 小時改。
做法｜n8n 接客戶需求表 → Gemini API 生 JSON 結構化企劃 → 寫入本機 Markdown → Make 發 Gmail 通知。
踩雷｜Gemini API 額度依模型、帳號與方案而異（請查 官方 Rate limits 頁面）。集中時段批次跑容易超過當前 RPM/RPD 觸發 429——以 Loop Over Items（每批 10）+ Wait 10 秒控速，並把工作量分散到不同小時跑。
