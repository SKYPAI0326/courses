M0 · VALIDATION PLAYBOOK

驗證實戰：把每個 workflow 跑成看得見的成果

你正在幫工作室把收件匣、客戶檔案與營運資料變成可交付成果。本章把「點 Execute」改成一條有情境、有檢查點、有恢復路徑的操作動線；每完成一段，都留下檔案、JSON、通知或 execution 作為證據。

你會完成至少 7 個核心流程的可重現驗收，知道哪些是主線、哪些是延伸。
你會判讀畫布綠框、Execution、輸出檔與 Telegram 通知各自代表什麼。
你會排錯路徑、權限、憑證、API 限速與空輸入，不靠 LLM 猜答案。
本章動線
先完成環境基線，再依情境逐段驗收。左側會跟著閱讀位置標示目前階段。

(01) ORIENT

先決定「什麼算成功」

情境
課堂中最容易出現的假成功，是畫布停在執行中、終端機貼錯內容，或 LLM 沒讀到檔案卻仍然生成一篇看似完整的文字。本章先把輸入、預期產物與證據寫清楚，再開始操作。

每個案例都用同一個判讀順序：輸入真的存在嗎？→ 節點是否成功？→ 產物是否落在正確位置？→ 內容是否能回溯到輸入？ 只有最後一項也成立，才算完成。

A
可觸發
Execute、Webhook、Schedule 或檔案觸發有回應。
B
可讀取
輸入檔、欄位、憑證與環境變數確實被節點讀到。
C
可交付
寫出檔案、JSON 或通知，內容可對照來源。
D
可恢復
遇到空輸入、壞檔或限速時，能看懂錯誤並重跑。
🧭
操作習慣：不要把終端機回傳的 JSON 當成指令執行；它是「結果」。看到 aiError: null 也只表示 API 節點沒有回報錯誤，仍要打開輸出檔確認內容確實引用了輸入。
(02) READY

環境、資料夾與兩套系統先對齊

情境
學員可能在 Mac 或 Windows 操作；Lite Pack 由同一份 workflow 提供兩套環境的教學路徑。先完成一次安裝與資料夾檢查，後面的失敗才有可判斷的起點。
  1. 依平台進入 Mac 安裝頁 或 Windows 安裝頁，完成 Docker Desktop、starter-kit 與 setup-wizard。
  2. 在 n8n Overview 確認總數為 14；Credentials 至少有 Gemini，Telegram 案例再確認 Telegram credential。
  3. 在檔案管理器或終端機確認 `shared/` 下有英文資料夾：`pdf-inbox`、`pdf-renamed`、`batch-inbox`、`daily-input`、`daily-output`、`ai-output`、`client-inbox`、`client-organized`。
  4. 先把測試素材放到對應資料夾；不要自行改成講義舊版的中文資料夾名稱。
⚠️
已知教材落差：部分 Module 3 舊頁仍寫 `shared/待處理PDF`、`每日文件` 等中文路徑；Lite Pack 與 wizard 實際使用英文路徑。本章以實際套件為準，舊頁請先看 檔案監看、PDF 改名、日報 時特別留意。
看到才能繼續14 個 workflow；Gemini credential 測試成功；測試資料確實在英文資料夾。
看不到先停下數量不符、資料夾空白、或 setup-wizard 沒有完成。先回安裝頁，不要用空輸入測 AI。
(03) CORE BASELINE

先跑三個「基準流程」建立判讀感

這一段的意義
#01、#05、#08 不依賴外部檔案或複雜 AI，適合先建立「觸發 → 節點 → 輸出 → execution」的觀察習慣。
#01

Webhook hello-world

主線

情境：你剛啟動 n8n，先確認本機能接受外部 GET 並回傳固定 JSON。

操作步驟
  1. 開啟 #01 workflow，按畫布下方橘色 Execute workflow。
  2. Webhook 節點進入等待狀態後，在瀏覽器開啟測試 URL：http://localhost:5678/webhook-test/lite-hello。
  3. 等頁面回應；不要按右上角 Publish。
  4. 回 n8n 查看 Webhook 與 Set 節點的 execution 輸出。
成功證據
瀏覽器收到 {"message":"hello from lite pack"}；兩節點出現綠框，Execution 可回看 1 item。
設計意義

把「能不能觸發」與「回傳什麼」拆成兩個責任，後續換成 POST body 仍沿用同一個骨架。

#05

Telegram smoke test

主線

情境：先驗證 Telegram credential 與通知通道，再把通知接到會產生檔案的流程。

操作步驟
  1. 開啟 #05 workflow，確認 Telegram 節點已選定 credential。
  2. 按 Execute workflow；等待 Manual Trigger、Telegram 節點綠框。
  3. 在手機 Telegram 找到測試 bot，確認收到 Lite Pack 通知。
成功證據
n8n 顯示成功 execution；手機收到完整測試訊息。只看到綠框但沒收到訊息，仍不算通過。
設計意義

通知是可觀察性，不是流程本身；先測通道能把後續 AI 失敗與 Telegram 失敗分開。

#08

Expression 語法練習場

主線

情境：你需要讀取巢狀資料、跨節點欄位與環境變數，先在可控的假資料上練習。

操作步驟
  1. 開啟 #08 workflow，按 Execute workflow。
  2. 依序打開 Set 假資料、Set expression 範例、Code 複合資料處理，查看 Output 的 JSON。
  3. 只改一個 expression，例如把 optional chaining 的欄位改成不存在的路徑，再執行一次。
  4. 觀察 `?.` 與 `??` 如何避免 undefined 讓整條流程中斷。
成功證據
Output 同時呈現 user object、items array 與處理後欄位；改一個 expression 後能在 execution 看出差異。
設計意義

在真實檔案前先學會資料形狀與 fallback，能降低「看起來有資料、實際讀錯欄位」的風險。

(04) FILE PIPELINE

文件流程：先確認讀到，再相信 AI 產物

情境
文件自動化的核心不是「AI 生成一個檔名」，而是能證明輸入 PDF 被讀取、文字被抽出、命名依據來自原文，而且失敗檔案有去處。
#02

PDF AI 改名

主線

情境：`pdf-inbox` 裡有 `doc-001.pdf` 等待整理，希望依文件日期、類型與對象產生可搜尋檔名。

操作步驟
  1. 把測試 PDF 放進 `shared/pdf-inbox/`，確認至少有一份真正可讀的 PDF。
  2. 開啟 #02 workflow，按 Execute workflow。
  3. 逐一查看 Read PDF、Extract PDF Text、Code 與 Write 節點輸出；不要只看最後檔名。
  4. 確認新檔出現在 `shared/pdf-renamed/`，再開啟檔案內容或檔名比對原文。
成功證據
每份輸入都有對應的 `newPath`；`parseMethod`、`finishReason` 與 `pdfTextLength` 有值；輸出檔可在檔案夾找到。
設計意義

Extract PDF Text 是 AI 前的可驗證邊界；若 `pdfTextLength` 為 0，後面的命名再漂亮也不能交付。

看 AI fallback 與命名規則 →
#03

批次處理錯誤恢復

主線

情境：一次收到多份 PDF，其中可能混入 `not-a-pdf.pdf`；好檔案要完成，壞檔案要留在 failed，不能拖垮整批。

操作步驟
  1. 把測試包的 4 份 good PDF 與 `not-a-pdf.pdf` 放入 `shared/batch-inbox/`。
  2. 開啟 #03 workflow，按 Execute workflow。
  3. 查看 Code AI 改名節點的 Success／Error 分支數量。
  4. 確認 good 檔案移到 `batch-processed/`，壞檔案移到 `batch-failed/`，並查看錯誤摘要。
成功證據
成功與失敗數量加總等於輸入數；兩個資料夾都有對應結果；單一壞檔沒有讓整個 execution 失敗。
設計意義

錯誤是資料流的一條路徑，不是全域例外。這個模式可延伸到 API 限速、欄位缺漏與權限問題。

#04

定時 AI 日報

主線

情境：每天把 `daily-input` 的 PDF、Markdown、TXT 彙整成一篇日報；日報必須能指出實際讀到哪些檔案。

操作步驟
  1. 把 3–4 份測試檔放入 `shared/daily-input/`，混合 PDF 與文字檔。
  2. 開啟 #04 workflow；課堂驗證時使用 Manual Execute，正式排程再看 Schedule。
  3. 確認 Switch 依副檔名分流，PDF 與純文字都經過 Extract，再到 Aggregate。
  4. 打開 AI 與 Write 節點輸出，確認日報的 `filesCount`、`sourceFiles` 或等價欄位對得上實際輸入。
  5. 開啟 `shared/daily-output/daily-YYYY-MM-DD.md`，抽查摘要是否引用來源內容。
成功證據
`filesCount` 等於實際輸入數；`sourceFiles` 列出檔名；`aiError` 為 null 仍要搭配內容抽查；空資料夾不應生成假日報。
設計意義

Aggregate 保留來源清單，讓日報具備可追溯性，避免 LLM 在沒有讀到檔案時自行補寫。

(05) AI + WEBHOOK

外部提問：看到回應，也要看到寫檔與通知

情境
使用者從瀏覽器或 Make 送來一個問題，Gemini 產生回答，n8n 同時寫成本機 Markdown、送 Telegram，並回傳 JSON。三個輸出都成功才算完成。
#06

Webhook → Gemini → 本機檔

主線

情境：用一個可重現的問題測 API，不把「即時天氣」誤當成 Gemini 具備瀏覽能力的證明。

操作步驟（本機測試）
  1. 開啟 #06 workflow，按 Execute workflow，等 Webhook 進入等待。
  2. 在終端機貼上整段請求（這是要執行的指令）：
curl -X POST http://localhost:5678/webhook-test/ai-ask \
  -H "Content-Type: application/json" \
  -d '{"question":"請用三點說明 n8n webhook 的用途"}'
  1. 先看終端機回傳的 JSON，再回 n8n 查看各節點 execution。
  2. 確認 `shared/ai-output/ai-YYYYMMDDHHMMSS.md` 出現，Telegram 收到通知，回應包含 `status: ok`、`question` 與 `answer`。
  3. 打開 Markdown 檔，確認問題與回答真的對應本次請求。
成功證據
Code 輸出 `aiError: null`；回傳 JSON、Markdown 檔、Telegram 三者都有；檔名時間與 execution 時間接近。
設計意義

Webhook 是入口，Code 統一資料形狀，Write／Telegram／Respond 各自是可觀察的交付端。任何一端缺失都能定位。

🔐
API 提醒：Gemini 新申請的 key 可能是 AQ 開頭；請只放在 `.env`／n8n credential，不要貼到講義或截圖。模型名稱以目前套件可用設定為準，遇到 404／429 先看 Code 的 `httpError` 與 log。
看本機與 Web UI 分支 →
#07

Quick Tunnel 接外部觸發

延伸

情境：要讓 Make、手機或朋友從網路觸發本機 n8n；這一步牽涉公開 URL 與 production workflow，適合主線跑通後再做。

操作步驟
  1. 先啟動套件附的 `tunnel-quick.command`（Mac）或 `tunnel-quick.bat`（Windows），保留終端機視窗。
  2. 複製終端機顯示的 `https://xxxxx.trycloudflare.com`，開啟 #07 workflow。
  3. 右上角按 Publish；在 Webhook 的 Production URL 確認路徑是 `/webhook/external-ping`。
  4. 用公開 URL 加上 `?message=hello` 呼叫，確認瀏覽器收到 status: ok，Telegram 收到外部 ping 通知。
  5. 到 Executions 查到成功紀錄；測試完取消 Publish（或關閉 Active），再在 tunnel 視窗按 Ctrl+C。
成功證據
公開 URL 回傳 JSON；Execution 顯示 Succeeded；Telegram 有通知。畫布不一定保留綠框，production 驗收以 Executions 為準。
設計意義

把「本機測試 URL」與「已發布 production URL」分開，讓學員理解 webhook 的生命週期與暴露風險。

🌐
Cloudflare quick tunnel URL 每次可能不同；不要把舊 URL 寫死在講義。課堂只記錄當次 URL，測完立即停用。
(06) EXTEND

延伸資料流：從個別案例走向業務資料

情境
主線驗收後，再把同一個「讀取 → 判斷 → 寫出 → 留證」模式套到客戶資料、CSV 與知識庫。這些流程更接近工作室日常，但也更需要準備資料。
#10

客戶資料夾自動整理

延伸

情境：`client-inbox` 混有 PDF、圖片、文字與規則格式，需分類到 6 個客戶資料夾並保留 index。

操作步驟
  1. 使用 sample pack 的混合 9 檔素材放入 `shared/client-inbox/`。
  2. 執行 #10 workflow，觀察圖片／規則格式的 bypass 與 AI 分類路徑。
  3. 確認 `client-organized/` 下產生分類資料夾與 `_index.md`。
  4. 在輸出查看 `_batchInfo.inputCount`、`outputCount`、`ruleFallback` 與 warnings。
成功證據
輸入與輸出數可對帳；每個檔案有分類依據；`_index.md` 能回溯原始檔案。
設計意義

先用規則處理高信心格式，再讓 AI 處理需要語意判讀的檔案，降低成本與不確定性。

#11

銷售線索 CSV 清洗評分

延伸

情境：業務收到重複、格式不一的 leads CSV，希望得到可用資料與評分報告。

操作步驟
  1. 把含 `name/email/phone/company` 欄位的 CSV 放入 `shared/leads-inbox/`。
  2. 執行 #11 workflow，查看電話標準化、重複移除與 email 判斷。
  3. 確認 `leads-output/leads-cleaned.csv` 與 `leads-report.md` 都出現，Telegram 收到摘要。
  4. 抽查 3 筆原始資料與清洗後資料，確認不是只產出漂亮的報告。
成功證據
輸出 CSV 可開啟；報告列出輸入／輸出／去重數；抽查結果能回溯原始列。
設計意義

把 deterministic cleaning 與 AI score 分開，讓資料品質問題不會被模型摘要掩蓋。

#12

本地知識庫問答

延伸

情境：把 `knowledge-docs` 建成可查詢索引，回答時必須附來源，不讓模型憑空回答。

操作步驟
  1. 先把教材或文字檔放入 `shared/knowledge-docs/`，執行 Part A 建索引。
  2. 確認 `knowledge-index/knowledge-index.jsonl` 存在，並在輸出看到 `_stats.indexed > 0`、`totalChunks > 0`。
  3. Publish 後執行 Part B POST `/webhook/kb-ask`，或用 Part C Web UI 提問。
  4. 挑一個能在文件中找到答案的問題，檢查回答是否列出 sources。
成功證據
索引統計大於 0；回答附來源檔名／chunk；問不存在的內容時能誠實表示找不到。
設計意義

索引是資料邊界，sources 是信任邊界；沒有這兩項就不算 RAG 驗證成功。

(07) OPERATE & OPTIONAL

營運流程與選修：知道何時跳過

情境
#09、#13、#14 需要額外憑證、排程或等待時間。它們很有價值，但不應阻塞第一堂課的主線交付。
#09

Gmail 分類通知

選修

需要 Gmail OAuth，對一般學員有 Google Cloud OAuth consent screen 與測試使用者門檻；課堂時間不足時直接跳過。

若要驗證
  1. 先完成 Gmail credential 與 OAuth 授權，再開啟 #09 workflow。
  2. 用測試信件驗證分類與 Switch 分支，只有客訴才送 Telegram。
  3. 到 Executions 查看 polling 結果；不要用「沒有新信」判定失敗。
成功證據／設計意義
有授權、有測試信、有分類結果；理解 Trigger polling 與通知條件。

把外部 OAuth 門檻明寫，學員才不會把環境問題誤認成 n8n 節點問題。

#13

每日營運快照與異常提醒

選修

Schedule 09:00 讀取 today.csv 與歷史 CSV，只有偏差超過 30% 才通知；正常執行可能沒有 Telegram。

驗證重點
  1. 使用含刻意異常的 sample data；先手動 Execute，再看 `ops-snapshots/`。
  2. 確認異常列進入 AI 摘要與 Telegram，正常列不重複通知。
設計意義

「沒有通知」可能是正確結果；要看 snapshot 與 anomaly count，不能只用手機訊息當唯一證據。

#14

私有 API 監控與診斷

選修

每 15 分鐘檢查 endpoints；sample 內含 `http://localhost:9999` 故意失敗的 URL，失敗時才寫 incident 與通知。

驗證重點
  1. 先執行 #14 workflow 的手動測試，確認健康與失敗分支都能跑。
  2. 失敗時檢查 `ops-incidents/` JSON 與 Telegram；正常時接受「沒有通知」。
設計意義

監控流程的完成定義包含正常與異常兩種狀態，故意失敗的 fixture 是可重現的驗收設計。
