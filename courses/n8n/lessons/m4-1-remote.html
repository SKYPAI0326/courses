Google Forms 遠端遙控 n8n

填表單 = 下指令。用手機提交 Google Forms，Make 接力轉送，本機 n8n 立刻啟動對應的文件處理任務。

先看懂本節的兩條路徑 · START HERE

這一節要理解「外部表單如何把資料送進本機 n8n」。請先用固定資料完成本機測試，確定 Webhook 能收到資料、Switch 能分流，再依需要接上雲端服務。固定資料可從這裡下載；完成後應留下 Webhook 收件畫面、分流結果與一次測試紀錄。若資料來自 Make，先閱讀 BRIDGE-1 資料契約，確認 task_type=document_request 與 data 結構，再設定 Webhook 欄位路徑。

主路徑｜本機固定資料

需要：已啟動的 n8n、瀏覽器與終端機（macOS Terminal 或 Windows PowerShell）。
會完成：Webhook → Switch 的可重複測試。全程不需 Google Forms、Make 或 Tunnel。

延伸路徑｜遠端表單

需要：Google 帳號、Make 帳號、Apps Script 授權、持續運作的 n8n，以及 Module 1 的 Quick Tunnel。外部平台額度與介面依帳號狀態而定。
會完成：Google Forms → Make → Tunnel → n8n。

本節順序：兩條路徑都先做 Step 1；主路徑接著做 Step 4 → Step 6，延伸路徑則做 Step 2 → Step 3 → Step 4 → Step 5 → Step 6。跳過的步驟請保留為「延伸」標記，回到主路徑完成核心驗證。

STEP BY STEP · 操作步驟
1
選擇路徑，準備一筆可追蹤的申請資料
先下載固定測試資料，確認三個欄位的意義：applicant 是申請人、document_type 決定分流、due_date 用來記錄期限。主路徑直接保留這份 JSON；要做遠端延伸時，再開啟 Google Forms，建立「申請人」簡短答案、「文件類型」選擇題（報告／企劃／合約）與「截止日期」日期欄位，並全部設為必填。
// m4-1-form-request.json：主路徑的固定資料 { "applicant": "王小明", "document_type": "報告", "due_date": "2026-09-30" }
提示：表單標題建議取名「文件處理申請」，讓填表人清楚知道提交後的效果。完成後複製表單連結，之後可直接用手機開啟填寫。
2
延伸｜Make.com 建立 Webhook 接收表單資料
只有選擇遠端路徑時才做這一步。在 Make.com 建立新 Scenario，第一個模組選「Webhooks → Custom webhook」。點擊「Add」建立新 Webhook，複製產生的 Webhook URL。Make 會進入 Listening 狀態等待第一筆測試資料；主路徑學員直接跳到 Step 4。
提示：先不要關閉 Make Scenario，保持 Listening 狀態。接下來設定 Google Forms → Make 的連接，送出測試資料後 Make 會自動識別欄位結構。
3
延伸｜連接 Google Forms → Make（用 Apps Script）
只有選擇遠端路徑時才做這一步。在 Google Forms 點擊右上角「⋮」→「Apps Script」，貼入以下程式碼，將 Make 的 Webhook URL 填入。儲存後設定觸發條件：「表單提交時」執行 onSubmit 函數；第一次授權時，依 Google 畫面完成授權。
// 替換為你的 Make Webhook URL const MAKE_WEBHOOK = 'https://hook.make.com/YOUR_WEBHOOK_ID'; function onSubmit(e) { const vals = e.namedValues; const payload = { applicant: vals['申請人'][0], document_type: vals['文件類型'][0], due_date: vals['截止日期'][0] }; UrlFetchApp.fetch(MAKE_WEBHOOK, { method: 'post', contentType: 'application/json', payload: JSON.stringify(payload) }); }
提示：設定觸發條件：Apps Script 左側「觸發條件」→「+ 新增觸發條件」→ 函數選 onSubmit，觸發事件選「表單提交時」。
4
主路徑｜n8n 設定 Webhook 觸發節點
在 n8n 建立新 Workflow，新增「Webhook」觸發節點。Method 設為 POST，Path 設為 form-request。先使用 Test URL，讓節點等待測試資料；完成主路徑後，延伸路徑才改用 Production URL 與 Tunnel。
// n8n Webhook 本機 URL http://localhost:5678/webhook/form-request // 透過 Cloudflare Tunnel 的對外 URL（Module 1 設定的） https://YOUR-TUNNEL-NAME.trycloudflare.com/webhook/form-request
// macOS Terminal：先把檔案下載到 Downloads，再切換到該資料夾 cd ~/Downloads curl -X POST -H "Content-Type: application/json" \\ --data-binary @m4-1-form-request.json \\ http://localhost:5678/webhook-test/form-request # Windows PowerShell：先把檔案下載到 Downloads，再切換到該資料夾 Set-Location "$env:USERPROFILE\Downloads" $body = Get-Content .\\m4-1-form-request.json -Raw Invoke-RestMethod -Method Post -ContentType "application/json" ` -Body $body -Uri "http://localhost:5678/webhook-test/form-request"
找不到檔案時：先在瀏覽器下載列確認檔名是 m4-1-form-request.json。也可以開啟檔案後全選複製 JSON，直接貼到可發送 POST 的工具中；資料內容必須與本頁範例一致。
Checkpoint 1A｜本機路徑：點擊 Webhook 的「Listen for test event」後，用上方指令送出直接包含 applicant、document_type、due_date 的固定資料。Webhook Output 看到三個根層欄位，才進入下一步。看不到資料時，先確認 URL 是 webhook-test，以及終端機目前位於檔案所在資料夾。
Checkpoint 1B｜BRIDGE 遠端路徑：Make 送入的原始資料會在 body.task_type 與 body.data；不要用根層欄位判斷是否成功，先完成 Step 6 的 Normalize，再檢查 bridge_data。
提示：確認 Cloudflare Tunnel 仍在運行（命令列視窗還開著）。若 Tunnel 重新啟動，URL 會改變，需更新 Make 的 HTTP Request 目標。
5
延伸｜Make 新增 HTTP Request 轉發資料到 n8n
只有選擇遠端路徑時才做這一步。在 Make Scenario 的 Webhook 之後，新增「HTTP → Make a request」模組。Method 選 POST，URL 填入 n8n 透過 Cloudflare Tunnel 的外部 URL。Header 加入 Content-Type: application/json，Body 把 Webhook 收到的欄位轉送。主路徑可略過本步，直接在本機完成 Step 6。
// Make HTTP Request Body（Raw JSON） { "request_id": "document-demo-001", "source_platform": "make", "task_type": "document_request", "evidence_mode": "MAKE", "data": { "applicant": "{{1.applicant}}", "document_type": "{{1.document_type}}", "due_date": "{{1.due_date}}" } }
提示：Body Type 選「Raw」→ Content Type 選「JSON (application/json)」，才能讓 n8n 正確解析傳入的資料。每次測試請替換 request_id，方便對照 Make 與 n8n 的同一筆執行。
6
主路徑｜先整理契約，再用 Switch 根據文件類型分流
在 n8n Webhook 後先加入「Code」節點，名稱設為 Normalize bridge data。它同時接受本機固定資料的直接欄位與 Make BRIDGE-1 的 data 封裝，先檢查三個必填欄位，再將合格資料統一成 $json.bridge_data。接著加入「IF」節點檢查 contract_status 是否為 accepted：True 才進入 Switch，False 接到標記為「契約錯誤」的 No Operation。Switch 再以 {{ $json.bridge_data.document_type }} 分流報告／企劃／合約；未知類型走契約錯誤出口。
// Code：Normalize bridge data（Run Once for Each Item） const incoming = $json.body ?? $json; const data = incoming.data ?? incoming; const required = ['applicant', 'document_type', 'due_date']; const missing = required.filter((key) => data[key] == null || String(data[key]).trim() === ''); const allowedTypes = ['報告', '企劃', '合約']; if (missing.length) { return [{ json: { ...$json, contract_status: 'rejected', contract_error: { code: 'MISSING_REQUIRED', fields: missing }, bridge_data: null } }]; } if (!allowedTypes.includes(String(data.document_type))) { return [{ json: { ...$json, contract_status: 'rejected', contract_error: { code: 'UNSUPPORTED_DOCUMENT_TYPE', value: data.document_type }, bridge_data: null } }]; } return [{ json: { ...$json, contract_status: 'accepted', bridge_data: { applicant: data.applicant, document_type: data.document_type, due_date: data.due_date, request_id: incoming.request_id ?? 'local-test' } } }]; // IF 節點設定 Value 1: {{ $json.contract_status }} Operation: is equal to Value 2: accepted True → Switch False → No Operation（命名：契約錯誤） // Switch 節點設定 Value: {{ $json.bridge_data.document_type }} Case 1: 報告 → 連接報告產生流程 Case 2: 企劃 → 連接企劃產生流程 Case 3: 合約 → 連接合約產生流程 Default: 未支援類型 → 契約錯誤出口
提示：提交表單後，先點 n8n Webhook 節點的「Test URL」，讓節點進入接收狀態。Make 送出資料後，n8n 會顯示收到的完整 JSON，確認結構正確再繼續。
Checkpoint 2：本機固定資料通過時，Normalize Output 的 contract_status 應為 accepted，bridge_data 有三個欄位與 request_id；IF True 後，報告 應只走報告分支。把 document_type 改成「合約」再送一次，應改走合約分支。
Checkpoint 3：把 Make BRIDGE-1 封裝送入時，Webhook Output 應看到 body.task_type 與 body.data；Normalize 後才檢查 bridge_data。故意刪除 data.due_date 時，contract_status 應為 rejected，IF False 走契約錯誤出口，不能進入 Switch 或建立空文件。
完成驗證 · VERIFY
主路徑完成：固定 JSON 送入 Test URL 後，Normalize Output 顯示 contract_status=accepted 與 bridge_data 三個欄位，IF True 後 Switch 依文件類型進入正確分支，並保留兩次執行記錄。
延伸路徑完成：再用手機填寫 Google Forms，Make 執行記錄顯示 Success，n8n Webhook 收到 BRIDGE-1 的 task_type 與 data，Normalize 後進入對應分支；缺值測試要顯示 contract_status=rejected 並停在契約錯誤出口。三項畫面或執行記錄可作為 m4-1-remote-test-v1 完成證據。
常見問題 · TROUBLESHOOT
Make 收到 Google Forms 資料但 HTTP 轉送失敗（n8n 沒收到）？
確認 Cloudflare Tunnel 仍在運行。若 Tunnel URL 失效，重新啟動 cloudflared 並更新 Make HTTP Request 的目標 URL。另外確認 n8n Workflow 已切換到 Active 狀態；若仍無資料，先用本機固定路徑重跑 Step 4，確認 Webhook 本身可收件。
n8n 收到資料但欄位路徑不對（取不到 applicant）？
本機固定資料可能直接在 Webhook 根層；Make BRIDGE-1 則會包在 $json.body 下，文件申請人的完整路徑是 {{ $json.body.data.applicant }}。依本頁 Code 的 Normalize 結果，後續節點統一讀 {{ $json.bridge_data.applicant }}；先在 Webhook Output 判斷封裝，再檢查 contract_status。
缺少 due_date 或文件類型不在三個 Case？
回到 Normalize Code，確認欄位名稱與 BRIDGE-1 任務型別一致。缺少必填欄位或遇到未支援類型時，應看到 contract_status=rejected 並走 IF False 的契約錯誤出口；此時不建立文件，修正輸入後從 Webhook 重新送出。
Apps Script 執行時顯示「未經授權」錯誤？
第一次執行時 Google 會要求授權。在 Apps Script 點「Run」→ 在彈出視窗同意授權。之後設定好觸發條件，就不需要再手動執行。
💼 實戰案例
情境｜某工作室老闆出國仍能透過 LINE 指令觸發本機 n8n 處理客戶訂單。
做法｜LINE Bot → Webhook → Cloudflare Tunnel → 自架 n8n → 處理完 LINE 回覆。能否在不付費的方案內完成，取決於 LINE、Cloudflare、n8n 與外部 API 的當前條款與用量；課前需逐項確認。
踩雷｜LINE Bot Messaging API 的主動推播額度依 LINE 當前方案與條款而定（請查 官方 pricing）；被動回覆與主動推播的計算方式也可能不同。設計上別讓 bot 主動推播太多，用『收到才回』的互動式設計。
安全提醒 · WEBHOOK SECURITY

遠端遙控本機 n8n 等於把控制面板對外開放。請務必：

  1. 測試期使用不易猜的 webhook path（例如 UUID），避免被機器人掃描觸發。
  2. 正式使用一定要加驗證：在 n8n Webhook 節點開啟 Header Auth 或 Basic Auth，並在 Apps Script / Make 端帶相對應 token；或在 Cloudflare Access 設來源限制。
  3. LINE Bot 的 Channel Access Token、Webhook signature key 用 n8n Credentials 集中管理；驗證 LINE 推播時記得驗 x-line-signature 防偽造。
  4. 含 credential 的 workflow JSON 不公開分享；export 前用「Reset Credentials」清乾淨。
