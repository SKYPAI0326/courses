#04 · DAILY AI REPORT · 8 NODES + 1 NOTE · 進階

每天 8:00 自動讀資料夾、AI 摘要、產 Markdown 日報

這是 #02／#03 的進階變體：先讀取 daily-input/，再依副檔名把 PDF 與純文字送往各自的抽取節點，最後合併成一批來源交給 Gemini。學完這頁，你能設計「定時讀多份輸入 → 保留來源 → AI 統整 → 結構化輸出」的早報、週報與專案摘要流程。

學習成果
能用 Schedule Trigger + cron expression 設定每天 / 每週 / 每月定時觸發
能用 Switch 分流 PDF／純文字，讓每份檔案走正確的抽取節點
能用 Aggregate 節點把多個 items 合併成 1 個 files array，並保留每份來源檔名
能設計含來源標記與衝突提醒的 Markdown 日報 prompt（摘要／待辦／決策／風險）
(01) WORKFLOW 全貌

節點與資料流

Schedule: 每天 08:00 → Read daily-input → Switch: 副檔名分流 → Extract PDF ／Extract 純文字

↘ Aggregate 多檔合併 → Code: AI 摘要 + 組 Markdown → Write daily-output

這條流程有 8 個功能節點與 1 張畫布說明卡。Read 讀入 daily-input/ 後，Switch 依副檔名分成 PDF 與純文字兩路；兩路各自抽取文字，再回到 Aggregate 合併。這樣一批輸入只會交給 AI 一次，且每份內容仍帶著檔名，後續可以回到原檔核對。最後 Code 產生日報與來源清單，Write 將 Markdown 寫入 daily-output/。

(02) NODE BREAKDOWN

節點逐一拆解（重點看分流、來源與驗收）

NODE 1 / 8
Schedule: 每天 08:00
scheduleTrigger v1.2cron

關鍵設定：cronExpression: 0 8 * * *（每天早上 8:00）。

cron 5 個欄位：分 時 日 月 週。常用範例：

  • 0 8 * * *：每天早上 8:00
  • 0 18 * * 1-5：週一到週五傍晚 6:00
  • 0 0 * * 0：每週日凌晨 0:00（週報）
  • */5 * * * *：每 5 分鐘（測試用）

注意：Schedule Trigger 必須把 workflow 開 Active才會真的定時跑。沒開 Active 只能手動 Execute。

NODE 2–5 / 8
Read → Switch → Extract PDF／Extract 純文字

Read 節點抓取 /files/shared/daily-input/*，每份檔案先成為一個 item。Switch 讀取 $binary.data.fileExtension：副檔名為 pdf 時送到 Extract PDF，其餘走 Extract 純文字。這個分流讓 PDF 解析與 .txt／.md 讀取各自使用正確的 operation；兩路會在下一個 Aggregate 節點匯合。

操作檢查：測試時在兩路輸出都看到 item，且檔案數量與 daily-input/ 內的檔案數相同。若某一路為 0，先檢查副檔名與 Switch 的 fallback output。

NODE 6 / 8
Aggregate 多檔合併 ← 關鍵節點
aggregate v1

用途：把多個 input items 合併成 1 個 item，把指定欄位變成 array。

關鍵設定：aggregate: aggregateAllItemData、destinationFieldName: files、include: allFields。

Input 是多個抽取後的 items；Output 是 1 個 item，將每份 item 的欄位放入 files array。Code 節點會從這個 array 取文字與檔名，並補回讀檔節點的 binary 檔名，避免來源只剩「檔案-1」。

下游 AI Code 節點只跑一次，把整批內容當 context 餵給 Gemini。輸出日報尾端會列出來源檔案，學員可依檔名回到 daily-input/ 查證。

NODE 7 / 8
Code: AI 摘要 + 組 Markdown
code v2

Code 節點先把每份來源整理成含 fileName、sourcePath、text 的資料，再呼叫 Gemini。Prompt 要求只使用輸入內容；每項摘要加上 [來源：檔名]；找不到負責人填 未指定；遇到金額或決策衝突要列出各來源，禁止自行補名字、日期、金額或狀態。

Code 節點 return 的 JSON 會含 outputPath、markdown、aiError、filesCount、filesProcessed、sourceFiles。其中 filesProcessed 是驗證來源是否真的讀入的第一個檢查點；Markdown 尾端的「來源檔案」區塊是第二個檢查點。

安全閘門：如果 AI 回應沒有逐一出現每個來源的 [來源：檔名]，Code 會把回應改為人工核對訊息，並將 aiError 設為原因。這可避免把沒有證據鏈的文字直接寫成日報。

NODE 8 / 8
Write: daily-output/

fileName: {{ $json.outputPath }} 寫到 shared/daily-output/daily-YYYY-MM-DD.md。完成後打開檔案，核對四段內容、來源檔案清單與 Code JSON 的數量。

(03) DESIGN RATIONALE

為什麼這樣設計

💭
為什麼 maxOutputTokens 設 2000 而 #02 只設 200？
Markdown 日報含 4 段結構化內容容易 800-1500 tokens。設 2000 留餘裕；同時使用 thinkingConfig: { thinkingLevel: 'minimal' }，避免推理消耗過多輸出額度。
⚠️
輸入太少，摘要容易失真：實測時如果 daily-input/ 內只有 1–2 份簡短測試檔（總字數 < 200），模型可能補出輸入沒有的產品名或待辦。課堂請使用可辨識的會議記錄、待辦或專案檔案；完成後以 filesProcessed、來源清單與原檔逐項核對，才採用日報內容。
(04) 改造方向

5 種改造方向

  1. 改 cron 排程：8:00 換成你的工作節奏（凌晨 6:00、中午 12:00、晚上 23:00）。週報設 0 9 * * 1（每週一早上 9 點）。
  2. 換 prompt 改風格：「給高層看的精煉版（每段 1-2 句）」/「給同事看的詳細版」/「給客戶看的成果報告」。同個架構切換不同對象。
  3. 串 Email 寄日報：在 Write 之後加 Email Send 節點（Gmail / SMTP），每天日報自動寄到自己信箱。
  4. 串 Telegram 推日報：複製 #05 Telegram 節點接在 Code 後面，把 markdown 推到你的 Telegram。
  5. 多語言版本：同個 input 跑 2 次 prompt（中 + 英），輸出兩份 daily-{date}-zh.md / daily-{date}-en.md。
