(B6) · 6 小時

用固定任務測試修正 Prototype

把一條 B4 互動交給另一個人重跑，留下能支持修正決策的紀錄。

學習成果
寫出含角色、起點、任務、操作與預期的測試腳本。
用 Actual／Expected 分開記錄，分類問題根因。
一次只改一個變因，完成同一任務的回歸測試。
(01)

從使用情境建立測試問題

阿凱把 B4 的任務回饋交給雯姊審查。雯姊能開啟畫面，卻不知道點擊後應該看到什麼。這堂課的完成物是一筆可重跑的測試紀錄、一個問題分類、一個最小修正，以及同一任務的回歸結果。

現在在哪裡B4 的 Host → Overlay 單一 action
手上有什麼B4 Figma 檔、Chrome Preview，以及 B6 起始頁（HTML）；先用起始頁確認工具、材料與測試表，若新視窗受限可直接開啟 uiux-designer/assets/B6-prototype-task-test/START-HERE.html
要留下什麼case_id、Actual／Expected、repair、rerun_result、證據路徑
第一步開啟上面的 B6 起始頁，確認看到測試表欄位後再複製它
可以繼續的結果另一個人能依腳本從 Host 開始點擊一次
測試邊界：本節只驗證一條 On click → Open overlay → Dialog / Overlay；登入、資料保存與第二個 action 另列待辦。
(02)

四個概念決定要記錄什麼

任務腳本是角色在固定起點執行一次任務的文字；Expected是操作前先寫下的可見結果；Actual是 Preview 實際呈現的結果；根因分類把差異放進內容、結構、互動、可讀性或方案限制。

看到的現象分類第一個修復位置
點擊後沒有目的地互動Prototype action 的 Destination
Preview 從空白畫布開始結構Host 的 Flow starting point
確認文字不一致內容Overlay 內的文字層
第二個 action 觸發升級提示方案限制另存一個測試檔並標 CONDITIONAL
(03)

操作示範：從失敗輸入走到回歸結果

先使用一筆固定輸入，觀察中間結果，再決定修哪裡。這樣可以區分「測試記錄」與「修正操作」。

欄位示範值判斷理由
case_id／起始狀態B6-001／Preview 從 Screen / Host 開始每次回歸都從同一畫面起跑
任務／操作確認任務回饋／點擊 Host 一次一個任務只保留一個動作
Expected看到「確認完成」Overlay操作前先寫，避免被 Actual 帶走
Actual（第一次）點擊後停在 Host保留原始失敗證據
分類／repair互動／把 Destination 指向 Dialog / Overlay只改造成差異的欄位
rerun_result同一起點再次點擊，看到 Overlay同一腳本通過才交 B7

這筆紀錄就是完成物的最小版本；若 Actual 與 Expected 相同，仍要保留證據路徑，讓接手者知道測試真的跑過。

(04)

跟著做：八步完成一筆測試

步驟學員操作預期結果沒看到時
1開 B6 起始頁與測試表看見欄位與 B4 輸入說明先確認 Chrome 能讀取 assets 路徑
2填角色、起始狀態與 case_id別人知道從哪裡開始缺欄就停在表格，不進 Preview
3填單一任務、操作、Expected腳本可被照做刪掉「試看看」等模糊動詞
4從 Host 開 Preview，點擊一次Actual 有畫面結果回 B4 檢查 Flow 起點
5把 Actual 與 Expected 分欄差異可被指出不要把 Expected 複製到 Actual
6為差異選一個根因分類有第一個修復位置先記現象，標記 BLOCK
7只改一個變因並保留前版repair 可回溯回上一個可重開檔重新做
8重跑同一腳本並填 rerun_result回歸結果可重現沒有證據就停在 Checkpoint
(05)

Checkpoint：判斷修正是否真的有效

現在應該有一筆紀錄：同一個 case_id、相同起點與任務、一次修正，以及一次回歸。三者缺一，不能把結果交給 B7。

  • 通過：另一個人能照表從 Host 開始，看到 Expected 指定的 Overlay。
  • 未通過：保留第一次 Actual、截圖與回復位置，再回到第 6 步重新分類。
  • 平台限制：若 Starter 顯示多 action 升級提示，記為 CONDITIONAL，另建測試檔；不按 Upgrade。
安全停止位置是「回歸前的可重開檔」。不要刪除整個檔案，也不要用講師口頭補充取代證據。
(06)

Solo：只改一個主要變因

複製 B4 的通過版本，將 Expected 文字改成「已儲存，回到任務清單」。Frame 尺寸、起點、Destination 與 Animation 保持不變。先預測新文字，再跑同一個 case_id 的副本，再比對兩次 Actual。

保持不變唯一變化交付檢查
Host、Overlay、起點、actionOverlay 文字同一操作得到新文字，沒有新增 action
測試者、Chrome、螢幕尺寸case_id 後綴 -solo前後版本與證據路徑可分辨
(07)

交付給 B7 的測試包

B7 需要知道哪一個 Figma 版本可以匯出、哪個 case_id 已回歸、還有哪些限制。把以下檔案或連結放進交接欄位：

  • B6 起始頁：工具、材料與第一步。
  • TASK-TEST-FORM：固定欄位與回歸紀錄。
  • Figma 檔連結、case_id、Actual／Expected、repair、rerun_result、證據路徑。
  • 未完成項目：登入、資料保存、第二個 action 都標成待辦。
(08)

完成檢查與自我測驗

  • 我能說明測試者、起始狀態、任務、操作與 Expected。
  • 我把 Actual 與 Expected 分開，保留第一次失敗結果。
  • 我只改一個主要變因，並用同一腳本回歸。
  • 我能指出互動問題與方案限制的不同去向。

Q1：為什麼 Actual 要在修正前記錄？答：它保留原始狀態，讓修正前後可以比較。
Q2：第二個 action 觸發 Starter 限制時怎麼做？答：停止升級，另建測試檔並在紀錄標示條件。

完成後按 下一堂：B7 Handoff 交付，把回歸通過的來源版本交給下一個單元。

(09)

操作示範記錄：誰負責、何時停止

B5 的 SCROLL-01／case_id 是本堂測試起始材料。測試負責人記錄 Actual，證據缺失時停止並重試同一個任務。保留截圖、case_id 與回復位置，這筆紀錄與測試表一起成為 B6 完成物。
