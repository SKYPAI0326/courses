# 設計能讓人知道下一步的回饋、彈窗與導覽
副標：工作室人員完成任務、遇到提醒或失敗時，都要立刻知道發生什麼事以及下一步怎麼做。
本堂完成物：成功、警告與錯誤三種提示；一個確認完成彈窗；手機與桌面導覽

## 從任務詳情接著做，補上操作後的回應

工作室人員已能從待處理清單打開「整理交付包」詳情，但按下「標記完成」之後，畫面還沒有說明結果。若操作成功卻沒有回應，使用者可能重複按；若資料尚未核對，系統需要先提醒；若儲存失敗，更要說清楚可以怎麼恢復。這堂會用成功、警告、錯誤三種提示處理結果，再用 Dialog（對話框）處理需要先確認的決定。

這項工作會使用上次完成的 `Screen / List`（待處理清單）、`Screen / List Empty`（空清單）、`Screen / Detail`（任務詳情）與 `Button / Complete`（完成按鈕）。先看[本堂起始材料](../assets/A8-toast-dialog-navigation/START-HERE.html)，確認這些畫面與 Button 元件都在同一頁；需要按鈕時從 Assets（元件資產面板）插入。完成三種提示、彈窗與導覽後，再用[完成檢查表](../assets/A8-toast-dialog-navigation/reference/EXPECTED-CHECK.html)逐項比對。

先把任務流程用一句話寫在畫布旁：「從待處理清單看詳情，確認完成後回到完成清單。」這句話會幫你判斷回饋放在哪個時刻：確認前需要 Dialog，完成後需要成功提示，資料有風險時需要警告，儲存失敗時需要錯誤提示。導覽則持續告訴使用者目前位於待處理或已完成。

## 先選回饋方式，再決定外觀

這一節要先分清楚每個元素處理的問題。Toast（短暫提示）用來告知剛剛發生的結果；警告提示指出目前有風險，但仍可能繼續；錯誤提示說明動作沒有完成，並給出恢復方向；Dialog 會停下流程，讓使用者做出選擇；Navigation（導覽）則維持位置感。

例如，「任務已移到已完成」是已發生的結果，適合成功提示。「這筆任務還有未核對的檔名」是繼續前要注意的風險，適合警告提示。「無法儲存變更，請檢查網路後再試一次」表示動作失敗，適合錯誤提示。「確認要把這筆任務標記完成嗎？」需要明確回答，適合 Dialog。

| 工作情境 | 使用元素 | 文字要回答什麼 | 使用者下一步 |
|---|---|---|---|
| 任務完成並移出待處理 | 成功提示 | 完成了什麼、結果在哪裡 | 繼續工作或查看完成清單 |
| 資料仍有需要注意之處 | 警告提示 | 有什麼風險、繼續會怎樣 | 回去檢查或決定繼續 |
| 儲存或連線失敗 | 錯誤提示 | 哪個動作失敗、如何恢復 | 重試或回到安全狀態 |
| 重要狀態即將改變 | Dialog | 要確認什麼、結果是什麼 | 取消或確認 |
| 待處理與已完成切換 | Navigation | 目前在哪裡、還能去哪裡 | 前往另一個主要區域 |

三種提示都要有「類型＋具體文字」，顏色與圖示只負責加快辨認。成功可以寫「任務已完成，已移到完成清單」；警告可以寫「尚有檔名未核對，請確認後再完成」；錯誤可以寫「無法儲存變更，請檢查網路後再試一次」。只寫「成功」「注意」「錯誤」會讓使用者知道情緒，卻不知道發生了什麼。

Dialog 只用在需要決定的時刻。它的順序是「問什麼」「會造成什麼結果」「有哪些選擇」；按鈕文字要直接寫動作，例如「取消」與「確認完成」。導覽則應在每張主要畫面保持同一位置，用文字和底線共同標示目前頁，讓位置感不只依賴顏色。

## 示範：建立三種提示與確認彈窗

這一節會先做共用的提示結構，再建立確認彈窗。規格表保存現稿的主要尺寸與間距；新增的警告與錯誤沿用成功提示的結構，只替換內容角色。

| 圖層或元件 | 規格 | 內容或用途 |
|---|---|---|
| `Toast / Success` | Horizontal；Gap 8；水平 Padding 16；垂直 Padding 12；Hug 寬高 | 「任務已完成，已移到完成清單」 |
| `Toast / Warning` | 同成功提示結構；Warning 色與警告圖示 | 「尚有檔名未核對，請確認後再完成」 |
| `Toast / Error` | 同成功提示結構；Error 色與錯誤圖示 | 「無法儲存變更，請檢查網路後再試一次」 |
| 提示文字 | 16／24；Auto height | 結果、風險或恢復方向 |
| `Overlay / Confirm` | Vertical；Gap 16；四邊 Padding 24；寬 320；Hug 高；白底；圓角 8 | 確認完成彈窗 |
| `Dialog / Title` | 24／32；Fill；Auto height | 「確認完成？」 |
| `Dialog / Body` | 16／24；Fill；Auto height | 「這筆任務將移到已完成清單。」 |
| `Dialog / Actions` | Horizontal；Gap 12；寬 272；Hug 高 | 取消與確認按鈕列 |
| `Button / Cancel` | Secondary／Default；高 48；Fill | 「取消」 |
| `Button / Confirm` | Primary／Default；高 48；Fill | 「確認完成」 |

1. 建立一個小勾號或「✓」文字，套用 Success 色。完成後會看到成功類型的第一個辨認線索。
2. 建立提示文字，輸入「任務已完成，已移到完成清單」。完成後結果與去向會一起出現。
3. 同時選取圖示與文字按 **Shift+A**，命名為 `Toast / Success`（成功提示），再套用規格表中的 Auto layout。完成後圖示與文字會成為一個能隨內容增高的容器。
4. 複製成功提示，命名為 `Toast / Warning`（警告提示），替換圖示、色彩與文案。完成後會看到一個指出風險與下一步的版本。
5. 再複製一份，命名為 `Toast / Error`（錯誤提示），替換圖示、色彩與文案。完成後會看到一個說明失敗與恢復方法的版本。
6. 將三種提示放在同一個元件區並排比較。完成後它們的結構、內距與文字層級會一致，類型與內容則各自清楚。
7. 在手機畫面外建立 Frame，命名為 `Overlay / Confirm`（確認彈窗）。完成後會得到可包含文字與按鈕的父容器。
8. 建立 `Dialog / Title`（彈窗標題）與 `Dialog / Body`（彈窗說明），填入規格表內容。完成後彈窗會先問問題，再解釋結果。
9. 從 Assets 插入兩個 Button 使用處，分別設定為取消與確認。完成後兩個選擇會沿用既有按鈕家族。
10. 同時選取兩個按鈕按 **Shift+A**，命名為 `Dialog / Actions`（彈窗動作列），再套用規格表設定。完成後兩顆按鈕會等寬排列。
11. 將 Title、Body、Actions 放入確認彈窗，套用垂直 Auto layout。完成後彈窗會依標題與說明長度自動增高。

在動作列寬 272、間距 12 的情況下，兩顆等寬按鈕各占 130。這個算式只用來理解現有版面；如果按鈕文字變長，先比較水平與垂直排列的可讀性，再決定結構。保留文字大小與按鈕高度，比把長文字壓成難讀的一行更穩定。

接著把 Body 改成較長的說明：「確認後這筆任務會移到已完成清單；如果資料尚未核對，請先取消並返回詳情修正。」文字使用 Auto height，外層使用 Hug，Actions 會自然往下移。這次測試證明彈窗能承受內容變化，也為警告情境留下足夠說明空間。

## 跟著做：把結果放回清單，再建立導覽

這一節要把元件放回工作室流程。先為完成結果準備畫面，再補上手機與桌面位置感；每一步都要能看到清楚的頁面狀態。

1. 複製待處理清單，命名為 `Screen / List Done`（完成清單畫面），把「整理交付包」狀態改成「已完成」。完成後會有一張能承接成功結果的畫面。
2. 將成功提示放在完成清單頂部內容區。完成後使用者會知道任務已移動，而且提示不會遮住主要操作。
3. 將警告提示放在任務詳情的測試副本。完成後畫面會在確認前指出尚未核對的內容。
4. 將錯誤提示放在另一個詳情副本。完成後會清楚說明儲存失敗與重試方向。
5. 建立「待處理」與「已完成」兩個導覽項目，分別包進小 Frame。完成後會得到兩個可排列的主要區域入口。
6. 將兩個項目水平排列，命名為 `Nav / Bottom`（手機底部導覽），再套用規格表中的手機值。完成後導覽會橫跨手機底部。
7. 在待處理清單用 Primary 文字與底線標示「待處理」，在完成清單改為標示「已完成」。完成後兩張畫面都能直接看出目前位置。
8. 複製一份桌面參考，建立 `Nav / Desktop`（桌面導覽）。完成後導覽會位於桌面上方，並能容納工作室名稱與較完整的連結。
9. 對照手機與桌面兩版，寫下位置與資訊密度的理由。完成後你能說明兩者服務相同目的，但因畫面空間採用不同配置。

手機導覽的現稿規格是兩個項目各寬 201、高 64，合起來寬 402、Gap 0，放在畫面底部；桌面導覽寬 1200、高 64，位於上方。此時先完成視覺與內容，後面處理捲動時再決定固定位置。桌面空間較大，可以加入品牌名稱；手機優先保留兩個短而清楚的目的地。

最後把工作室流程排成五個內容節點：登入、待處理清單、任務詳情、確認彈窗、完成清單。取消會回到詳情，確認完成會前往完成清單；目前先用畫布位置與文字說明表達，後面的原型階段再建立實際連線。

## 看兩版回饋，判斷哪一版能指引下一步

這一節要比較回饋是否只表達情緒，或真的提供行動方向。版本一在儲存失敗後顯示紅色小框，文字只有「錯誤」；確認彈窗標題寫「你確定嗎？」，兩顆按鈕都寫「確定」。版本二的錯誤提示寫「無法儲存變更，請檢查網路後再試一次」；彈窗標題是「確認完成？」，說明任務會移到完成清單，按鈕是「取消」與「確認完成」。

請判斷哪一版能回答「發生什麼」「結果是什麼」「我能怎麼做」。再指出版本一的哪一段文字會讓使用者無法預測按下後的結果，以及版本二如何讓安全離開與主要動作容易區分。

## 卡住時，回到元素的工作重新檢查

這一節用「這個元素本來要解決什麼」來找原因。提示處理結果與風險，彈窗處理選擇，導覽處理位置；把責任分清楚，修復會更直接。

| 看到的現象 | 通常的原因 | 怎麼修 |
|---|---|---|
| 三種提示只靠顏色區分 | 文案只寫成功、注意、錯誤 | 補上具體結果、風險或恢復方向 |
| 提示長句被裁切 | 文字或外層使用固定高度 | 將文字設 Auto height，外層設 Hug |
| Dialog 的子層無法一起排列 | 外層使用 Rectangle | 改用 Frame，將 Title、Body、Actions 移入 |
| 兩顆按鈕文字太擠 | 水平 Actions 不適合目前文案 | 比較改短文字或垂直排列，保留可讀尺寸 |
| 導覽看不出目前頁 | 選中狀態只改了顏色 | 同時加入底線與文字差異 |
| 成功提示蓋住主要按鈕 | 提示放在操作區上方 | 移到頂部內容區，保留主要操作空間 |

修完後先遮住顏色，只讀文字與排列。若仍能分辨成功、警告、錯誤、取消、確認與目前頁，代表資訊沒有只依賴視覺色彩。

## 換你做：報名確認 App

現在把回饋系統移到活動報名。行政人員在詳情按「確認報名」時，可能成功完成、遇到特殊需求提醒，或因網路中斷而失敗；在真正改變狀態前，還需要確認彈窗。手機底部導覽則要讓人切換待確認與已確認報名。

要達成的條件：

- 製作成功提示，說明這筆報名已確認以及結果會出現在哪裡。
- 製作警告提示，用於備註含特殊需求時，文字要指出應先查看的內容。
- 製作錯誤提示，用於網路中斷，文字要提供可行的恢復方向。
- 製作「確認報名」彈窗，包含清楚標題、結果說明、取消與確認動作。
- 製作手機底部導覽，讓待確認與已確認都有文字，並標示目前頁。
- 用張家豪的特殊需求備註測試警告；讓彈窗與提示在 360 寬畫面中保持可讀。

合格的結果要能通過以下自我檢查：

- 三種提示即使遮住顏色，也能從文字辨認用途。
- 警告說明需要先檢查的特殊需求，錯誤說明如何重試。
- 彈窗能回答要確認哪一筆操作，以及確認後會改變什麼。
- 取消是次要但可操作，確認報名是主要且可操作。
- 底部導覽以文字和另一個視覺線索共同標示目前頁。

- 快捷鍵：Shift+A 加 Auto layout，對應規格書第 5 節「快捷鍵」。

- 主線提示值：成功提示 Horizontal／Gap8／水平 Padding16／垂直12／16／24／Hug，對應現稿 CH8「跟著做」第 1 步；警告與錯誤沿用同結構，內容類型依規格書第 3、4 節新增要求。
